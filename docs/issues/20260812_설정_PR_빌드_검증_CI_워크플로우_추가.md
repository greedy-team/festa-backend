# 🔧 [설정][CI] PR 빌드 검증 워크플로우 추가

## 📝 작업 내용

- develop, main 으로 향하는 Pull Request에서 빌드 검증이 자동으로 돌도록 워크플로우를 추가합니다
- JDK 21 환경 구성, Gradle 캐시 적용, 빌드 실행까지 포함합니다
- 테스트 결과를 PR 댓글로 요약하고, 실패한 테스트는 해당 코드 줄에 표시되도록 리포트 단계를 함께 넣습니다
- 테스트 실행에 필요한 설정값을 CI에서 어떻게 공급할지 함께 정합니다 (아래 영향 범위 참고)

## 🎯 필요한 이유

- 현재 백엔드에는 PR 단계 검증이 하나도 없습니다. 컴파일이 깨진 코드도 develop에 머지될 수 있는 상태입니다
- 프론트엔드는 이미 PR에서 빌드 검증이 돌고 있어 두 레포의 기준이 어긋나 있습니다
- 저장소에 있는 워크플로우는 모두 이슈·릴리스 자동화용이며, 빌드 검증은 포함되어 있지 않습니다

## ⚠️ 영향 범위

- 빌드와 개발 환경에만 영향을 줍니다. 제품 코드는 바뀌지 않습니다
- 지금 빌드가 통과하는 이유는 테스트가 하나도 없기 때문입니다. 테스트 디렉터리 자체가 없는 상태입니다
- 애플리케이션 설정이 DB_URL, DB_USERNAME, DB_PASSWORD, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, JWT_SECRET, AES_KEY 일곱 개를 필수로 요구합니다. 스프링 컨텍스트를 띄우는 테스트가 처음 추가되는 순간 이 값들이 없어 CI가 실패합니다
- 리포트 단계는 테스트 결과 파일을 읽는데, 테스트가 0개인 현재는 그 파일이 생성되지 않습니다. 파일이 없을 때 경고만 남는지 단계가 실패하는지는 첫 PR에서 확인하고, 실패한다면 옵션을 조정합니다
- 검증 기준은 정상 PR에서 통과하는 것만으로 부족합니다. 컴파일 오류를 일부러 넣은 커밋에서 실패하는 것까지 확인해야 항상 통과하는 워크플로우를 걸러낼 수 있습니다

## 🔎 테스트 환경에 대해 확인한 것

이 이슈를 진행하며 조사한 결과입니다. 다음 사람이 같은 조사를 반복하지 않도록 남깁니다.

- H2 인메모리 DB는 쓸 수 없습니다. V1__init.sql이 pg_trgm과 unaccent 확장을 생성하는 PostgreSQL 전용 DDL이고, Flyway가 켜져 있어 컨텍스트 로딩 시 무조건 실행되기 때문입니다
- 따라서 선택지는 Testcontainers로 실제 PostgreSQL 컨테이너를 띄우거나, CI 워크플로우에 서비스 컨테이너를 붙이는 두 가지입니다
- Testcontainers 방향이면 이 CI 워크플로우는 수정할 필요가 없습니다. GitHub 러너에 Docker가 이미 포함되어 있기 때문입니다. 반대로 서비스 컨테이너 방향이면 워크플로우를 고쳐야 합니다
- Testcontainers를 쓰더라도 앞의 일곱 개 중 DB 관련 세 개만 해결됩니다. OAuth 두 개와 JWT, AES 값은 여전히 테스트용 기본값이 따로 필요합니다
- 즉 첫 테스트를 다루는 후속 작업은 라이브러리 추가가 아니라 테스트 환경 구성 전체가 범위입니다

## 🔀 이 이슈에서 다루지 않기로 한 것

- 브랜치 보호 및 필수 상태 검사 설정. 현재 main과 develop 모두 보호되지 않아, 이 워크플로우는 머지를 차단하지 못하고 결과만 알립니다. 차단이 필요하면 별도 작업으로 분리합니다
- 배포 관련 사항 전부. 별도 이슈에서 다룹니다
