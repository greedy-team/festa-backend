## 본문

## 📝 현재 문제점

- 에러 응답 형식이 코드에 없다. 첫 API가 들어가는 순간 형식이 굳어지므로, 먼저 정해두지 않으면 나중에 모든 엔드포인트를 고쳐야 한다
- 형식은 회의에서 합의됐지만 구현으로 옮기지 않았다
- 성공 응답은 화면마다 다르게 쓰이니 제각각이어도 되지만, 에러는 터졌다는 같은 사건이라 형식이 같아야 프론트가 한 번만 처리한다

## 🛠️ 해결 방안 / 제안 기능

- 에러 응답을 네 필드로 통일한다
  - 에러 코드 — 예: FESTIVAL_NOT_FOUND
  - 메시지 — 예: 존재하지 않는 축제입니다
  - HTTP 상태를 담은 숫자 — 예: 404
  - 에러가 발생한 API 경로 — 예: /api/festivals/42/summary
- 경로는 값이 치환된 실제 요청 경로를 담는다. 경로 템플릿을 담으면 어느 엔드포인트인지만 알 뿐 어느 호출이 실패했는지는 알 수 없다
- 경로는 전역 예외 처리에서 일괄로 채운다. 개별 처리 지점에 맡기면 누락이 생긴다
- 메시지는 프론트 개발자가 디버깅할 때 보는 값이다. 사용자에게 그대로 노출하지 않으며, 사용자 문구는 프론트가 에러 코드별로 따로 준비한다
- 예외 클래스는 공통 하나만 둔다. 전역 예외 처리가 모든 예외를 같은 방식으로 다루므로 도메인별로 나눌 이유가 없다
- 에러 코드는 공통과 도메인별로 나누어 관리하고 하나의 규약으로 묶는다. 여러 명이 서로 다른 도메인을 동시에 작업할 때 코드가 한 파일에 몰려 충돌하는 것을 막는다
- 에러 코드 이름에 도메인 접두사를 붙인다. 코드 목록이 나뉘어 있어도 코드 문자열이 전역에서 유일해진다
- 파라미터 오류는 공통 코드 하나로 묶지 않고 개별 코드로 나눈다. 에러 코드 하나가 사용자 문구 하나에 대응하면 프론트가 응답 본문을 파헤치지 않아도 된다
- 필드별 오류 배열은 두지 않는다. 응답을 네 필드로 고정하기로 했으므로 다섯 번째 필드가 될 수 없다
- 도메인별 에러 코드와 파라미터 검증 매핑은 해당 API 이슈에서 이 규약에 맞춰 추가한다. 어떤 코드가 어떤 파라미터에 붙을지는 API가 정해져야 알 수 있다
