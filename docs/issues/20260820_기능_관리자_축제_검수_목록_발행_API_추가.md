## 본문

## 📝 현재 문제점

- **발행 게이트를 전제로 스키마를 짜놨는데 게이트가 없다.** `festival`의 NOT NULL은 셋뿐이고 마이그레이션 주석이 그 이유를 「미완성 저장을 허용하고 발행 게이트가 막는다」로 적었다. `published_at` 컬럼도 이미 있다. 막는 쪽이 아직 없어서 미완성 축제를 걸러낼 수단이 없다
- **임포트가 커밋한 축제는 전부 미발행으로 들어온다.** 발행 경로가 없으면 임포트한 축제는 영원히 공개되지 않는다
- **#34가 미발행 축제를 드러내기까지만 한다.** 대시보드 결정이 「이번 단계에서는 대시보드까지만 만든다」로 명시적으로 멈춰 있어, 관리자는 미발행 축제를 **볼 수는 있으나 발행할 수가 없다.** #32가 중복을 찾을 수는 있으나 합칠 수 없어 #36이 필요했던 것과 같은 모양이다
- 관리자가 미발행을 포함한 축제 목록을 볼 수단도 없다. 공개 목록 API는 발행된 것만 다룬다

## 🛠️ 해결 방안 / 제안 기능

- 관리자용 축제 검수 목록과 개별 발행·해제 API를 만든다 — `GET /admin/festivals`, `POST /admin/festivals/{id}/publish`, `DELETE /admin/festivals/{id}/publish`
- **발행 조건은 셋이다** — 라인업 0건, 주최 미연결, 좌표 없음. 앞의 둘은 명세가 `LINEUP_EMPTY`·`HOST_NOT_LINKED`로 이름을 정해뒀고, 세 번째는 ERD의 「`longitude` 없으면 발행 불가」에서 온다
- **세 번째 조건의 사유 이름이 명세에 없다.** 일괄 발행(후속 이슈)이 `failed[].reason`으로 내보낼 값이 필요하므로 여기서 정한다 — `COORDINATES_MISSING`. 명세와 갈리는 자리 1
- 개별 발행이 조건을 어기면 `PUBLISH_VALIDATION_FAILED`(400)로 막고, 어긴 조건을 응답에 함께 싣는다. 명세의 에러 코드 표에 「새 코드다. 표에 추가해야 한다」로 표시돼 있는 코드다
- **일괄 발행의 `failed[].reason`과 에러 코드는 다른 체계다.** 개별 발행은 부분 성공이 없으므로 HTTP 오류로 막고, 일괄 발행은 본문으로 사유를 돌려준다. 두 체계가 섞이지 않게 사유 값(`LINEUP_EMPTY` 등)을 에러 코드 enum에 넣지 않는다
- **발행 여부는 `published_at IS NOT NULL`로 판정한다.** 명세는 `published`(boolean)라 부르지만 스키마와 엔티티는 `published_at`(timestamptz)이다. 응답에는 `published`와 `publishedAt`을 함께 실어 화면이 「언제 발행됐는지」까지 쓸 수 있게 한다. 명세와 갈리는 자리 2
- **해제는 `published_at`을 null로 되돌린다.** 최초 발행 시각은 남기지 않는다. 명세의 발행 해제 응답 필드표가 비어 있어 정하는 자리다. 이력이 필요해지면 후속 이슈에서 별도 테이블로 붙인다. 명세와 갈리는 자리 3
- **이미 발행된 축제를 다시 발행하면 멱등으로 본다** — `published_at`을 유지하고 성공으로 답한다. 임포트가 「이미 발행된 축제는 자동 SKIP」으로 다루는 것과 같은 태도다. 해제도 마찬가지로 이미 미발행이면 그대로 성공이다
- 검수 목록은 미발행을 포함해 돌려주고, 발행 여부로 거를 수 있다. 페이지네이션과 정렬을 갖는다
- **목록의 검수 상태는 #34가 만든 `FestivalCoverageStatus`(PUBLISHED / REVIEW_PENDING / NEEDS_CHECK)를 재사용한다.** 같은 개념을 두 벌 만들지 않는다
- **파라미터 검증은 #32가 쓰는 `INVALID_PAGE`·`INVALID_PAGE_SIZE`를 재사용한다.** 명세가 새로 제안한 `INVALID_PARAMETER`는 만들지 않는다 — 에러 코드 표가 「이미 `INVALID_PAGE`·`INVALID_PAGE_SIZE`가 있어 역할이 겹친다, 통합할지 정해야 한다」로 남겨둔 자리를 기존 코드 재사용으로 닫는다. 명세와 갈리는 자리 4
- `/admin/festivals` 아래 컨트롤러가 #34의 커버리지와 둘로 갈리지 않게 한다. 커버리지가 이미 `@RequestMapping("/admin/festivals")`에 `/coverage`를 잡고 있으므로, 검수 목록·발행을 어디에 둘지는 #34 위에서 정한다
- 권한 없음(403) 응답은 만들지 않는다. 관리자 권한을 나누지 않기로 했으므로 #32·#36과 같다

## ⚙️ 작업 내용

- 검수 목록 조회 — 미발행 포함, 발행 여부 필터, 정렬, 페이지네이션
- 개별 발행 · 해제 엔드포인트
- 발행 게이트 검증 3종과 위반 조건 응답
- 발행 전용 에러 코드 추가
- 발행 상태 판정(`published_at`)과 응답 형식 정의
- **발행 게이트는 실제 DB 행으로 검증한다.** 라인업 0건·주최 null·좌표 null은 전부 스키마가 일부러 허용한 상태라, 그 조합이 실제로 막히는지는 실물로만 확인된다

## ⚠️ 선행 조건 · 범위 밖

- **#34(관리자 대시보드 커버리지)가 먼저다.** `/admin/festivals` 경로와 `FestivalCoverageStatus`를 공유하므로 병렬로 가면 같은 자리에 두 벌이 생긴다
- **일괄 발행(`POST /admin/festivals/publish`)은 이 이슈에 넣지 않는다.** 부분 성공 응답 형식과 실패 사유 배열이 따로 필요하고, 그 체계가 에러 코드와 다르다. 개별 발행이 게이트를 확정하면 일괄은 그것을 반복 적용하는 일이 되므로 이쪽이 먼저다
- **발행 이력과 되돌리기는 만들지 않는다.** 해제는 `published_at`을 지우는 것까지다
- **축제 등록·수정 API는 범위 밖이다.** 명세의 관리자 API 15개에 없고, 축제는 임포트로 들어온다
- 공개 API가 미발행 축제를 거르는지는 이 이슈에서 다루지 않는다. 발행 상태를 만드는 쪽이 먼저다
