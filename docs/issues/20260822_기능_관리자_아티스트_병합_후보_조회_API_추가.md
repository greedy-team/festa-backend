## 본문

## 📝 현재 문제점

- #36이 병합 실행을 만들었으나, **무엇을 병합할지는 관리자가 목록에서 직접 찾아야 한다.** 그런데 목록 검색은 표기가 다른 중복을 못 잡는다 — `잔나비`로 검색하면 `잔나비 (밴드)`는 걸리지만 `DAY 6`와 `Day6`는 서로를 영원히 못 찾는다. 검색은 부분 문자열 일치이고 중복의 실체는 표기 차이다
- **원문이 똑같은 중복은 애초에 만들어지지 않는다.** `ArtistService.validateName`이 `artistRepository.existsByName`과 `artistAliasRepository.existsByName`을 둘 다 걸어 이름·별칭 교차 중복을 막는다. 즉 실제로 남아 있는 중복은 **전부 표기 차이**이고, 그것만 골라내는 수단이 지금 하나도 없다
- 그래서 중복 발견이 사람이 목록을 눈으로 훑는 일에 의존한다. 아티스트가 늘어나면 그대로 무너진다
- 중복이 남으면 출연 이력이 쪼개진다 — 12회 나온 밴드가 9회와 3회로 갈려 보인다 (#36이 지적한 그대로이며, 병합할 대상을 못 찾으면 병합 API가 있어도 이 문제는 남는다)

## 🛠️ 해결 방안 / 제안 기능

- 관리자용 아티스트 병합 후보 조회 API를 만든다 — `GET /api/admin/artists/{id}/merge-candidates`
- `limit` 쿼리 파라미터로 후보 개수를 받는다 (1~20, 기본 5)
- 응답은 기준 아티스트(`source`)와 후보 목록(`candidates`)이며, 각 후보는 id·대표명·별칭·장르·출연 횟수와 함께 **유사도 점수(`similarity`)와 근거(`reasons`)** 를 담는다. 후보가 없으면 `candidates: []`

### 후보 판정은 두 층으로 나눈다

**후보를 만드는 규칙 — 이름 기반 둘.** 비교는 모두 **정규화 후**에 한다 (소문자화 + 공백·괄호·특수문자 제거). 원문 완전일치는 위에 적은 대로 서비스가 이미 막으므로, 정규화가 실제로 잡는 것은 표기 차이뿐이다.

- `ALIAS_MATCH` — 기준의 (이름 ∪ 별칭) 집합과 후보의 (이름 ∪ 별칭) 집합이 정규화 후 겹친다
- `NAME_SIMILAR` — 정규화 후 이름이 같거나, 한쪽이 다른 쪽의 부분 문자열이다 (`잔나비` ⊂ `잔나비밴드`)

**근거를 보강하는 규칙 — 하나.**

- `SAME_FESTIVAL` — 두 아티스트가 같은 축제에 출연한 이력이 있다

### 명세와 다르게 가는 자리 둘

- **`SAME_FESTIVAL`은 후보를 만들지 않는다. 이미 이름으로 걸린 후보에만 붙는다.** 명세 개요는 「이름 유사도, 별칭 일치, 같은 축제 출연 여부를 근거로」라고 셋을 나란히 적었으나, 같은 축제 출연을 후보 생성 규칙으로 쓰면 **한 축제에 선 아티스트 전원이 서로의 후보가 된다.** 펜타포트 라인업 60팀이면 후보 60개다. 명세의 예시 응답도 `reasons`에 `NAME_SIMILAR`와 `SAME_FESTIVAL`이 함께 들어 있어 「이름으로 걸린 뒤 축제로 보강」 쪽과 일치한다
- **`similarity`는 규칙별 고정 가중치의 합이다.** 명세는 `Double 0.0~1.0`이라고만 적고 계산 방법을 적지 않았다. 편집거리 기반 점수를 쓰려면 「몇 점부터 후보인가」를 정해야 하는데 **그 임계값을 정할 표본이 없다** — 중복을 대량으로 만드는 CSV 임포트(#37→#39→#41)가 아직 develop에 없어서, 지금 존재할 수 있는 중복은 관리자가 손으로 등록한 몇 건이 전부다. 그래서 임계값을 아예 두지 않는다: 위 규칙에 하나라도 걸리면 후보이고, `similarity`는 `ALIAS_MATCH` 0.6 / `NAME_SIMILAR` 0.3 / `SAME_FESTIVAL` 0.1의 합(1.0 상한)으로 **결정론적으로** 나온다. 추측한 숫자가 응답에 섞이지 않으며, 이 값은 정렬 키 역할만 한다

노션 API 명세는 #49에서 동결됐으므로 명세 쪽을 고치지 않는다. **이 두 자리의 계약 원본은 이 이슈와 구현 코드다.**

### 그 밖의 규칙

- 기준 아티스트 자신은 후보에서 제외한다
- 정렬은 `similarity` 내림차순, 동점이면 출연 횟수 내림차순
- 에러는 `limit`이 1~20을 벗어나면 `ARTIST_INVALID_LIMIT`(400, 신설), 없는 아티스트면 #32가 만든 `ARTIST_NOT_FOUND`(404)를 쓴다
- 권한 없음(403) 응답은 만들지 않는다. 관리자 권한을 나누지 않기로 했으므로 #32·#36과 같다
- 읽기 전용이다. 후보 산출은 제안일 뿐이고 병합 여부는 사람이 정한다 — 이 API는 아무것도 바꾸지 않는다

## ⚙️ 작업 내용

- 응답 형식 정의 — `source` 객체와 `candidates` 배열
- 근거 열거값 3종 추가 — `NAME_SIMILAR`, `ALIAS_MATCH`, `SAME_FESTIVAL`
- 이름·별칭 정규화 후보 조회 쿼리 추가
- 같은 축제 출연 여부 조회 추가 — **`LineupRepository`는 develop에 없다.** #36 브랜치가 만들고 있으므로 그쪽이 먼저 머지되면 재사용하고, 아니면 이 이슈에서 만든다
- 점수 합산·정렬·`limit` 적용
- `ARTIST_INVALID_LIMIT` 에러 코드 추가
- 후보 조회 서비스는 병합 실행 서비스와 분리한다. 이쪽은 읽기 전용이고 저쪽은 트랜잭션 안에서 지운다
- **검증은 데이터베이스에 실제 행을 넣고 한다.** 정규화 비교가 PostgreSQL 함수 위에 얹혀 있어 목으로는 확인되지 않는다. 최소한 다음은 실물로 본다 — 표기만 다른 아티스트가 후보로 잡히는지 / **같은 축제에만 함께 선 무관한 아티스트가 후보로 잡히지 _않는지_** / `limit` 경계 / 기준 아티스트 자기 제외

## ⚠️ 선행 조건 · 범위 밖

- **#36(PR #51)이 먼저 머지되는 편이 낫다.** 코드 의존은 없지만(이 API는 읽기 전용이고 병합 실행을 호출하지 않는다) 두 가지가 겹친다 — `ArtistErrorCode` 열거형 끝에 양쪽이 각각 코드를 추가해 텍스트 충돌이 나고, `LineupRepository`를 양쪽이 만들게 된다
- **편집거리·`pg_trgm` 유사도는 넣지 않는다.** 위에 적은 대로 임계값을 정할 표본이 없다. CSV 임포트가 develop에 들어가 실제 중복이 쌓인 뒤, 그 표본을 보고 후속 이슈에서 판단한다. 그때 갈아끼울 자리는 `similarity` 계산 한 곳이며 응답 형식은 바뀌지 않는다
- **`instagramUrl`이 같다는 신호는 근거에 넣지 않는다.** 표기가 달라도 같은 사람이라는 강한 증거지만, 명세의 `reasons` 열거값 3종을 늘려야 하고 프론트가 모르는 값을 받게 된다. 필요해지면 후속 이슈에서 계약 변경으로 처리한다
- **병합 전 미리보기는 여전히 만들지 않는다.** #36에서 정한 그대로다. 이 API도 겹침 가능성만 알리고 지워질 출연 이력 건수는 주지 않는다
- 후보를 눌러 바로 병합하는 화면 흐름은 프론트 몫이다. 이 이슈는 후보를 내주는 데까지다
