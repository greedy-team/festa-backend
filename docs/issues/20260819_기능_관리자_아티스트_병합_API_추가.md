## 본문

## 📝 현재 문제점

- 임포트는 크롤러가 준 이름을 그대로 아티스트로 만든다. `아이유` / `IU` / `아이유(IU)`처럼 같은 사람이 표기만 다른 채로 여러 건 생기는데 이것을 하나로 합칠 방법이 없다
- #32가 목록에 검색과 병합 검토 대기 필터를 넣어 **중복을 찾을 수는 있게 됐으나, 찾은 뒤에 할 수 있는 일이 없다.** 한쪽을 지우려 하면 출연 이력이 남아 있어 삭제가 거부된다
- 중복이 남으면 아티스트의 출연 이력이 쪼개진다. 12회 나온 밴드가 9회와 3회로 갈려 보인다
- 라인업이 아티스트를 참조하므로 중복을 지우려면 라인업을 먼저 옮겨야 하는데 그 이관 경로가 없다

## 🛠️ 해결 방안 / 제안 기능

- 관리자용 아티스트 병합 API를 만든다 — POST /admin/artists/merge
- 요청은 남길 아티스트 하나(`targetId`)와 흡수될 아티스트 목록(`sourceIds`, 1~10개), 별칭 보존 여부(`keepAliases`, 기본 참)를 받는다
- 흡수될 아티스트의 출연 이력을 남길 아티스트로 옮기고, 흡수된 아티스트를 삭제한다
- **이관 후 같은 축제·같은 일차에 같은 아티스트가 여러 순서를 잡으면 순서가 앞선 하나만 남기고 지운다.** 명세는 이 판정을 「같은 축제·일차·순서」로 적었으나 그 키로는 아무것도 잡히지 않는다 — 병합은 라인업의 아티스트 참조만 바꾸고 라인업의 유일성 제약은 `(축제, 일차, 순서)`에 걸려 있어 **아티스트를 바꿔도 제약이 깨지지 않는다.** 명세대로 구현하면 지운 건수가 영원히 0으로 나간다. 실제로 이상해지는 것은 한 무대에 같은 아티스트가 두 번 뜨는 것이고 그 판정 키는 `(축제, 일차, 아티스트)`다
- `keepAliases`가 참이면 흡수된 아티스트의 **이름과 그 아티스트가 갖고 있던 별칭을 모두** 남길 아티스트의 별칭으로 옮긴다. 거짓이면 흡수된 아티스트의 별칭은 함께 사라진다. 명세는 「흡수된 이름을 별칭으로 추가」 여부만 적고 기존 별칭 처리를 적지 않았다
- 흡수된 아티스트를 지우기 전에 별칭 행을 먼저 정리한다. 별칭이 아티스트를 참조하므로 남겨두면 삭제가 실패한다 (#32의 삭제와 같은 이유다)
- **병합 후 남은 아티스트의 병합 검토 대기 표시를 켠다.** 병합은 결과를 사전에 다 보여줄 수 없는 작업이라 사후 확인이 필요하다 — 지워질 출연 이력 건수를 누르기 전에 알 수 없고, 장르가 비어 있는 채로 남을 수 있다. 응답에도 이 값을 실어 화면이 「검토 대기열에 넣었습니다」를 띄울 수 있게 한다. 명세는 병합의 검토 대기 표시 처리를 적지 않았다
- **남을 아티스트의 장르·인스타그램 주소·이미지 주소는 건드리지 않는다.** 흡수되는 쪽에만 값이 있어도 옮기지 않는다. 병합은 출연 이력을 옮기는 작업이고 항목 값을 합치는 작업이 아니다. 흡수되는 쪽이 여럿일 때 어느 값을 쓸지가 요청 배열의 순서에 달리게 되는 것도 피한다. 빈 자리는 관리자가 수정 API로 채우며, 검토 대기 표시가 켜져 있어 목록에서 빈 칸이 눈에 띈다
- 응답은 남은 아티스트의 id와 대표명, 흡수한 아티스트 수, 옮긴 출연 이력 수, 중복으로 지운 출연 이력 수, 병합 후 별칭 목록, 검토 대기 표시를 담는다
- 전체를 한 트랜잭션으로 처리한다. 중간에 실패하면 아무것도 바뀌지 않아야 한다
- 남길 아티스트가 흡수 목록에 들어 있으면 오류다. 흡수 목록이 비었거나 10개를 넘으면 오류다. 없는 아티스트가 섞여 있으면 오류다 — 앞의 둘은 전용 에러 코드를 새로 만들고, 없는 아티스트는 #32가 만든 코드를 쓴다
- 흡수 목록에 같은 id가 여러 번 오면 하나로 보고 처리한다. 흡수한 아티스트 수는 실제로 지운 개수다
- **출연 이력이 있는 아티스트는 삭제하지 않는다는 #32의 방어를 병합은 타지 않는다.** 병합은 출연 이력이 있는 아티스트를 지우는 것이 목적이므로 그 검사를 재사용하면 항상 막힌다
- 시크릿 게스트로 아티스트가 비어 있는 라인업 행은 병합의 영향을 받지 않는다
- 권한 없음(403) 응답은 만들지 않는다. 관리자 권한을 나누지 않기로 했으므로 #32와 같다

## ⚙️ 작업 내용

- 병합 요청·응답 형식 정의
- 라인업 이관과 이관 후 중복 정리
- 별칭 이관과 흡수 대상 삭제
- 병합 검토 대기 표시 처리
- 병합 전용 에러 코드 추가
- 요청 값 검증 연결 — 자기 자신 병합, 흡수 목록 크기, 없는 아티스트, 흡수 목록 안의 중복 id
- **중복 정리는 데이터베이스에 실제 라인업 행을 넣고 검증한다.** 쿼리가 정말 그 행을 지우는지는 실물로만 확인된다 — 열거값 컨버터 작업에서 단위 테스트가 전부 초록인 채로 컨버터가 실제로는 적용되지 않았던 것과 같은 종류의 함정이다

## ⚠️ 선행 조건 · 범위 밖

- **#32가 먼저 머지되어야 한다.** 아티스트 서비스·저장소가 거기서 생기고, 병합 후 빈 항목을 채울 수정 API도 아직 컨트롤러에 붙지 않았다
- **병합 후보 조회(GET /admin/artists/{id}/merge-candidates)는 이 이슈에 넣지 않는다.** 명세가 유사도 점수와 근거 3종을 응답에 두면서 계산 방법을 적지 않았고, 임계값을 정할 표본이 아직 없다 — 중복을 만드는 CSV 임포트가 미구현이라 지금 있을 수 있는 중복은 관리자가 손으로 따로 등록한 몇 건이 전부다. 표본 없이 임계값을 정하면 추측이 된다. 병합 실행은 후보 조회가 없어도 목록 검색으로 중복을 찾아 쓸 수 있으므로 이쪽이 먼저다
- **병합 전 미리보기는 만들지 않는다.** 지워질 출연 이력 건수를 누르기 전에 보여줄 방법이 없고, 후보 조회 응답도 겹침 가능성만 알리고 건수를 주지 않는다. 정말 되돌릴 수 없는 것은 아티스트 삭제이고 그것은 확인 창이 이미 보여준다 — 중복으로 지워진 라인업 행은 관리자가 라인업 화면에서 다시 넣을 수 있다. 실제로 얼마나 지워지는지 보고 후속 이슈에서 판단한다
- 되돌리기와 백업 롤백은 만들지 않는다. 앞서 P1로 미뤄둔 것이 그대로 유효하다
- 별칭 이관이 별칭 유일성과 충돌하지 않는다고 보는 근거는 **#32가 아티스트 이름과 별칭의 교차 중복을 서비스에서 막는다는 것**이다. 그 검사가 온전하다는 가정 위에 서 있으므로 구현 중에 확인이 필요하다
- 명세와 다르게 가는 자리가 넷이다 — 중복 판정 키 / 응답에 검토 대기 표시 추가 / 병합이 검토 대기 표시를 켠다 / `keepAliases`가 거짓일 때 기존 별칭 처리. 노션 명세도 함께 고쳐야 한다
