## 작업 목적

Issue #182의 조회 병목을 개선했다. PR #184는 develop에 병합되었고, Repository/API 코드는 바꾸지 않고 Flyway 인덱스와 PostgreSQL 통합 테스트만 추가했다.

## 최종 추가 인덱스와 대상 쿼리

| 인덱스 | 대상 쿼리 |
| --- | --- |
| `idx_festival_host_start_id_unpublished ON festival(host_id, start_date, id) WHERE published_at IS NULL` | Host coverage의 미발행 LATERAL `LIMIT 1` |
| `idx_festival_host_start_id_published ON festival(host_id, start_date, id) INCLUDE (end_date) WHERE published_at IS NOT NULL` | Host coverage의 발행/진행 LATERAL `LIMIT 1` |
| `idx_lineup_artist_id ON lineup(artist_id)` | Artist별 published lineup 조회, lineup count, 완료 공연 count |

coverage는 발행 여부에 따라 predicate와 읽는 열이 달라 두 partial index로 나눴다. 각 경로의 불필요한 행을 제외하면서 발행/진행 경로는 `end_date`를 INCLUDE해 Index Only Scan을 사용할 수 있다.

`lineup(artist_id, festival_id)` 단일 covering index는 동일 fixture 실측에서 `lineup(artist_id)`와 성능 차이가 거의 없었고, 인덱스 크기만 2.70MB에서 9.05MB로 증가해 채택하지 않았다.

## #154 기준 성능 결과

동일 `festa_perf` fixture(PostgreSQL 17, warm-up 2회 후 5회 median)에서 다음 결과를 확인했다.

| 경로 | 이전 | 이후 | 개선 |
| --- | ---: | ---: | ---: |
| Coverage | 640.636ms | 2.155ms | 99.66% |
| Artist published lineup | 28.543ms | 0.188ms | 99.34% |
| lineup count | 26.189ms | 0.082ms | 99.69% |
| 완료 공연 count | 27.719ms | 0.160ms | 99.42% |

## 검증과 테스트

`QueryIndexesPostgresIntegrationTest`를 추가해 Flyway 적용 뒤 세 인덱스의 정의와 대상 SQL의 `EXPLAIN` plan을 검증했다. 미발행 coverage는 partial Index Scan, 발행/진행 coverage는 partial Index Only Scan, Artist별 lineup 경로는 `idx_lineup_artist_id` 사용을 확인한다.

PR #184의 PROJECT-SPRING-CI 빌드 검증, Test Results, JUnit Test Report는 모두 성공했고 `./gradlew clean build`도 통과했다.

## 후속 주의사항

#174의 `V20260914_0000__default_artist_needs_review_false.sql`은 #184의 `V20260915_0000__coverage_and_lineup_query_indexes.sql`보다 앞선 버전이다. #174를 병합할 때에는 migration 버전을 #184보다 뒤로 조정해야 Flyway 버전 순서 충돌을 피할 수 있다.
