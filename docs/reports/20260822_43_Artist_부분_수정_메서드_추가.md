### 📌 작업 개요

`Artist` 엔티티에 부분 수정 도메인 메서드를 추가했다.
관리자 `PATCH /admin/artists/{id}`는 미전송 필드를 기존 값으로 유지해야 하는데,
`develop`의 `Artist`에 그 메서드가 없어 PATCH 정책을 구현할 자리가 없던 상태였다.

### 🔍 현재 문제점

- 최신 `develop`의 `Artist`에는 부분 수정 메서드가 없었다
- 미병합 PR #40에는 3인자 `update(ArtistGenre, String, boolean)`가 있었는데,
  `boolean`이라 **미전송과 `false`를 구분할 수 없어** 최종 PATCH null 정책과 맞지 않았다

### ✅ 구현 내용

#### 부분 수정 메서드 추가

- **파일**: `src/main/java/com/greedy/festa/artist/entity/Artist.java`
- **변경 내용**: `update(String name, ArtistGenre genre, String instagramUrl, Boolean needsReview)` 추가.
  각 인자가 `null`이면 기존 값을 유지한다
- **이유**: 부분 수정 판단을 서비스가 아니라 엔티티 안에 두어, 호출부가 어느 필드를 건드릴지만 정하게 한다

핵심은 `needsReview`의 타입이다. 래퍼 `Boolean`으로 받아야 **미전송(`null`)과 명시적 `false`가 갈린다.**
원시 `boolean`이면 둘 다 `false`로 들어와 "검토 필요 해제"를 표현할 수 없다.

`instagramUrl`은 빈 문자열이 오면 `null`로 저장한다. 빈 문자열과 미설정이 DB에 섞이는 것을 막는다.

### 🧭 결정 기록 (ADR)

#### `needsReview`를 `Boolean`으로

- **문제**: PATCH에서 "안 보냈다"와 "false로 보냈다"를 구분해야 한다
- **선택**: 래퍼 타입 `Boolean`. `null`이면 유지, 값이 있으면 그대로 반영
- **대안**: 원시 `boolean` — 미전송이 `false`로 들어와 기존 `true`를 조용히 덮는다
- **트레이드오프**: 엔티티 필드는 원시 `boolean`(`@Column(nullable = false)`)이고 인자만 래퍼라
  타입이 한 곳에서 갈린다
- ⭐ **볼트 승격 권장** — 이후 모든 PATCH 계약이 따라야 하는 규칙이다

#### 다른 사람의 미병합 브랜치를 건드리지 않음

- **문제**: PR #40의 3인자 `update`와 이 메서드가 공존하게 된다
- **선택**: 이 이슈에서는 `develop`에만 4인자 메서드를 넣고, PR #40의 3인자 update 제거는 그쪽 작업으로 남긴다
- **대안**: PR #40 브랜치를 직접 수정 — 남의 미병합 브랜치를 임의로 고치면 그쪽 작업이 충돌로 막힌다
- **트레이드오프**: **머지 시점까지 의미가 다른 `update`가 둘 남는다.** 시그니처가 달라 컴파일은 되지만
  호출부만 봐서는 어느 규약인지 알 수 없다. 반영 순서를 문서로 남겨 대응했다

### 🧪 테스트 및 검증

  `needsReview=false`가 반영되는지

### 📌 참고사항

**구현된 시그니처가 이슈 본문과 다르다.** 이슈는 `(genre, imageUrl, instagramUrl, needsReview)` 4인자에
"`name`은 수정 대상에서 제외"라고 적었으나, 머지된 메서드는 `(name, genre, instagramUrl, needsReview)`다.

| 항목 | 이슈 명세 | 구현 |
| --- | --- | --- |
| `name` | 수정 대상 제외 | **수정 가능** |
| `genre` | 수정 가능 | 수정 가능 |
| `imageUrl` | 수정 가능 | **수정 불가** — 인자에 없음 |
| `instagramUrl` | 수정 가능 | 수정 가능 (빈 문자열 → `null`) |
| `needsReview` | 수정 가능 | 수정 가능 |

`Artist` 엔티티에 `imageUrl` 필드는 존재하지만 이 메서드로는 바꿀 수 없다.
`imageUrl`을 관리자 화면에서 수정할 수 있어야 한다면 별도 대응이 필요하다.
`name`은 `@Column(nullable = false, unique = true)`이므로 수정 경로가 열려 있다면
중복 이름 검증이 호출부에 있어야 한다.

- `otherNames` 및 `ArtistAlias` 갱신은 이 메서드 밖에서 처리한다
- 이 메서드가 `develop`에 들어간 뒤에도 PR #40에는 의미가 다른 `Artist.update`가 남아 있다.
  두 브랜치가 만나는 시점에 하나로 정리해야 한다
