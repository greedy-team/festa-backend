### 📌 작업 개요

`develop` 자동 배포가 무작위로 실패하던 것을 고쳤다. 최근 CD 8건 중 3건 실패 + 1건 취소.

**앱은 정상 기동 중인데 검증이 먼저 포기하고 있었다.** 헬스체크와 compose의 판정 예산이
실제 기동 시간보다 짧아, 곧 정상이 될 배포를 이전 이미지로 되돌리고 있었다.
고친 것은 앱도 인프라도 아니라 **「언제까지 기다릴지」** 뿐이다.

### 🔍 문제 분석

앱 코드 가설은 증거 셋이 각각 독립적으로 죽인다.

| 증거 | 내용 |
| --- | --- |
| 같은 코드가 5분 뒤 성공 | run `33054981856`(`5a0eb4f`)은 실패한 `d645b19`의 자손이라 `#41` 코드와 `V20260826_0000` 마이그레이션을 전부 포함하는데 정상 배포됐다 |
| 문서만 바뀐 커밋이 실패 | run `32939746023`(`192f2e6`) — `.md` 2개 187줄 추가가 변경의 전부다 |
| 롤백 이미지마저 죽음 | 그 실패에서 **15분 전 128초에 정상 기동했던 바로 그 이미지가 168초에도 못 떴다** |

실패한 run을 더 파는 것으로는 안 나왔다. **이웃 run과 비교**해야 드러나는 종류였다.

원인은 산수였다. 실측 기동은 **128초~190초 이상**을 오가는데 판정 예산이 그 범위 안에 있었다.

| 자리 | 계산 | 죽는 시각 |
| --- | --- | --- |
| `Dockerfile` `--start-period=30s --retries=12 --interval=10s` | 30 + 12×10 | **150초** |
| `PROJECT-SPRING-CD.yaml` `--wait-timeout 180` | — | **180초** |

두 실패 시각이 갈리는 이유까지 이 계산으로 맞는다. 포트가 아직 안 열려 curl이 즉시 거절당하면
검사 주기가 10초라 **~150초**에 죽고(실측 153.5초), 포트는 열렸는데 응답이 느려 `--timeout=3s`에
걸리면 주기가 13초가 되어 **~186초**에 죽는다(실측 187.3초).

기동이 느린 것 자체는 `VM.Standard.E2.1.Micro`(1 OCPU / 1GB RAM) 한 대에
postgres · JVM · caddy가 함께 올라간 구성 때문이다(#14).

**피해가 단순 실패가 아니었다.** compose가 포기해도 새 컨테이너는 죽지 않고 계속 뜨는 중이다.
즉 워크플로우가 **곧 정상이 될 배포를 굳이 되돌리고 있었다.** `#41`은 실제로 멀쩡했는데 롤백당했다.

### ✅ 구현 내용

#### 헬스체크 예산 재배분

- **파일**: `Dockerfile`
- **변경 내용**: `--start-period` `30s` → `240s`, `--retries` `12` → `3`,
  `--timeout` `3s` → `5s`
- **이유**: **start-period 안의 실패는 retries로 세지 않는다.** 두 값을 반대 방향으로 움직여
  기동에는 여유를 주고 기동 이후에는 더 빨리 죽은 것을 알아채게 했다

| | 기동 허용 | 기동 후 장애 감지 |
| --- | --- | --- |
| 전 | 150초 | 120초 |
| 후 | 240초 | **45초** |

`--timeout`을 5초로 올린 것은 기동 중 응답이 3초를 넘는 것이 실측됐기 때문이다.
이 값이 짧으면 살아 있는 앱을 죽은 것으로 센다.

변경 이유를 `Dockerfile`에 주석으로 남겼다 — 숫자만 보면 「왜 retries를 줄였나」가
거꾸로 읽히기 때문이다.

#### compose 대기 시간

- **파일**: `.github/workflows/PROJECT-SPRING-CD.yaml`
- **변경 내용**: `--wait-timeout` `180` → `300`, **3곳 모두**(신규 배포 181행,
  롤백 192행, 외부 헬스체크 실패 시 롤백 230행)
- **이유**: compose 예산이 헬스체크 예산보다 커야 한다. 작으면 **컨테이너가 아직 판정 중인데
  compose가 먼저 포기한다.** 롤백 경로 둘을 빠뜨리면 되돌리는 것마저 같은 이유로 실패한다

#### 실패 원인을 남기는 로그

- **파일**: `.github/workflows/PROJECT-SPRING-CD.yaml`
- **변경 내용**: 롤백 **직전에** 앱 컨테이너 로그 마지막 200줄을 `stderr`로 덤프
- **이유**: 지금까지는 `container app-1 is unhealthy` 한 줄만 찍고 롤백했다.
  **롤백하면 실패한 컨테이너가 사라져 원인이 영영 남지 않는다** — 진짜 기동 실패인지
  그냥 느린 것인지를 CI 로그만으로 구분할 방법이 구조적으로 없었다

`APP_IMAGE`를 다시 넘긴다. `compose.yaml`이 이 값을 필수로 선언해서 주지 않으면
`logs`가 그 자리에서 죽는다. `|| true`를 붙여 **로그 수집 실패가 롤백을 막지 않게** 했다.

### 🧭 결정 기록 (ADR)

#### 기동 시간을 줄이지 않고 판정 예산만 늘린다

- **문제**: 128초 기동 자체가 길다. JVM 힙 옵션·스왑·인스턴스 상향(A1)으로 줄일 수 있다
- **선택**: 이번엔 **「측정이 실제보다 성급하다」만** 고친다. 기동 시간은 별도 이슈로 남긴다
- **대안**: 함께 처리 — 원인이 둘 섞여 무엇이 효과를 냈는지 알 수 없게 되고,
  인스턴스 상향은 비용 결정이라 판단 주체가 다르다
- **트레이드오프**: 배포가 여전히 느리다. 다만 **느린 것과 실패하는 것은 다른 문제**이고
  지금 아픈 쪽은 후자였다

#### `retries`를 늘리지 않고 오히려 줄인다

- **문제**: 기동에 여유를 주려면 재시도를 늘리는 것이 직관적이다
- **선택**: `start-period`로 여유를 주고 `retries`는 12에서 3으로 **줄였다**
- **대안**: `retries`를 늘려 해결 — 기동 여유는 생기지만
  **기동이 끝난 뒤 실제로 죽은 앱을 알아채는 데도 그만큼 오래 걸린다.**
  두 상황에 같은 손잡이를 쓰면 한쪽을 좋게 할 때 다른 쪽이 나빠진다
- **트레이드오프**: 없음에 가깝다. 두 값이 서로 다른 구간을 맡으므로 양쪽이 함께 좋아졌다
- ⭐ **볼트 승격 권장** — start-period와 retries가 각각 무엇을 재는지가 이 수정의 핵심이고,
  다음에 헬스체크를 손댈 사람이 같은 자리에서 헤맬 수 있다

#### 실패 판정이 늦어지는 것을 받아들인다

- **문제**: 진짜로 기동하지 못하는 배포는 실패 판정까지 최대 5분이 걸린다(현재 3분)
- **선택**: 받아들인다
- **대안**: 예산을 조금만 올려 타협 — 실측 상한이 190초 이상인데 여유가 없으면
  같은 실패가 낮은 빈도로 계속 난다. **간헐적 실패는 매번 사람이 원인을 다시 의심하게 만든다**
- **트레이드오프**: `#14`가 받아들인 「헬스체크 실패 시 최대 3분 dev 서버 다운」이 5분이 된다.
  대신 멀쩡한 배포를 되돌리는 일이 없어진다

### 🧪 테스트 및 검증

배포 설정이라 단위 테스트 대상이 아니다. 대신 정적으로 확인했다.

- `docker build --check` 경고 0건
- 최소 이미지를 만들어 파싱된 값을 직접 확인 — `StartPeriod:240s`, `Retries:3`
- 워크플로우의 셸 블록 11개(원격 실행 히어독 3개 포함)를 `bash -n`으로 문법 검사
- PR CI 통과

### 📌 참고사항

**같은 자리에서 두 번 막혔다.** 실패 시 앱 로그를 한 줄도 남기지 않아 CI 로그만으로는
원인을 구분할 수 없는 문제는 `#47`(ADMIN_JWT_SECRET 미전달) 조사 때도 똑같이 걸렸다.
이번 조사가 길어진 이유도 그것이며, 로그 덤프를 이 PR에 함께 넣은 것은 그 반복을 끊기 위해서다.

**증상 문구가 과거 이슈와 글자 단위로 같았지만 원인은 전혀 달랐다.**
`#47`도 `container app-1 is unhealthy`로 실패했다. 그 원인(필수 환경변수 미배선)을
그대로 대입했으면 틀렸을 것이다. 증상만으로 과거 이슈를 재사용하면 안 되는 사례다.

- **기동 시간 자체를 줄이는 것은 이 이슈 범위 밖이다.** JVM 힙 옵션·스왑·인스턴스 상향(A1)은
  별도 이슈로 남아 있다
- 이 수정은 간헐적 실패의 빈도를 낮추는 것이 아니라 **원인을 제거한다.**
  예산이 실측 상한 위에 있으면 기동이 느려도 실패하지 않는다.
  다만 인스턴스가 더 느려져 240초를 넘기면 같은 증상이 돌아온다 — 그때는
  이 숫자를 또 올릴 것이 아니라 기동 시간 쪽 이슈를 열어야 한다
