# 관리자 쓰기 엔드포인트 HTTP 계약 고정 최종 구현 리포트

## 작업 개요

Issue #134와 PR #135는 관리자 쓰기 엔드포인트 13개가 어떤 테스트에서도 실제 HTTP 요청을 받지 않던 공백을 메웠다. 기존 세 컨트롤러 테스트(`FestivalAdminControllerTest`·`ArtistAdminControllerTest`·`LineupAdminControllerTest`)는 전부 `standaloneSetup`이고 실제 요청은 GET 목록·상세뿐이었다.

PR head `c5416d06e176169bca4d2c68d0529be7cf89ee5e`는 develop merge commit `23d0ac77c3fa4a18099513bb8ffb10b124c79dbd`(2026-09-06T03:28:37Z)로 병합됐다. 신규 파일 4개, `+926/-0`이며 `src/main`은 변경하지 않았다.

- 관련 Issue: [#134](https://github.com/greedy-team/festa-backend/issues/134)
- 관련 PR: [#135](https://github.com/greedy-team/festa-backend/pull/135)
- 보고서 파일: `docs/reports/20260906_134_관리자_쓰기_엔드포인트_HTTP_계약_고정_최종_구현_리포트.md`

## 문제 분석

서비스 단위 테스트는 이미 역직렬화가 끝난 DTO 객체를 손으로 만들어 넘기므로 컨트롤러 계층(매핑 애너테이션, 실제 JSON 바인딩, 응답 직렬화)을 구조적으로 볼 수 없다. `docs/reports/`에 계약 정정 리포트가 다섯 건(#95·#97·#102·#112·#114) 쌓여 있었고, 그 회귀들이 나온 층이 정확히 여기다.

인가 계약도 실제 컨트롤러에 걸려 있지 않았다. `SecurityConfigTest`의 401 검증 3건은 테스트 파일 안에 선언한 stub `@RestController`를 때리므로, 새 관리자 컨트롤러가 `/api/admin/**` 밖에 매핑돼도 `anyRequest().permitAll()`로 새어 나가 200이 나가는 상황을 이 테스트가 못 본다.

## 구현 내용

### FestivalAdminWriteContractTest — 10건

`@WebMvcTest(controllers = FestivalAdminController.class, excludeAutoConfiguration = OAuth2ClientWebSecurityAutoConfiguration.class)` + `@AutoConfigureMockMvc(addFilters = false)`로 인증 필터를 끄고 컨트롤러 슬라이스만 띄운다. 17필드 JSON 본문을 실제로 보내 등록·수정의 상태 코드·응답 키·`ArgumentCaptor` 바인딩을 확인하고, 선택 필드를 생략한 등록 요청이 null로 바인딩되는 경로도 별도로 검증한다. 삭제·일괄 발행·단건 발행·발행 취소까지 6종 엔드포인트를 덮는다.

### ArtistAdminWriteContractTest — 10건

등록·수정의 상태 코드·응답 9키·`ArgumentCaptor` 바인딩에 더해, `otherNames` 필드의 생략·명시적 null·빈 배열·값 있음 네 가지 입력을 구분하는 테스트 2건을 뒀다. 병합은 응답 7키 확인과 `keepAliases` 생략 시 기본값 true, 명시적 false 전달 두 갈래를 각각 검증한다. 삭제 포함 4종 엔드포인트를 덮는다.

### LineupAdminWriteContractTest — 8건

경로 변수 2개(`festivalId`, `lineupId`)를 받는 구조라 인자 순서가 바뀌어도 컴파일은 통과하는 지점을 `수정은_festivalId와_lineupId를_뒤바꾸지_않고_순서대로_넘긴다`, `삭제는_...festivalId와_lineupId를_순서대로_넘긴다`로 명시적으로 못박았다. `artistId` 생략·명시적 null이 시크릿 게스트로 바인딩되고 응답의 `artistId`/`artistName` 키가 null 값으로 유지되는 것도 확인한다. 등록·수정·삭제 3종을 덮는다.

### AdminPathPrefixTest — 3건

`@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제 애플리케이션 컨텍스트를 띄우되 DataSource·JPA·Flyway 자동 설정은 제외하고 Repository 8종을 `@MockitoBean`으로 대체했다. `List<RequestMappingHandlerMapping>`을 직접 주입받아 `com.greedy.festa` 패키지의 핸들러 메서드 전체에서 컨트롤러명·HTTP 메서드·경로를 추출하는 `애플리케이션_매핑()` 헬퍼를 두고, 세 방향(관리자 컨트롤러→`/api/admin/`, `/api/admin/`→관리자 컨트롤러, 전체→`/api/`)으로 위반 목록이 비었는지 확인한다. `SecurityConfigTest`의 stub 컨트롤러와 달리 실제 컨트롤러 빈을 대상으로 한다.

## 결정 기록 (ADR)

### 응답 필드명은 `containsOnlyKeys`로, `convertTo(Dto.class)`는 쓰지 않는다

- **문제**: 기존 방식인 `convertTo(Dto.class)`는 DTO 필드명을 바꾸면 직렬화·역직렬화가 함께 바뀌어 테스트가 계속 초록으로 통과한다. 이슈가 지적한 사각지대다.
- **선택**: `bodyJson().extractingPath("$").asMap().containsOnlyKeys(...)`로 실제 JSON 키 이름을 문자열로 고정한다.
- **대안**: `convertTo(Dto.class)` — DTO 개명에 응답 계약이 조용히 따라 바뀌어 회귀를 못 잡는다.
- **트레이드오프**: 키 목록을 테스트마다 나열해야 해 DTO에 필드가 추가될 때마다 테스트도 함께 고쳐야 한다. 그 수고가 곧 이 테스트의 존재 이유다.
- ⭐ **볼트 승격 권장** — 응답 계약 테스트 작성 시 재사용할 수 있는 원칙이다.

### 관리자 경로 전수 검사는 stub이 아니라 실제 컨텍스트를 쓴다

- **문제**: `SecurityConfigTest`는 테스트 파일 안의 stub `@RestController`를 때려 401 계약은 보지만, 새 컨트롤러가 `/api/admin/` 밖에 매핑되는 실수는 구조적으로 못 본다.
- **선택**: `@SpringBootTest`로 실제 컨텍스트를 띄우고 `RequestMappingHandlerMapping.getHandlerMethods()`에서 전체 매핑을 뽑아 접두어를 검사한다. DB 관련 자동 설정은 제외하고 Repository는 mock으로 대체해 Docker 없이 돌게 했다.
- **대안**: `SecurityConfigTest`에 컨트롤러를 하나씩 추가하는 방식 — 새 컨트롤러가 추가될 때마다 사람이 챙겨야 해서 이슈가 지적한 문제를 반복한다.
- **트레이드오프**: 클래스명에 "Admin"이 없는 관리자 컨트롤러가 생기면 이 검사도 놓친다(테스트 내 주석으로 명시).

- 파일별 테스트 개수(Festival 10 / Artist 10 / Lineup 8 / AdminPathPrefix 3, 합계 31): 각 파일의 `@Test` 개수를 세어 PR 본문 표와 일치함을 확인.
- 기존 `standaloneSetup` 테스트(`FestivalAdminControllerTest`·`ArtistAdminControllerTest`·`LineupAdminControllerTest`)와 `SecurityConfigTest`는 이번 PR로 손대지 않았다 — 마지막 커밋이 각각 #98·#122·#122이고 PR #135 diff에 포함되지 않음을 `git log`로 확인.
- PR 본문의 "리뷰어가 알아야 할 것" 5개 항목 중 코드로 확인 가능한 것은 실제로 그 상태였다: `GlobalExceptionHandler`에 `@ExceptionHandler(Exception.class)`가 존재, `FestivalCreateRequest`·`FestivalUpdateRequest`는 17개 컴포넌트가 완전히 동일한 record, `DELETE /{id}`는 204인데 `DELETE /{id}/publish`는 200, `POST /merge`는 200(다른 POST는 201), 세 컨트롤러 어디에도 `@Valid`가 없음. 405 대신 500이 나온다는 부분은 PR 작성자가 직접 요청을 쏴 확인했다고 기록했고 이번 검증에서 재현하지는 않았다.
- `AdminPathPrefixTest`의 "위반 0건" 자체는 로컬 재실행으로 확인했다(아래 테스트 절). 다만 PR 본문의 "매핑 39건·관리자 31건"이라는 총 개수는 테스트가 직접 출력하지 않는 값이라 별도로 재계산하지 않았고, 구현자 기록으로만 인용한다.
- PR 본문의 "프로덕션 코드를 망가뜨려 빨개지는 것을 확인했다"는 표 4건(201→200, 인자 순서 뒤바꿈, PATCH→PUT, 접두어 상수 변경)은 구현자가 로컬에서 수행하고 원복한 실험 기록이다. 이번 작업에서 동일 변형을 재현하지 않았다.

Issue 본문과 PR 본문은 이번 리포트 작성 과정에서 수정하지 않았다.

## 기존 결정과의 관계

이슈가 지적한 계약 정정 리포트 5건(#95·#97·#102·#112·#114)이 나온 층 — 컨트롤러가 실제로 받는 JSON과 응답 — 을 처음으로 구조적 테스트가 덮게 됐다. `AdminPathPrefixTest`의 "모든 경로는 `/api` 접두어 아래" 검사는 코드 내 주석이 명시하듯 기존 #60 결정(API 경로 `/api` 접두사)을 실제 컨텍스트에서 전수 검사로 재확인하는 것이며 새 정책을 도입하지 않았다.

관리자 인증, 접속 기록, WARN 로그 보관, import·publish 파이프라인 등 다른 운영 구현은 이번 diff에 포함되지 않는다.
