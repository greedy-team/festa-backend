# CORS 설정 추가 최종 구현 리포트

## 작업 개요

Issue #59와 PR #61을 통해 프론트엔드 로컬 개발 서버와 백엔드 개발 서버가 서로 다른 Origin에서 통신할 때 브라우저의 CORS 정책을 통과할 수 있도록 Spring Security CORS 설정을 추가했다. 이 리포트는 PR 초안이 아니라 `develop`에 병합된 merge commit `4bcb65a9f913d6d306915858390b285024182b32`의 실제 코드를 기준으로 작성했다.

## 구현 범위

- `SecurityConfig`의 `SecurityFilterChain`에 `cors` 설정을 활성화했다.
- `UrlBasedCorsConfigurationSource`에 `/**` 범위의 `CorsConfiguration`을 등록했다.
- 허용 Origin은 쉼표로 구분된 `app.cors.allowed-origins` 값을 사용한다.
  - 공통 설정: `${CORS_ALLOWED_ORIGINS:}`로 기본값은 빈 목록이다.
  - `development` 프로파일: `http://localhost:3000`을 허용한다.
- 허용 HTTP Method는 `GET`, `POST`, `PATCH`, `DELETE`다.
- 허용 Header는 `Authorization`, `Content-Type`이다.
- `allowCredentials`는 설정하지 않았으므로 기본값인 비허용 정책을 유지한다. 인증은 쿠키가 아니라 `Authorization` JWT 헤더를 사용한다.
- Spring Security의 CORS 필터가 preflight `OPTIONS`를 인증 처리보다 앞에서 다룬다. `OPTIONS`를 허용 Method 목록에 직접 추가한 구조는 아니다.
- 기존 인증 정책은 유지한다. `POST /api/admin/auth/login`은 공개되고, `/api/admin/**`는 인증이 필요하며, 나머지 요청은 허용된다.

## 주요 구현 내용

`http.cors(...)`가 Spring Security filter chain에 CORS 처리를 연결한다. 요청 Origin과 요청하려는 Method/Header가 등록된 정책에 맞으면 preflight 응답에 필요한 CORS 헤더가 추가되고 브라우저가 본 요청을 보낼 수 있다. 등록되지 않은 Origin에는 `Access-Control-Allow-Origin`이 제공되지 않아 브라우저가 교차 출처 응답 접근을 허용하지 않는다.

preflight `OPTIONS`는 브라우저가 본 요청 전에 서버의 Origin·Method·Header 허용 여부를 확인하는 요청이다. CORS 허용과 JWT 인증 허용은 별개의 문제다. preflight가 통과하더라도 실제 `/api/admin/**` 요청은 기존 `JwtAuthenticationFilter`와 `authenticated()` 정책을 그대로 적용받으므로 유효한 관리자 JWT가 없으면 401 응답을 받는다.

## API 경로 정합성

PR #61 작성 당시 Issue와 PR의 수동 확인 예시는 `/admin/hosts`였지만, 이후 PR #62가 병합된 최신 `develop`의 관리자 계약은 `/api/admin/**`다. 현재 `SecurityConfig`도 `POST /api/admin/auth/login`과 `/api/admin/**`를 기준으로 인증 정책을 적용한다. 따라서 현재 preflight 및 실제 호출 검증 경로는 `/api/admin/...`를 사용해야 하며, 과거 `/admin/**` 표기는 당시 기록으로만 본다.

## 리뷰 및 검토 내용

PR #61은 커밋 1개, 변경 파일 4개로 병합됐다. GitHub에 사람의 review, review thread, line comment는 없었다. PR 대화에는 GitHub Actions가 게시한 Test Results 댓글만 있으므로 별도의 “리뷰 반영” 내역은 없다.

PR 본문은 설정 변경이 단순하다는 이유로 CORS 동작 전용 자동 테스트를 추가하지 않았다고 명시했다. 최신 `develop`의 테스트 코드에서도 Origin, preflight `OPTIONS`, `Access-Control-Allow-Origin`을 검증하는 CORS 전용 테스트는 확인되지 않았다.

## 제한사항 및 후속 작업

- 운영 환경은 기본적으로 허용 Origin이 비어 있다. 실제 프론트엔드 배포 Origin이 정해지면 `CORS_ALLOWED_ORIGINS` 또는 운영 프로파일 설정으로 명시적으로 관리해야 한다.
- 로컬 프론트엔드가 `http://localhost:3000` 이외의 Origin을 사용하면 허용 목록을 조정해야 한다.
- HTTPS 프론트엔드에서 HTTP 개발 서버를 호출할 때 발생하는 mixed content 문제는 CORS로 해결되지 않으며 Issue #59 범위 밖이다.
- 허용/비허용 Origin, preflight 응답, 인증이 필요한 `/api/admin/**` 본 요청을 함께 검증하는 자동 회귀 테스트가 없다. 별도 Issue 번호는 확인되지 않았다.
