# 엔티티 공통 픽스처 최종 구현 리포트

## 작업 개요

Issue #130과 PR #131은 테스트마다 반복하던 엔티티 생성과 식별자 주입을 `support/fixture/`로 모았다. 테스트가 검증하는 값은 호출부에 남기고, 관심 없는 준비값만 공통 builder가 채운다.

최종 PR head `99c945d10741030dbcb90799a3312f5016ead054`와 develop merge commit `0f70b0e7f0b7077a7e2067cc3e09c05413049921`을 기준으로 확인했다. 구현 변경은 테스트 28파일과 새 픽스처 5파일, 총 33파일 `+348/-308`이다.

- 관련 Issue: [#130](https://github.com/greedy-team/festa-backend/issues/130)
- 관련 PR: [#131](https://github.com/greedy-team/festa-backend/pull/131)
- 보고서 파일: `docs/reports/20260905_130_엔티티_공통_픽스처_최종_구현_리포트.md`

## 문제 분석

엔티티 builder 체인에 테스트와 무관한 준비값까지 반복돼 무엇을 검증하는 테스트인지 읽기 어려웠다. 식별자 주입도 `ReflectionTestUtils.setField(entity, "id", id)` 24곳에 흩어져 필드명 변경에 대응할 지점이 많았다.

이슈의 생성 지점 103곳은 작성 당시 Host·Artist·Festival·Lineup 네 종류의 집계다. 최종 PR은 ArtistAlias 생성까지 함께 정리해 126곳을 치환했다. 이슈의 최초 규모와 최종 변경 규모를 같은 수치로 취급하지 않는다.

## 구현 내용

### 공통 builder 4종과 식별자 헬퍼

추가 위치는 `src/test/java/com/greedy/festa/support/fixture/`다. 기존 `PostgresTestSupport`·`LogCaptor`가 있는 테스트 지원 패키지 아래에 배치했다.

| 파일 / 메서드 | 채우는 값 |
| --- | --- |
| `HostFixture.host(name)` | 이름, `region="서울"` |
| `ArtistFixture.artist(name)` | 이름, `genre=BAND` |
| `ArtistFixture.alias(artist, name)` | 전달받은 아티스트와 별칭 이름 |
| `FestivalFixture.festival(name)` | 이름, `2026-05-20`부터 `2026-05-22`까지의 기간 |
| `FestivalFixture.publishable(name, host)` | 기본 축제 값, 주최, 위도 `37.5509`, 경도 `127.0748` |
| `LineupFixture.lineup(festival, artist)` | 전달받은 관계, `day=1`, `displayOrder=1` |
| `Fixtures.withId(entity, id)` | `ReflectionTestUtils`로 id 설정 후 동일 객체 반환 |

`festival(name)`은 host를 채우지 않아 주최 누락 사례를 그대로 만들 수 있다. `publishable`은 주최·좌표를 채우는 준비 헬퍼이며, 실제 발행이나 라인업 저장을 수행하지 않는다. 발행 조건 전체를 보장하는 검증기도 아니다.

### 기존 테스트의 관심값 유지

Artist·Festival·Host·Lineup 서비스와 리포지토리, 통합 검색, 임포트, commit 이후 로그 테스트의 생성 코드를 치환했다. 날짜 경계와 정렬을 검증하는 테스트는 `startDate`·`endDate`·`day`·`displayOrder`를 호출부에서 계속 지정한다. 시크릿 게스트는 `LineupFixture.lineup(festival, null)`로 명시한다.

일부 Artist 준비 객체는 기존 `genre=null`에서 `BAND`로 바뀌었다. 이는 테스트 데이터의 변경이며 운영 엔티티의 기본값 변경은 아니다. 해당 치환 지점의 단언과 사용 경로를 리뷰했고, 기존 검증 대상 장르값은 명시적 override로 유지했다.

### 리플렉션 사용 지점 축소

id 주입 24곳을 `Fixtures.withId`로 옮겼다. 제네릭 반환값으로 호출부의 객체 타입을 유지하지만, `"id"` 필드의 존재와 타입까지 컴파일 시 검증하지는 않는다. 리플렉션을 제거한 것이 아니라 변경 대응 지점을 한 곳으로 모은 것이다.

`ImportCommitServiceTest`의 이미 완료된 batch 설정은 `batch.commit(...)`, 발행 축제 설정은 `festival.publish(...)`를 사용한다. `ImportPreviewServiceTest`의 발행 축제도 `publish(...)`로 바꿨다. 상태를 나타내는 시각은 호출부에 유지했고 현재 메서드 구현에서 기존 리플렉션과 같은 상태가 만들어짐을 확인했다.

치환으로 사용하지 않게 된 별칭 헬퍼 1개와 import 9개도 제거했다.

## 결정 기록 (ADR)

### 완성된 객체 대신 builder를 반환한다

- **문제**: 완성 객체를 공통화하면 날짜 경계처럼 테스트의 핵심 입력까지 준비 코드 뒤에 숨기 쉽다.
- **선택**: 관심 없는 값만 채운 builder를 반환하고 테스트가 검증하는 값을 호출부에서 지정한다.
- **대안**: 모든 값이 채워진 객체 반환은 테스트별 조건을 바꾸기 어렵고, 각 테스트의 builder 중복 유지는 이번 문제를 해결하지 못한다.
- **트레이드오프**: 호출부에 일부 builder 체인은 남는다. 유효한 입력이나 경계값의 의미는 각 테스트가 책임진다.

### 이름과 관계는 호출자가 정한다

- **문제**: Host·Artist·ArtistAlias 이름에 UNIQUE 제약이 있어 공통 이름을 재사용하면 저장 테스트가 충돌한다. 관계를 숨기면 주최 누락·시크릿 게스트 사례도 표현하기 어렵다.
- **선택**: 이름을 인자로 받고 Lineup 관계를 명시한다. Festival은 최소 생성과 주최·좌표 준비를 나눈다.
- **대안**: 공통 이름이나 증가 카운터는 데이터 충돌 또는 호출 순서 의존성을 만든다.
- **트레이드오프**: 테스트는 관계 객체와 고유 이름을 직접 준비해야 한다.

### id 주입은 중앙화하고 상태 변경은 기존 메서드를 사용한다

- **문제**: Mockito 단위 테스트의 식별자를 실제 저장으로 얻으려면 DB와 테스트 구성을 함께 바꿔야 한다.
- **선택**: id 리플렉션은 단일 헬퍼에 유지하고, 발행·commit 상태는 이미 존재하는 메서드로 설정한다.
- **대안**: 모든 호출을 실제 DB 저장으로 전환하거나 테스트용 setter를 운영 엔티티에 추가하는 방식은 이번 테스트 준비 코드 정리 범위를 넘는다.
- **트레이드오프**: id 필드명 변경은 여전히 런타임 실패가 될 수 있다. 실제 영속화 검증은 기존 PostgreSQL 통합 테스트가 담당한다.
- ⭐ **볼트 승격 권장** — 리플렉션 유지 범위와 실제 저장 전환 비용을 감수한 선택이다.

## 리뷰 논의 및 반영 내용

머지 전 Issue #130, PR 전체 diff, 최신 develop, 관련 테스트 전략·엔티티 매핑 결정을 대조했다. Blocking·Non-blocking 코드 finding은 없었고, 리뷰에 따른 추가 코드 수정 없이 병합됐다. 이 리뷰 결과는 대화에서 전달됐으며 GitHub 리뷰 댓글로 게시한 결과와 혼동하지 않는다.

리뷰에서는 운영 코드 변경 부재, 단언·테스트 이름·개수·순서 유지, 날짜 경계와 시크릿 게스트 입력 유지, 상태 설정의 동등성을 확인했다. PR은 당시 최신 develop `88eb9d9` 위의 커밋 1개로 뒤처진 변경이나 중복 구현이 없었다.

이슈 초안의 `TestEntities`는 최종 코드에서 `Fixtures`가 됐다. 또한 기본값은 엄밀히 non-null 필드만으로 제한되지 않는다. Artist의 nullable genre와 `publishable`의 좌표도 준비값으로 제공한다. 최종 계약은 위 구현 표를 따른다.

### 기본값 변경 실험의 해석

PR 본문에는 기본값 7종을 바꾸고 650 runs가 통과했다는 구현자 기록이 있다. 해당 실험의 별도 실행 결과는 이번 최종 확인에서 독립 검증하지 못했으므로 위 최종 CI의 622 runs와 합치거나 같은 실행으로 표기하지 않는다.

이슈의 “기본값을 바꿔 테스트가 빨개지는지 확인”과 PR의 “변경해도 전부 통과”는 관찰 결과가 다르다. 관심 없는 준비값만 변경했다면 통과할 수 있으며, 통과만으로 단언을 삼켰거나 검증력을 유지했다고 단정할 수 없다. 이번 리뷰는 단언과 경계 입력이 실제로 남아 있는지도 함께 대조했다. 검증 대상 로직을 고장 내는 변이 검증까지 수행했다고 주장하지 않는다.

### 머지 후 배포

merge commit `0f70b0e`의 [PROJECT-SPRING-CD run 33971546749](https://github.com/greedy-team/festa-backend/actions/runs/33971546749)은 실패했다. Docker 이미지 내부의 `./gradlew bootJar --no-daemon`이 의존성을 받는 중 Maven Central에서 `429 Too Many Requests`를 반환했다.

실패 단계는 컨테이너 이미지 빌드이며, SSH 준비·서버 전송·재기동·HTTPS 확인은 건너뛰었다. 테스트 assertion 실패나 픽스처 컴파일 실패가 아니며, 이 실행을 배포 성공으로 취급하지 않는다.

## 기존 결정과의 관계

- 테스트 준비값과 검증 대상 입력을 분리해 “통과해도 실제로 아무것도 검증하지 않는 테스트”를 경계하는 기존 테스트 전략을 따른다.
- 실제 매핑·제약·commit/rollback은 기존 Testcontainers PostgreSQL 테스트에서 검증한다. 공통 픽스처가 DB 저장을 흉내 내거나 테스트 트랜잭션을 바꾸지 않는다.
- API·에러·스키마·엔티티 매핑 규칙은 변경하지 않았다. 프론트 타입이나 Swagger 계약 갱신도 필요하지 않다.
