### 📌 작업 개요

Issue #14의 OCI 인스턴스 배포 기반을 구성하고 PR #25 리뷰에서 확인된 배포 안전성 문제를 보완했다.
GitHub Actions 러너에서 이미지를 빌드한 뒤 OCI 서버로 전송하고, 같은 서버의 Docker Compose로
Spring Boot 애플리케이션과 PostgreSQL을 실행한다.

**보고서 파일**: `docs/reports/20260820_14_oci_인스턴스_cd_워크플로우_구성.md`

### 🎯 원래 요구사항과 구현 목표

저장소에 남은 Issue #14 작업 파일과 커밋 범위에서 확인되는 원래 목표는 다음과 같다.

- Java 21 Spring Boot 애플리케이션을 Docker 이미지로 빌드
- 애플리케이션과 PostgreSQL 17을 단일 Docker Compose 스택으로 실행
- `/actuator/health`를 컨테이너 및 배포 헬스체크에 사용
- GitHub Actions에서 이미지를 빌드하고 SSH/SCP로 OCI 인스턴스에 전달
- 서버에서는 애플리케이션을 빌드하지 않고 전달받은 이미지만 로드·기동

이후 DEC-0078~0080에 따라 배포 환경을 다음과 같이 구체화했다.

- `develop` → development GitHub Environment → OCI E2 → `linux/amd64`
- `main` → production GitHub Environment → OCI A1 → `linux/arm64`
- `develop` push마다 개발 서버 자동 배포 유지
- 런타임 헬스체크 실패 시 이전 정상 이미지로 자동 롤백

### ✅ 최종 구현 내용

#### Docker 이미지 빌드

- **파일**: `Dockerfile`, `.dockerignore`
- **변경 내용**: Java 21 JDK 빌더에서 `bootJar` 생성 후 Java 21 JRE 런타임 이미지로 복사하는
  멀티 스테이지 빌드 구성. 런타임은 비루트 `festa` 사용자로 실행
- **헬스체크**: 컨테이너 내부에서 `/actuator/health` 확인
- **이유**: OCI E2의 1GB 메모리에서 Gradle 빌드를 실행하지 않고 GitHub Actions 러너가 빌드를 담당

#### 단일 호스트 Compose 스택

- **파일**: `deploy/compose.yaml`
- **변경 내용**: `postgres:17-alpine`과 Spring Boot 앱을 한 스택으로 구성. PostgreSQL이 healthy가
  된 뒤 앱을 기동하며 DB 데이터는 named volume에 보존
- **DB 계약**: `POSTGRES_DB=festa`, 앱의 `DB_URL`은
  `jdbc:postgresql://postgres:5432/festa`
- **근거**: DEC-0079

#### Actuator 헬스 엔드포인트

- **파일**: `build.gradle.kts`, `src/main/resources/application.yml`,
  `src/test/java/com/greedy/festa/HealthEndpointSecurityTest.java`
- **변경 내용**: Actuator 의존성 추가, health 엔드포인트만 노출하고 상세 정보는 숨김.
  인증 없이 `/actuator/health`가 `200`과 `UP`을 반환하는 테스트 추가
- **이유**: Docker와 CD 워크플로우가 애플리케이션 정상 기동 여부를 판정할 공통 엔드포인트 필요

#### 개발·운영 배포 분기

- **파일**: `.github/workflows/PROJECT-SPRING-CD.yaml`
- **변경 내용**: `develop`과 `main` push 및 수동 실행 지원. 선택된 GitHub Environment를 기준으로
  플랫폼 결정
- **매핑**: development는 `linux/amd64`, production은 `linux/arm64`
- **특이사항**: 수동 실행을 `main`에서 시작하더라도 선택한 `environment`가 development면 amd64를 사용
- **근거**: DEC-0078, DEC-0080

#### 이미지 전달과 원격 기동

- Buildx로 대상 플랫폼 이미지를 빌드해 tar로 내보낸 뒤 gzip 압축
- SSH/SCP로 이미지, `app.env`, Compose 파일을 OCI 배포 경로에 전송
- 원격에서 `docker load` 후 `docker compose up -d --wait --wait-timeout 180` 실행
- 서버 내부와 GitHub Actions 러너 양쪽에서 `/actuator/health` 확인
- 원격 배포 스크립트의 `EXIT` trap으로 성공·실패 여부와 관계없이 전송된 tarball 정리

#### Secret과 연결 정보 검증

- `DB_URL`이 `jdbc:postgresql://postgres:5432/festa`와 정확히 일치하지 않으면 배포 중단
- 런타임 `ssh-keyscan`을 제거하고, 사전에 검증해 GitHub Secret으로 등록한 `OCI_HOST_KEY`를
  `known_hosts`로 사용
- `app.env` 파일 권한은 생성 시 `umask 077`, 서버에서 `chmod 600` 적용
- env-file 값은 single quote로 감싸 `$`, `#`, 공백, `${...}`가 Compose에서 보간·주석·공백
  처리되지 않게 함. 값 안의 single quote는 `\'`로 이스케이프
- Secret 실제 값은 워크플로우 로그에 출력하지 않음

#### 자동 롤백과 이미지 정리

- 새 배포 전 현재 실행 컨테이너의 이미지 태그를 최초 롤백 기준으로 저장
- 마지막 성공 이미지를 `.last-successful-image`, 진행 중 이미지를 `.deployment-in-progress`에 기록
- Compose 대기·서버 내부 헬스체크 또는 외부 헬스체크 실패 시 직전 정상 이미지로 재기동
- 외부 헬스체크까지 성공한 뒤에만 새 이미지를 정상 이미지로 확정
- 성공 후 `festa-backend:*` 중 현재 정상 이미지와 직전 정상 이미지만 보존하고 오래된 태그 삭제
- 정리 대상 판정에서 롤백용 직전 정상 이미지를 명시적으로 제외

자동 롤백은 애플리케이션 Docker 이미지에 한정된다. 새 이미지 기동 과정에서 Flyway 등으로 이미 적용된
DB 스키마는 자동으로 롤백하지 않으며, 스키마 롤백이 필요한 경우 수동으로 대응해야 한다.

### 🔍 PR #25 리뷰 반영

| 리뷰 내용 | 판정 및 반영 |
| --- | --- |
| 수동 실행에서 environment와 platform이 어긋날 수 있음 | environment를 먼저 결정한 뒤 development→amd64, production→arm64로 변환하도록 수정 |
| 런타임 `ssh-keyscan`으로 known_hosts 생성 | 제거. 미리 검증한 `OCI_HOST_KEY` Secret 사용 및 누락 검증 추가 |
| 새 배포 실패 시 이전 정상 이미지로 자동 롤백 필요 | 마지막 성공 이미지와 진행 상태를 서버 파일에 기록. 로컬·외부 헬스체크 실패 시 이전 이미지로 복구 |
| DB명 오타가 DB_URL 검증을 통과 | Compose의 `POSTGRES_DB=festa`와 정확히 일치하는 URL만 허용 |
| 오래된 Docker 이미지 정리 | 성공 확정 후 현재·직전 정상 이미지 두 개를 제외한 `festa-backend:*` 삭제 |
| app.env의 `$`, `#`, 공백 등 dotenv 특수문자 처리 | single-quoted literal 형식과 single quote escaping 적용 |
| 전송된 이미지 압축 파일 잔존 | 원격 스크립트에 `EXIT` trap 적용 |
| 관리자 API 무인증 공개 | 이번 이슈에서 정책을 새로 정하거나 수정하지 않음. 관리자 인증 작업 범위로 유지 |
| branch protection·required status check | 저장소 설정 영역이므로 이번 코드 변경에 포함하지 않음 |

### 🧭 결정 기록 (ADR)

#### 개발·운영 서버와 플랫폼을 Environment 기준으로 매핑

- **결정**: development/E2는 amd64, production/A1은 arm64
- **근거**: DEC-0078
- **결과**: push와 수동 실행이 같은 Environment→플랫폼 규칙을 사용

#### 빌드는 러너에서 수행하고 앱과 DB는 한 서버에 배치

- **결정**: GitHub Actions에서 이미지를 완성하고 OCI는 이미지 로드와 Compose 실행만 담당
- **근거**: DEC-0079
- **결과**: E2 메모리 제약과 무관하게 서버 빌드 없이 배포 가능

#### 자동 배포 빈도를 낮추지 않고 롤백을 추가

- **결정**: `develop` push 자동 배포를 유지하고 런타임 실패 위험은 자동 롤백으로 처리
- **근거**: DEC-0080
- **결과**: 개발 서버는 `develop` 최신 상태를 유지하며 실패 시 직전 정상 이미지로 복구

새로운 제품·인프라 정책 결정은 추가하지 않았다. 리뷰 반영은 위 활성 결정의 미구현 부분과
배포 안전성 보완이다.

  - 수동 production → `linux/arm64`
  - `develop` push → `linux/amd64`
  - `main` push → `linux/arm64`
- `ssh-keyscan` 제거 및 `OCI_HOST_KEY` 사용 검증 통과
- DB URL 와일드카드 제거 및 정확 일치 검증 통과
- 로컬·외부 헬스체크 롤백 경로 정적 검증 통과
- 현재·직전 정상 이미지 보존과 오래된 이미지 삭제 대상 시뮬레이션 통과
- tarball `EXIT` trap 성공·실패 경로 검증 통과
- `$`, `#`, 공백, `${...}`, `=`, 따옴표를 포함한 가짜 값으로 env-file 인코딩 검증 통과
- `git diff --check` 통과

실제 Secret 값은 검증 출력에 사용하지 않았으며 OCI 인스턴스에 대한 실제 배포 실행은 이 검증 범위에
포함하지 않았다.

### 📌 실제 배포 전 남은 확인사항

- development와 production GitHub Environment 각각에서 `DEPLOY_ENABLED`, OCI 접속 정보,
  DB·애플리케이션 Secret이 설정되어 있는지 확인
- 등록된 `OCI_HOST_KEY`가 실제 대상 서버의 현재 host key 및 SSH 포트 표기와 일치하는지 확인
- development의 OCI_HOST가 E2 amd64 서버를, production의 OCI_HOST가 A1 arm64 서버를 가리키는지 확인
- DEC-0078 작성 당시 A1은 미확보 상태였으므로 production 실제 인스턴스 확보 여부 확인
- OCI 사용자에게 배포 경로 생성·파일 쓰기, Docker 실행 권한이 있는지 확인
- 서버 Docker Compose가 워크플로우에서 사용하는 `--wait`와 `--wait-timeout`을 지원하는지 확인
- OCI 네트워크·방화벽에서 외부 헬스체크용 8080 접근이 허용되는지 확인
- 첫 실제 배포에서 기존 실행 컨테이너가 있으면 `.last-successful-image`가 현재 이미지로 초기화되는지,
  없으면 첫 성공 배포 뒤 정상 이미지 기록이 생성되는지 확인
- 의도적으로 실패하는 테스트 이미지를 사용하기 전, 직전 정상 이미지가 서버에 남아 있고 해당 태그로
  Compose 재기동이 가능한지 확인
- 성공 배포 후 현재·직전 이미지 두 개만 남고 롤백 대상 이미지가 삭제되지 않았는지 확인
- 배포 성공과 실패 양쪽에서 배포 경로의 `festa-backend.tar.gz`가 제거되는지 확인

관리자 인증 정책과 branch protection·required status check 설정은 이 리포트의 배포 전 확인사항에서
새로 결정하지 않는다.
