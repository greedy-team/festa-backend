# 관리자 아티스트 병합 후보 조회 API 최종 구현 리포트

## 작업 개요

Issue #54와 PR #63을 통해 관리자가 기준 아티스트와 표기가 유사한 중복 후보를 조회하는 읽기 전용 API를 구현했다. 기존 병합 API는 병합 대상을 알고 있어야 사용할 수 있었으므로, 이름·별칭 표기 차이와 축제 출연 이력을 근거로 후보를 제시하는 기능을 추가했다.

이 리포트는 PR 초안이 아니라 최신 `develop`의 merge commit `ee23bfec6bd4ee4f2f2675d96c5c2693e8059c36`에 반영된 코드와 최종 review thread를 기준으로 작성했다.

- `GET /api/admin/artists/{id}/merge-candidates` 추가

- 서비스 단위 테스트 14개 추가

## API 계약

### 요청

`GET /api/admin/artists/{id}/merge-candidates?limit=5`

- 관리자 JWT 인증이 필요하다. 최신 `SecurityConfig`의 `/api/admin/**` 인증 규칙을 그대로 적용한다.
- `limit` 기본값은 5다.
- `limit` 허용 범위는 1~20이다.
- 범위를 벗어나면 `ARTIST_INVALID_LIMIT` 400을 반환한다.
- 기준 아티스트가 없으면 `ARTIST_NOT_FOUND` 404를 반환한다.

### 응답

응답은 기준 아티스트 `source`와 후보 배열 `candidates`로 구성된다. 각 아티스트에는 ID, 대표명, 별칭, 장르, 출연 횟수가 포함되고, 후보에는 `similarity`와 `reasons`가 추가된다. 후보가 없으면 `candidates: []`를 반환한다.

후보 조회는 데이터를 변경하지 않으며 실제 병합 여부는 관리자가 별도의 병합 API로 결정한다.

## 후보 생성 및 정규화

이름과 별칭은 Unicode 문자·숫자만 남기고 `Locale.ROOT` 기준 소문자로 변환한다. 공백, 괄호, 특수문자와 대소문자 차이는 비교에서 제거된다.

후보 생성 규칙은 다음과 같다.

- `NAME_SIMILAR`
  - 정규화한 대표명이 완전히 같다.
  - 또는 짧은 쪽이 3자 이상이고 한쪽 대표명이 다른 쪽 대표명의 부분 문자열이다.
- `ALIAS_MATCH`
  - 기준 별칭과 후보 대표명, 기준 대표명과 후보 별칭 또는 양쪽 별칭이 정규화 후 일치한다.
- 정규화 결과가 빈 문자열인 이름·별칭은 매칭에 사용하지 않는다.
- 기준 아티스트 자신은 repository 조회 단계에서 제외한다.

`SAME_FESTIVAL`은 단독으로 후보를 생성하지 않는다. 이름 또는 별칭 규칙으로 이미 생성된 후보에만 근거와 점수 보너스를 추가한다. 같은 축제 라인업 전체가 서로 후보가 되는 과도한 결과를 피하기 위한 최종 결정이다.

## similarity와 정렬

최종 구현의 `similarity`는 편집거리 기반 연속 점수가 아니라 후보 근거의 강도를 나타내는 고정 rule score다.

- 대표명 exact 또는 alias exact: 0.9
- 대표명 partial: 0.5
- 같은 축제 출연: +0.1
- 상한: 1.0

여러 별칭이나 같은 축제 출연이 여러 건이어도 보너스는 후보당 한 번만 더한다. `reasons`도 각 열거값을 조건별로 한 번만 추가하므로 중복되지 않는다.

정렬 순서는 다음과 같다.

1. `similarity` 내림차순
2. 과거 출연 횟수 내림차순
3. `artistId` 오름차순
4. 정렬 후 `limit` 적용

마지막 ID tie-break는 코드 리뷰에서 추가됐다. 점수와 출연 횟수가 모두 같은 후보가 DB 반환 순서에 따라 달라지고 `limit` 경계의 결과가 바뀌는 문제를 방지한다.

## Repository와 조회 구조

후보 매칭은 의도적으로 Java에서 수행한다. 한 요청에서 다음 데이터를 집합 단위로 조회한다.

- 기준 아티스트 1건
- 기준 아티스트를 제외한 전체 아티스트
- 전체 별칭
- 아티스트별 출연 횟수 집계
- 기준 아티스트와 같은 축제에 출연한 아티스트 ID

후보마다 추가 query를 실행하지 않으므로 Artist 수에 비례하는 N+1은 없다. 다만 전체 Artist와 Alias를 메모리에 적재하므로 데이터 규모가 커질 때는 정규화 키 컬럼과 index 또는 DB 검색 방식으로 전환할 수 있다.

출연 횟수는 발행됐고 종료일이 현재보다 이전인 Festival의 Lineup만 센다. 같은 축제 여부는 Festival 단위로 `DISTINCT` 후보 ID를 조회하므로 여러 day에 함께 출연해도 점수가 중복 가산되지 않는다.

## 최신 develop 통합

PR 작성 뒤 develop에 `/api` prefix, Artist CRUD/merge, 관리자 인증과 Swagger 변경이 들어와 `ArtistAdminController`에서 충돌이 발생했다. 최종 merge commit `817a3bf6`에서 develop 버전을 기준으로 충돌을 해결하고 병합 후보 endpoint를 다시 결합했다.

최종 Controller는 다음을 모두 보존한다.

- `/api/admin/artists` 기반 Artist CRUD
- 기존 Artist 병합 endpoint
- 신규 `/{id}/merge-candidates`
- Controller의 `@Tag`, Bearer 인증 요구사항과 각 endpoint의 Swagger 명세

PR 최초 설명에서는 Swagger annotation을 제외했지만, 최신 develop에서 해당 Controller의 다른 endpoint 모두에 명세가 추가된 뒤에는 신규 endpoint에도 `@Operation`과 200/400/404 응답 명세를 추가하는 것으로 최종 결정이 바뀌었다.

- 반영: commit `8c6b02717b62d40a3c1ce6f46897a6ce6a9288fa`에서 `artistId` 오름차순을 마지막 comparator로 추가했다.
- 검증: 점수와 출연 횟수가 같은 후보가 ID 오름차순으로 반환되는 테스트를 추가했다.

### 최신 develop 충돌과 API 계약

- 지적: 최신 develop과 `ArtistAdminController` 충돌이 있고 `/api` prefix, 기존 endpoint와 Swagger 계약을 보존해야 했다.
- 반영: merge commit `817a3bf60b5dcc1c3836ddacafa2e554a9ec3a87`에서 develop Controller를 기준으로 신규 endpoint를 다시 적용했다.

## 제한사항 및 후속 작업

- 실제 HTTP mapping, 기본 `limit`, JSON shape, 오류 응답과 인증을 이 endpoint 전용 MockMvc 테스트로 직접 검증하지는 않는다. 현재 Controller 연결은 compile/context와 전체 CI로 검증됐다.
- 후보 로직은 전체 Artist와 Alias를 메모리에 올리는 MVP 구조다. 데이터 증가로 응답 시간이 문제가 될 때 정규화 키 저장과 index 기반 DB 검색을 검토한다.
- 편집거리와 `pg_trgm`은 실제 중복 표본과 임계값 근거가 마련되기 전까지 적용하지 않는다.
- `instagramUrl` 동일 여부는 현재 `reasons` 계약에 포함하지 않는다.
- API는 병합 후보만 제시하며 병합 미리보기나 자동 병합을 수행하지 않는다.
- `similarity`는 일반적인 문자열 유사도 값이 아니라 고정 rule score이므로 소비자는 절대적 확률로 해석하면 안 된다.
