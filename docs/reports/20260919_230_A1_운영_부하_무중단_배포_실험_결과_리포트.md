# A1 운영 부하 · 무중단 배포 실험 결과 리포트

## 측정 목적

출시 전 A1 운영 서버에 대해 두 가지를 확인했다.

1. **부하가 올라갈 때 서버가 어떻게 반응하는가** — 그리고 자체 호스팅 관측 스택이 그것을 실제로 보여주는가
2. **부하 중 blue/green 배포가 정말 무중단인가** — 지금까지 한 번도 부하 아래에서 검증된 적이 없었다

측정 대상은 **읽기 전용 공개 API만**이며, 쓰기·관리자 경로에는 요청을 보내지 않았다.

- 전 단계에서 **HTTP 오류 0%**, **checks 100%**, **threshold 실패 0건**이었다.
- `DB 커넥션`은 전 구간 12로 고정이었다 (HikariCP 10 + 익스포터). 부하와 무관하게 움직이지 않았다.
- `메모리 가용`은 전 구간 9.5~9.75 GiB에서 사실상 변동이 없었다. **메모리는 부하에 반응하지 않았다.**
- 1·5·10 RPS 단계의 호스트 지표는 Grafana 캡처 시간창 밖이라 이 표에 옮기지 못했다. Prometheus에는 남아 있어 회수 가능하다.

### 발견 ① 응답시간의 대부분은 네트워크다

| 구간 | 값 |
| --- | ---: |
| 클라이언트 p50 (150 RPS) | 69.8ms |
| 서버 내부 평균 (Grafana) | ~2.5ms |
| **차이 = 네트워크 + TLS + Caddy** | **약 67ms** |

p95는 10 RPS 이후 **부하와 무관하게 약 100ms에 고정**되어 있다(103.3 → 103.7 → 98.3 → 100.7 → 99.6). 서버가 15배 더 많은 요청을 받는 동안 클라이언트 지연은 움직이지 않았다.

즉 **사용자 체감 응답시간의 대부분은 서버가 아니라 왕복 네트워크와 TLS**다. 서버 코드 최적화로 줄일 수 있는 여지가 크지 않다는 뜻이기도 하고, 앞으로 무릎을 찾을 때 **클라이언트 지표로는 판정할 수 없다**는 뜻이기도 하다.

### 발견 ② 부하로는 포화에 닿지 못했다

150 RPS에서 CPU 35.5%, 5xx 0%, pending 0이었다. 오히려 **평균 응답시간이 9ms → 2.5ms로 떨어졌다** — JIT 예열 효과가 부하 증가분보다 컸다. 무릎은 나타나지 않았다.

다만 **한계 기울기는 이미 휘기 시작했다.**

| 구간 | 한계 기울기 |
| --- | ---: |
| 50 → 100 RPS | 0.196 %p/RPS |
| 100 → 150 RPS | **0.226 %p/RPS** |

요청 하나를 더 처리하는 비용이 15% 늘었다. 포화에 접근할 때 나타나는 신호이므로, **평균 기울기로 선형 외삽하면 실제보다 낙관적인 값이 나온다.** 이 리포트는 수용 한계 수치를 제시하지 않는다 (아래 「측정하지 않은 것」 참조).

### 발견 ③ 병목은 CPU이며 DB가 아니다

150 RPS에서도 HikariCP는 **풀 10개 중 최대 2개**만 사용했고 `pending`은 0을 유지했다. DB 트랜잭션은 RPS와 1:1로 따라갔고 (150 RPS에서 150 commit/s) **rollback은 0**이었다. 요청 1건이 트랜잭션 1건이다.

호스트 CPU만 부하에 비례해 올라갔다. **먼저 포화되는 자원은 2코어 CPU다.**

## 무중단 배포 실험

50 RPS 부하를 5분간 유지하는 동안, 사람이 별도로 `PROJECT-SPRING-CD`를 `production`으로 실행했다.

1 RPS      :  08:55 - 08:58
5 RPS      :  08:59 - 09:02
10 RPS     :  09:05 - 09:08
25 RPS     :  09:08 - 09:11   CPU 11.4%
50 RPS     :  09:12 - 09:15   CPU 14.4%
100 RPS    :  09:15 - 09:18   CPU 24.2%
150 RPS    :  09:19 - 09:22   CPU 35.5%   <- 최고 부하, 무릎 미도달
Recovery   :  09:24 - 09:26   CPU 약 2% 복귀

배포 실험   :  09:26:43        50 RPS 부하 시작
             09:27:52        app-green JVM 기동
             09:28:06        app-green 준비 완료 (기동 14.1s)
             09:28:30        Caddy 전환 · CPU 62% 피크 · 최대 응답 1.4s

             09:31:43        부하 종료 (5m00.1s)

### 결과: 실패 요청 0건

| 지표 | 값 |
| --- | ---: |
| 완료 iteration | **14,991** |
| 중단된 iteration | **0** |
| `httpErrorRate` | **0** |
| `checksRate` | **1.0** |
| `failedThresholds` | **없음** |

엔드포인트 7종 모두 오류 0건·체크 실패 0건이었다. **Caddy 레벨의 502도 없었다** — Grafana의 상태코드 패널은 앱에 도달한 요청만 보므로, 전환 순간의 무중단 여부는 k6 클라이언트 지표로만 확정할 수 있고 그 값이 0이다.

### 배포의 비용

| 항목 | 평상시 (50 RPS) | 배포 중 | 차이 |
| --- | ---: | ---: | ---: |
| 호스트 CPU | 14.4% | **약 62% 피크** | **+47%p** |
| Load 1m | 0.17 | 2.33 | — |
| 메모리 가용 | 9.75 GiB | 9.25 GiB | **−500 MiB** (JVM 2개) |
| 서버 내부 평균 응답 | ~5ms | ~13ms (약 1분간) | +8ms |
| 최대 응답시간 | ~10ms | **약 1.4s** | 콜드 스타트 |
| DB 커넥션 | 12 | 약 21 (순간) | 풀 2개 공존 |
| **5xx** | **0%** | **0%** | — |
| **HikariCP pending** | **0** | **0** | — |

**콜드 스타트 요청은 p99에도 잡히지 않았다.** p99가 119.2ms인데 이는 느린 순 150번째 요청이 119ms였다는 뜻이므로, 1.4초짜리 요청은 **150건 미만**이다. 사용자 관점에서 배포 비용은 상위 1% 밖에 있다.

한 가지 단서: k6가 `preAllocatedVUs` 50을 넘겨 **VU를 60개까지 늘렸다**. 전환 순간 동시성이 튀었다는 뜻으로, 클라이언트 쪽에도 콜드 스타트가 기록된 셈이다.

### 대시보드 판독 시 주의 두 가지

**① 최대 응답시간의 1.4초 「평탄부」는 2분간 느렸다는 뜻이 아니다.** Micrometer의 `http_server_requests_seconds_max`는 2분 슬라이딩 윈도우(`distributionStatisticExpiry` 기본 PT2M)라 **한 건**이 2분짜리 평평한 지붕을 만든다. 실제 영향은 평균 쪽(5ms → 13ms, 약 1분)에서 봐야 한다.

**② 전환 순간 RPS 그래프의 움푹한 자국은 트래픽 누락이 아니다.** blue 시계열이 끝나고 green 시계열이 시작될 때 `rate()`가 이력 없는 새 시리즈에서 잠깐 낮게 나온 것이다. k6는 그 구간에도 초당 50건을 끊김 없이 보냈다.

## 측정하지 않은 것

**수용 한계(무릎)는 측정하지 않았다.** 최고 단계 150 RPS에서 CPU 35.5%로 여유가 컸고, 도구의 허용 레이트 상한이 150이었다.

따라서 이 리포트는 **「최대 N RPS까지 수용 가능」이라는 문장을 제공하지 않는다.** 기울기가 이미 휘고 있어 외삽값도 신뢰할 수 없다. 발표·보고에는 아래 형태로만 인용할 수 있다.

> **150 RPS까지 측정했고, 그 지점에서 호스트 CPU 35.5%로 포화에 도달하지 않았다. 전 구간 오류 0%.**

수용 한계를 실측하려면 상한을 올린 뒤 추가 측정이 필요하다 (#228).

## 부하 도구에서 발견한 결함

**① `host_detail`이 한 번도 호출되지 않았다.**

`mixed` 시나리오의 가중치 합이 정확히 100%인데 `host_detail` 몫이 0이다.

| 엔드포인트 | 요청 수 | 비중 |
| --- | ---: | ---: |
| `search` | 2,998 | 20.0% |
| `festival_list` | 2,699 | 18.0% |
| `artist_list` | 2,698 | 18.0% |
| `festival_upcoming` | 1,799 | 12.0% |
| `festival_detail` | 1,799 | 12.0% |
| `festival_recent` | 1,499 | 10.0% |
| `artist_detail` | 1,499 | 10.0% |
| **`host_detail`** | **0** | **0.0%** |

매니페스트에 검증해 넣은 주최자 ID는 사용되지 않았다. **`/api/hosts/{id}`는 이번 테스트에서 부하를 받지 않았으므로, 「주요 API 전수 검증」이라고 기술해서는 안 된다.**

**② 검색 버킷 태깅이 동작하지 않았다.** `search`가 2,998건 나갔는데 `searchTags`의 16개 조합이 모두 0건이다. 희귀어·공백정규화·영문 등 버킷별 지연 비교가 통째로 불가능했다.

**③ `imageSha`가 `null`이다.** 배포 실험인데 영수증에 **어느 이미지에서 어느 이미지로 바뀌었는지**가 없다. `gitSha`는 부하 생성기 쪽 커밋이다.

## 결론

| 질문 | 답 | 근거 |
| --- | --- | --- |
| 부하를 견디는가 | **예** | 150 RPS에서 CPU 35.5%, 오류 0%, pending 0 |
| 무중단 배포가 되는가 | **예** | 14,991건 전원 성공, 5xx 0%, 체크 100% |
| 먼저 포화되는 자원은 | **CPU** | 풀 10개 중 2개만 사용, pending 0 유지 |
| 축제 당일 배포해도 되는가 | **예** | 배포가 CPU 47%p를 쓰므로 여유 구간에서 안전 |
| 수용 한계는 어디인가 | **미측정** | 최고 단계에서 포화 미도달 (#228) |

관측 스택 쪽에서도 성과가 있었다. 계단 부하·배포·회복이 `festa-overview` 대시보드 한 화면에 그대로 찍혔고, 특히 **최대 응답시간 패널이 부하 구간 내내 바닥에 붙어 있다가 배포 순간에만 솟는 모습**으로 「부하는 느리게 만들지 않았고 배포만 잠깐 느리게 만들었다」를 단독으로 보여준다.
