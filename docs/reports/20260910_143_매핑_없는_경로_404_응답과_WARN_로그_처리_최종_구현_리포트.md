# 매핑 없는 경로 404 응답과 WARN 로그 처리 최종 구현 리포트

## 작업 개요

Issue #143과 PR #145는 존재하지 않는 정적·API 경로 요청이 `NoResourceFoundException`으로 전파된 뒤 전역 catch-all에 잡혀, `500 INTERNAL_SERVER_ERROR`와 ERROR 스택트레이스로 기록되던 문제를 수정했다.

최종 PR head `0e6411b4026b72b4481ef23aa2cf3e3f2b53ec95`와 develop merge commit `e52f944439297a7069a0c9d270cf4be1e821b79e`을 기준으로 확인했다. 실제 머지 diff는 `GlobalExceptionHandler` 1파일 `+10/-0`이다.

- 관련 Issue: [#143](https://github.com/greedy-team/festa-backend/issues/143)
- 관련 PR: [#145](https://github.com/greedy-team/festa-backend/pull/145)
- 보고서 파일: `docs/reports/20260910_143_매핑_없는_경로_404_응답과_WARN_로그_처리_최종_구현_리포트.md`

## 문제 상황과 기존 동작

Spring MVC가 매핑되지 않은 경로를 `NoResourceFoundException`으로 처리할 때, 기존 `GlobalExceptionHandler`에는 이 예외의 전용 핸들러가 없었다. 따라서 `@ExceptionHandler(Exception.class)`가 예외를 받아 `INTERNAL_SERVER_ERROR` 500 응답을 만들고 `log.error(..., e)`로 전체 스택트레이스를 남겼다.

존재하지 않는 경로는 외부 스캐너·브라우저의 일반적인 요청에서도 발생한다. 이 요청을 서버 내부 장애처럼 500과 ERROR로 기록하면 실제 장애 신호와 구분하기 어렵고, 스택트레이스가 로그 보관 용량을 불필요하게 사용한다.

## 구현 내용

### NoResourceFoundException 전용 처리

- **파일**: `src/main/java/com/greedy/festa/global/exception/GlobalExceptionHandler.java`
- `NoResourceFoundException`을 import하고 `handleNoResourceFoundException` 전용 핸들러를 추가했다.
- 핸들러는 `CommonErrorCode.RESOURCE_NOT_FOUND`를 `toResponse(...)`에 전달해 기존 공통 에러 응답 형식으로 404를 반환한다.
- 로그에는 `RESOURCE_NOT_FOUND - {HTTP method} {request URI}`를 WARN으로 남긴다.

### 기존 RESOURCE_NOT_FOUND 재사용

`RESOURCE_NOT_FOUND`는 도메인 특정 코드가 없는 리소스 부재를 위한 기존 공통 404 코드다. 이번 변경은 새 응답 형식이나 새 에러 코드를 만들지 않고, 이미 정의돼 있던 코드의 실제 사용 경로를 추가했다. 따라서 클라이언트는 기존 `ErrorResponse` 형식과 공통 오류 처리 규칙을 그대로 사용한다.

### WARN/ERROR 책임과 stack trace 정책

전용 핸들러의 `log.warn(...)` 호출은 예외 객체를 인자로 넘기지 않는다. 처리된 경로 부재는 요청 메서드와 URI만으로 원인을 확인할 수 있어 stack trace를 남기지 않는다.

반대로 `@ExceptionHandler(Exception.class)`는 변경하지 않았다. 예상하지 못한 예외는 기존처럼 `INTERNAL_SERVER_ERROR` 500을 반환하고 `log.error(..., e)`로 ERROR와 stack trace를 남긴다. 처리된 요청 실패와 조사해야 할 서버 오류를 로그 레벨과 증빙량으로 구분한다.

## 범위와 기존 동작에 미치는 영향

- 매핑되지 않은 정적·API 경로만 500에서 404로 바뀐다.
- 지원하지 않는 HTTP 메서드의 `HttpRequestMethodNotSupportedException` 405 처리와 본문 역직렬화 실패의 400 처리는 이번 diff에 없다.
- 도메인 리소스 조회의 `FESTIVAL_NOT_FOUND`, `ARTIST_NOT_FOUND`, `HOST_NOT_FOUND` 등 기존 404 경로도 변경하지 않았다.
- API 응답 구조, 데이터베이스 스키마, 의존성, 컨트롤러 매핑은 변경하지 않았다.

## 결정 기록 (ADR)

### 경로 부재는 전용 404와 WARN으로 처리한다

- **문제**: 매핑되지 않은 경로가 catch-all로 흘러 500 및 ERROR 스택트레이스로 기록돼, 정상적으로 처리 가능한 요청 실패가 서버 장애처럼 보였다.
- **선택**: `NoResourceFoundException`만 전용 핸들러에서 기존 `RESOURCE_NOT_FOUND` 404로 변환하고, WARN에 메서드·URI만 기록한다.
- **대안**:
  - catch-all을 그대로 사용 — 실제 서버 오류와 경로 부재를 구분할 수 없다.
  - 새 전용 에러 코드 추가 — 기존 공통 404 코드와 응답 계약을 불필요하게 늘린다.
  - 405·400 예외까지 함께 처리 — 각각의 응답 계약과 검증이 필요해 Issue 범위를 넘는다.
- **트레이드오프**: 이 변경만으로 지원하지 않는 HTTP 메서드와 잘못된 본문에 대한 500 가능성은 해소되지 않는다.
- ⭐ **볼트 승격 권장** — 처리된 요청 실패와 예상하지 못한 서버 오류의 로그 책임을 구분하는 운영 규칙이다.

## 리뷰 과정에서 확인한 사항

PR #145에는 GitHub review 또는 라인 코멘트가 등록되지 않았다. GitHub Actions의 테스트 결과 댓글만 존재한다.

머지된 `GlobalExceptionHandler`와 PR diff를 대조해 다음을 확인했다.

- 전용 핸들러는 `NoResourceFoundException`에만 적용된다.
- 404 응답은 새 코드가 아닌 `RESOURCE_NOT_FOUND` 재사용이다.
- WARN 로그 호출에는 예외 객체가 없어 stack trace를 기록하지 않는다.
- 기존 catch-all의 `log.error(..., e)`와 `INTERNAL_SERVER_ERROR` 500 반환은 그대로다.
- 400·405 처리 변경이나 테스트 소스 추가는 실제 merge diff에 없다.

## 테스트 및 CI/CD

## 남은 후속 사항

- `HttpRequestMethodNotSupportedException`의 405 변환과 `HttpMessageNotReadableException`의 400 변환은 별도 범위로 남는다.
- 전용 핸들러의 영구 HTTP 회귀 테스트는 최종 PR에 포함되지 않았다. 향후 예외 매핑을 바꿀 때는 실제 애플리케이션 요청 기준으로 404 응답과 WARN 무스택 로그를 함께 검증할 필요가 있다.
