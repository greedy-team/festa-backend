### 📌 작업 개요

[#166](https://github.com/greedy-team/festa-backend/issues/166)의 개발 서버에서 동일 이미지로
기본 JVM과 `-XX:TieredStopAtLevel=1`을 각각 3회 측정했다. Spring 기동 중앙값이
104.797초에서 55.105초로 49.692초(47.4%) 줄어 개발 환경에 채택한다.
기동 직후 첫 API 조회는 느려졌으며, 운영 환경으로 확대하지 않는다.

측정을 위해 준비했던 실험 스위치(`STARTUP_JVM_TRIAL`)는 이 판정으로 필요가 없어져 걷어내고,
development 배포에 옵션을 항상 적용하는 구성으로 바꿨다.

### 🔍 측정 조건

- 선행 이슈 #156·#164·#165는 모두 종료됐고 GHCR 배포도 성공했다.
- 이미지: `ghcr.io/greedy-team/festa-backend:0db4738393e84ff2a8958342cd260f500a452ef3-amd64-34690469768-2`.
- OCI 개발 서버: 가용 메모리 총량 약 954MiB, `nproc` 출력 2, 스왑 약 2GiB.
- 실제 JVM 기본값: `TieredStopAtLevel=4`, `UseSerialGC=true`, 최대 힙 251658240바이트.
- 기본 → 후보 순서를 3회 반복했다. 앱만 `--no-deps --force-recreate`로 교체하고
  PostgreSQL·Caddy·DB·이미지는 유지했다. 빌드와 다운로드 시간은 포함하지 않는다.
- 후보는 임시 Compose override의 entrypoint를
  `["java", "-XX:TieredStopAtLevel=1", "-jar", "app.jar"]`로 설정했다.
- Docker 헬스체크와 Compose의 `--wait-timeout 300`은 변경하지 않았다.
- 첫 스크립트 전달 오류로 중단된 시도는 표본에서 제외했다. 아래는 수정 후 완주한 6회다.

### 🧪 실측 결과

Spring 기동은 `Started FestaApplication in … seconds` 로그에서 읽었다.
Compose 대기는 `up` 호출 직전부터 `--wait` 종료까지여서 기존 앱 종료·컨테이너 생성·
헬스체크 판정 대기도 포함한다. 두 지표를 같은 기동 시간으로 혼용하지 않는다.

6회 모두 `/actuator/health`가 `UP`이었고
`/api/artists?page=0&size=10`이 HTTP 200을 반환했다. API 시간은 기동 직후 첫 요청
한 번씩의 측정이며, 워밍업 후 처리량이나 부하 테스트 결과가 아니다.

기본 기동의 관측 범위는 90.978~123.984초(폭 33.006초), 후보는
50.022~55.592초(폭 5.570초)다. 중앙값 차이 49.692초가 두 범위의 폭보다 크고,
후보 3회 모두 가장 빠른 기본값보다 빨랐다. Compose 대기 중앙값도 55초(40.4%) 줄었다.
표본이 각각 3개이고 시간대·서버 부하가 통제되지 않았으므로 통계적 유의성이나
향후 모든 배포의 동일한 절감 폭을 보장하지는 않는다.

### ✅ 구현 내용

- `.github/workflows/PROJECT-SPRING-CD.yaml`: `development`일 때만 `app.env`에
  `APP_JAVA_TOOL_OPTIONS='-XX:TieredStopAtLevel=1'`을 기록하고 `production`은 빈 값을 기록한다.
  기존 `DEPLOY_ENVIRONMENT`를 사용하므로 push와 수동 배포에 같은 분기가 적용된다.
  선택한 값은 `JVM 기동 옵션: JAVA_TOOL_OPTIONS=…` 로그로 남기며, 실험 스위치 변수 참조는 제거했다.
- 배포 실패 롤백: `app.env`에서 옵션 줄을 지우고 JVM 기본값으로 직전 정상 이미지를 띄운다.
  옵션이 실패 원인이어도 복구가 같은 이유로 막히지 않게 하기 위해서다. 다음 정상 배포가
  `app.env`를 다시 쓰면서 옵션이 복원된다.
- `deploy/compose.yaml`: `APP_JAVA_TOOL_OPTIONS`를 앱의 `JAVA_TOOL_OPTIONS`로 전달하며 기본값은 빈 문자열이다.
- `deploy/test_deployment.py`: development만 옵션을 받고 production은 기본값인지,
  실패 롤백이 옵션 줄을 지우고 직전 이미지를 띄우는지 검증한다.
- `deploy/README.md`: 적용 범위, 롤백 시 동작, 채택을 되돌리는 방법과 이 측정 결과 링크를 추가했다.
- `deploy/startup-trial.md`: 스위치 사용 절차가 더는 맞지 않아 삭제했다. 기준 표본은 위 표로 옮겼다.
- 앱 코드·의존성·헬스체크 예산은 변경하지 않았다. 새로운 Secret·Variable은 필요 없다.

### 🧭 결정 기록 (ADR)

#### 기동 최적화는 development에만 적용

- **문제**: 단일 배포의 기동 편차가 커서 옵션 효과를 한 번의 배포로 판정할 수 없었다.
- **선택**: 같은 이미지의 반복 측정에서 편차를 넘는 절감이 확인돼 개발 서버에 항상 적용한다.
- **대안**:
  - JVM 기본값 유지. 운영 환경에는 이 선택을 유지한다.
  - 실험 스위치를 켠 평소 배포 5건 이상으로 표본을 다시 모으고, API 응답 악화가 없을 때만 채택.
    같은 이미지 반복 측정으로 편차를 넘는 차이가 이미 확인됐고, 첫 요청 지연은 개발 서버에
    한정된 트레이드오프로 받아들여 채택하지 않았다.
- **트레이드오프**: C2 최적화를 사용하지 않아 장시간 실행 성능이 낮아질 수 있다.
  실제로 첫 아티스트 조회 중앙값은 1.964초에서 5.689초로 늘었다. 개발 환경의
  배포 대기 단축을 위한 선택이며, API 성능 개선으로 해석하지 않는다.
- GC·힙은 기존 기본값을 유지한다. 초기화 지연으로 설정 오류를 숨기지 않는다.
- ⭐ **볼트 승격 권장** — 기동 시간과 실행 성능을 맞바꾼 선택의 근거다.

[Spring Boot의 BootRun 구현](https://raw.githubusercontent.com/spring-projects/spring-boot/main/build-plugin/spring-boot-gradle-plugin/src/main/java/org/springframework/boot/gradle/tasks/run/BootRun.java)도
개발용 빠른 기동에 같은 옵션을 사용한다. 외부 근거는 후보 선정에만 사용했고,
채택 판단은 위 서버 실측으로 했다.

### 🧪 구성 검증

- 배포 스크립트 테스트 12개 통과(`python -B -m unittest discover -s deploy -p 'test_*.py'`).
  새 테스트가 스위치가 남아 있던 워크플로우에서는 development 옵션 누락으로 실패하는 것을 먼저 확인했다.
- 수정한 Compose를 Docker Compose `config`로 렌더링해 development는 옵션 값,
  production과 롤백 경로(옵션 줄 삭제 + 빈 값)는 빈 값이 전달되는 것을 확인했다.
- 앱 코드 변경이 없어 Gradle 빌드·애플리케이션 테스트는 다시 실행하지 않았다.
- 장시간 API 부하와 arm64 운영 환경은 측정하지 않았다.

### 📌 적용 상태와 복구

측정용 override는 저장소 배포 설정과 분리했다. 측정 후 서버를 기존 기본 Compose로
복구했고 실제 프로세스가 `java -jar app.jar`임을 확인했다. 외부 HTTPS 헬스체크는
`UP`, 아티스트 목록은 HTTP 200이었다. PostgreSQL·Caddy는 재기동하지 않았다.

저장소 변경은 develop 머지 후 첫 정상 배포부터 적용된다. 적용 뒤 CD 로그의 `JVM 기동 옵션` 줄과
실행 중인 앱 컨테이너의 `JAVA_TOOL_OPTIONS`가 일치하는지 확인한다. 배포 실패 롤백은 옵션을 해제한 채
직전 이미지를 띄우고, 다음 정상 배포에서 다시 적용된다. 채택 자체를 되돌리려면 CD의 development
분기에서도 빈 값을 기록하도록 고친 뒤 재배포한다.
