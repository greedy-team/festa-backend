### 📌 작업 개요

`POST /api/admin/festivals/publish` 일괄 발행 API를 추가했다.
축제 id 목록을 받아 발행 가능한 것만 발행하고, 막힌 것은 사유와 함께 응답 본문으로 돌려준다.

임포트가 커밋한 축제는 **전부 미발행으로 들어온다.** 한 배치가 수십 건이면 관리자가
검수 목록에서 그만큼 눌러야 했다. #46이 개별 발행으로 게이트를 확정하며
*"개별 발행이 게이트를 확정하면 일괄은 그것을 반복 적용하는 일"*이라고 후속으로 미뤄둔 자리이고,
그 선행 조건이 PR #55로 닫히면서 이번에 만들었다.

명세의 관리자 API 15개 중 **축제 쪽에서 마지막으로 남아 있던 엔드포인트**다.

### 🎯 구현 목표

- 부분 성공을 허용한다 — 실패를 HTTP 상태가 아니라 응답 본문으로 낸다
- 발행 게이트를 두 벌 만들지 않고 개별 발행과 같은 함수를 재사용한다
- id마다 조회가 나가지 않게 한 번에 집계한다
- 요청 자체의 오류(빈 목록·100개 초과)는 부분 성공 이전에 막는다

### ✅ 구현 내용

#### 엔드포인트

- **파일**: `festival/controller/FestivalAdminController.java`
- **변경 내용**: `POST /publish`. 요청 body는 `festivalIds`, 응답은 200에
  `publishedIds`와 `failed[]`. Swagger 설명과 응답 코드도 함께 달았다
- **이유**: 클래스 레벨이 `/api/admin/festivals`라 최종 경로는 `/api/admin/festivals/publish`다.
  개별 발행(`/{id}/publish`)과 경로가 겹치지 않는다

#### 요청·응답 DTO

- **파일**: `festival/dto/FestivalBatchPublishRequest.java`,
  `FestivalBatchPublishResponse.java`, `FestivalPublishFailure.java`,
  `FestivalPublishFailureReason.java`
- **변경 내용**: 응답은 `publishedIds`와 `failed[]` **둘뿐**이다.
  `failed[]`의 원소는 `festivalId` + `reason`
- **이유**: 명세 원본은 `requested`·`published` 건수를 함께 두지만
  각각 `festivalIds.size()`·`publishedIds.size()`와 **항상 같은 값**이다.
  한 사실을 두 필드가 말하면 갈라질 여지가 생기고, 갈라지면 어느 쪽이 참인지 정하는 규칙이 또 필요하다

```json
{
  "publishedIds": [1, 2, 7],
  "failed": [
    { "festivalId": 4, "reason": "LINEUP_EMPTY" },
    { "festivalId": 9, "reason": "HOST_NOT_LINKED" }
  ]
}
```

`FestivalPublishFailureReason`은 `LINEUP_EMPTY` · `HOST_NOT_LINKED` ·
`COORDINATES_MISSING` · `NOT_FOUND` 넷이며 **`FestivalErrorCode`와 별도 enum**이다.
`from(FestivalPublishBlocker)`가 게이트 결과를 사유로 옮긴다.

#### 일괄 발행 로직

- **파일**: `festival/service/FestivalAdminService.java`
- **변경 내용**: `batchPublish(List<Long> ids)` — 검증 → 중복 제거 → 일괄 조회 →
  id별 판정 → 응답 조립
- **이유**: 실패를 예외가 아니라 **데이터로 모은다.** 루프가 아무것도 던지지 않으므로
  한 트랜잭션으로도 부분 성공이 성립한다

판정 순서는 이렇다.

```
조회 결과에 없음            → failed[NOT_FOUND]
이미 publishedAt이 있음     → publishedIds  (게이트를 보지 않는다)
게이트에 걸림               → failed[첫 번째 blocker]
그 외                      → publish(publishedAt) 후 publishedIds
```

`Instant.now(clock)`을 루프 **밖에서 한 번** 뽑아 같은 배치의 발행 시각을 하나로 맞췄다.
`distinct()`로 중복 id는 한 번만 처리하고, 응답은 요청 순서를 유지한다.

#### 한 번에 집계하는 조회

- **파일**: `festival/repository/FestivalRepository.java`
- **변경 내용**: `findPublishTargets(festivalIds)` — 축제·주최·라인업 수를
  `LEFT JOIN` + `GROUP BY`로 한 번에 가져오는 프로젝션
- **이유**: 개별 발행이 쓰는 `countLineupsByFestivalId`를 id마다 부르면
  **100건 요청에 조회가 100번** 나간다

#### 요청 검증

- **파일**: `festival/exception/FestivalErrorCode.java`
- **변경 내용**: `FESTIVAL_INVALID_IDS`(400) 추가.
  목록이 `null`이거나 비었거나 100개를 넘거나 `null` 원소를 담으면 **아무것도 발행하지 않고** 던진다
- **이유**: 이것은 개별 축제의 실패가 아니라 요청 자체가 성립하지 않는 경우다.
  부분 성공 체계에 섞으면 「무엇을 요청했는지 모르겠다」를 `failed[]`에 담아야 한다

### 🧭 결정 기록 (ADR)

#### 실패를 예외가 아니라 데이터로 모은다 — 트랜잭션은 하나

- **문제**: 부분 성공을 어떻게 만들 것인가. 기존 `publish(Long id)`는 게이트에 걸리면
  `FestaException`을 던진다
- **선택**: 게이트에 걸린 축제는 예외 없이 건너뛰고 사유를 `failed[]`에 담는다.
  전체가 `@Transactional` 하나다
- **대안**: `publish(id)`를 id마다 호출하고 예외를 잡는다 — **프록시를 거친 내부 트랜잭션이
  rollback-only를 표시해 바깥 커밋이 `UnexpectedRollbackException`으로 터진다.**
  그 구조를 고르면 축제 단위로 트랜잭션을 갈라야 한다
- **트레이드오프**: 부분 성공은 **게이트 실패에 대한 것이지 DB 오류에 대한 것이 아니다.**
  트랜잭션이 하나이므로 저장 중 제약 위반이 나면 그 배치 전체가 rollback된다
- 이슈 본문이 이 자리에서 한 번 정정됐다. 초안은 *"트랜잭션 경계를 축제 단위로 가른다 …
  구현의 선택지가 아니라 계약이 요구하는 조건이다"*라고 적었으나, 그 문장은
  **실패를 예외로 신호할 때만 참**이다. PR #65 리뷰에서 드러나 2026-08-26에 고쳤다

#### 존재하지 않는 id가 전체를 막지 않는다

- **문제**: 100개 중 하나가 지워졌을 때
- **선택**: `reason: NOT_FOUND`로 `failed[]`에 담고 나머지 발행은 진행한다
- **대안**: 404로 전체 거절 — **부분 성공을 허용한 이유 자체가 사라진다.**
  관리자는 어느 것이 없는지도 모른 채 목록을 새로 고쳐 다시 골라야 한다
- **트레이드오프**: 명세에 정의가 없어 여기서 정한 자리다. **명세와 갈리는 자리 2**

#### 게이트를 재사용하고 사유는 첫 하나만 낸다

- **문제**: 일괄 경로에 게이트를 다시 쓸지
- **선택**: `FestivalPublishBlocker.evaluate()`를 개별 발행과 공유한다.
  위반이 여럿이면 `blockers.getFirst()` 하나만 `reason`으로 낸다
- **대안**: 일괄용 게이트를 따로 구현 — 판정이 두 곳으로 갈리면
  같은 축제가 개별에서는 발행되고 일괄에서는 막히는 일이 생긴다
- **트레이드오프**: 라인업도 없고 좌표도 없는 축제는 **한 번에 한 사유만 보인다.**
  관리자는 하나를 고치고 다시 눌러야 두 번째 사유를 안다

#### 이미 발행된 축제는 게이트를 보지 않고 성공으로 담는다

- **문제**: 이미 `publishedAt`이 있는 축제를 다시 요청했을 때
- **선택**: 시각을 유지한 채 `publishedIds`에 담는다. **게이트 판정 자체를 건너뛴다**
- **대안**: 다시 게이트를 통과시켜야 성공 — 발행 후 라인업이 지워진 축제가
  일괄 요청마다 실패로 뜬다. 이미 공개된 축제를 「발행 실패」라고 말하게 된다
- **트레이드오프**: **게이트는 발행하는 순간에만 적용된다.** 과거에 발행된 뒤
  조건이 깨진 축제는 이 API가 다시 걸러주지 않는다.
  테스트 `이미_발행된_축제는_게이트를_어겨도_성공으로_담긴다`가 이 동작을 못박고 있다

#### 사유를 에러 코드 enum에 넣지 않는다

- **문제**: `LINEUP_EMPTY` 같은 값을 `FestivalErrorCode`에 넣을지
- **선택**: 별도 `FestivalPublishFailureReason` enum으로 둔다
- **대안**: 에러 코드에 합치기 — 에러 코드는 **HTTP 상태와 짝지어 실패한 요청**을 말하는 체계다.
  여기서는 요청이 성공(200)했고 그 안의 항목이 처리되지 않은 것이라 의미가 다르다.
  에러 코드 표도 *"이 표의 `errorCode`와는 다른 체계다. 섞이지 않도록 구분해 두어야 한다"*고 적었다
- **트레이드오프**: 프론트가 두 벌의 상수 목록을 갖는다
- ⭐ **볼트 승격 권장** — 부분 성공 응답과 에러 코드를 가르는 경계이고, 이후 일괄 API가 따를 규약이다

`@DataJpaTest` + `PostgresTestSupport`로 **실제 PostgreSQL**에 붙는다.

**스키마가 일부러 허용한 상태**다. 엔티티를 목으로 세우면 실제로 그 행이 저장될 수 있는지는
확인되지 않는다. 그래서 실물 행으로 검증했다.

잠근 동작: 게이트 3종 각각, 위반이 여럿일 때 첫 사유만, 없는 id가 나머지를 막지 않음,
이미 발행된 축제의 시각 유지, 이미 발행된 축제가 게이트를 어겨도 성공,
중복 id 1회 처리, 요청 순서 유지, 그리고 `FESTIVAL_INVALID_IDS` 세 경로(빈 목록·100 초과·null 원소).

### 📌 참고사항

**이 API는 지금 실전에서 거의 전부 `COORDINATES_MISSING`으로 실패한다.**
`latitude` · `longitude`를 채우는 코드가 저장소에 없다. 두 필드는 `Festival` 빌더로만 들어오는데,
임포트 CSV 헤더(`ImportSection.FESTIVALS`)에 좌표 열이 아예 없어 임포트로 들어온 축제는
좌표가 `null`이다. 축제 등록·수정 API도 없다.

**이 PR이 만든 문제가 아니고 개별 발행(#46)도 같은 상태다.** 발행 게이트가 좌표를 요구하기로 한
결정 자체는 유효하며, 좌표 공급 경로(크롤러 지오코딩 또는 관리자 입력)가 정해져야 닫힌다.
이슈 #15가 *"축제 위치 좌표는 크롤러가 지오코딩해 내보내는 것으로 설계됐으나 현재 산출물에
해당 컬럼이 없다"*고 이미 적어 둔 자리다.

**응답만 봐서는 「지금 발행됨」과 「이미 발행돼 있었음」을 구분할 수 없다.**
둘 다 `publishedIds`에 들어간다. 멱등 계약의 대가이고 #46이 개별 발행에 정한 규칙을
그대로 반복한 결과다. 구분이 필요하면 응답 형식을 바꿔야 한다.

**부분 성공은 게이트에만 적용된다.**
트랜잭션이 하나이므로, 발행 저장 중 DB 오류가 나면 `failed[]`에 담기지 않고
그 배치 전체가 rollback된다. 현재 `publish()`가 `publishedAt` 하나만 세팅해 위험이 낮지만,
발행이 다른 테이블을 건드리게 되면 이 전제를 다시 봐야 한다.

- **일괄 발행 해제는 없다.** 명세의 관리자 API 15개에 없어 해제는 개별
  (`DELETE /api/admin/festivals/{id}/publish`)만 둔다
- **발행 이력과 되돌리기는 만들지 않았다.** #46의 판정을 유지한다
- **명세와 갈리는 자리가 둘이다** — 응답에서 `requested`·`published` 건수를 뺀 것,
  그리고 없는 id를 전체 거절이 아니라 `failed[]`로 처리한 것.
  프론트가 명세 기준으로 이미 만들었다면 맞춰야 한다
- 이 이슈는 #60(`/api` 접두사, PR #62)과 `FestivalAdminController`를 함께 건드리지만
  스택하지 않고 `develop`에서 분기했다. 클래스 레벨 매핑 아래에 메서드를 더하는 형태라
  머지 순서와 무관하게 최종 경로가 `/api/admin/festivals/publish`로 수렴했다
