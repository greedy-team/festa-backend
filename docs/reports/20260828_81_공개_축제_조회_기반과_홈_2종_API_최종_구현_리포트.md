# 공개 축제 조회 기반과 홈 2종 API 최종 구현 리포트

## 작업 개요

홈 화면에서 사용할 공개 축제 조회 기반과 다가오는 축제·최근 등록 축제 API를 구현했다. 공개된 축제만 조회하도록 기준을 통일하고, 조회 목적별 정렬·기간 조건과 응답 필드를 분리했다. 리뷰에서 확인된 다가오는 축제의 장소 정보와 잘못된 `limit` 형식의 400 오류 계약까지 반영했다.

## 구현 범위

### 다가오는 축제 조회

- `GET /api/festivals/upcoming`
- `published_at IS NOT NULL`인 공개 축제만 조회
- KST 기준 오늘 종료되지 않은 축제(`endDate >= today`)만 조회
- 시작일 오름차순, 동일 시작일이면 ID 오름차순 정렬
- `limit` 기본값 10, 허용 범위 1~50
- 축제·주최자 요약, 포스터, 장소명, 시작일과 종료일 반환

### 최근 등록 축제 조회

- `GET /api/festivals/recent`
- `published_at IS NOT NULL`인 공개 축제만 조회
- 종료 여부와 관계없이 최근 공개된 축제 조회
- 공개 시각 내림차순, 동일 공개 시각이면 ID 내림차순 정렬
- `limit` 기본값 10, 허용 범위 1~30
- 축제·주최자 요약, 포스터, 시작일과 종료일 반환

## API 계약

- 두 API 모두 `ItemsResponse`의 `items` 배열로 결과를 반환한다.
- 다가오는 축제는 `FestivalUpcomingResponse`, 최근 등록 축제는 `FestivalRecentResponse`를 사용한다.
- 주최자 정보는 공통 `HostSummaryResponse`로 반환한다.
- 범위를 벗어난 `limit`와 숫자로 변환할 수 없는 `limit`은 모두 HTTP 400과 `FESTIVAL_INVALID_LIMIT`를 반환한다.
- 데이터가 없으면 HTTP 200과 빈 `items` 배열을 반환한다.

## 주요 구현 내용

- 저장소 쿼리에서 공개 여부와 조회별 기간 조건을 적용하고 `Limit`으로 필요한 개수만 조회한다.
- `JOIN FETCH f.host`로 응답 변환 시 주최자 조회 N+1을 방지한다.
- 서비스 조회 트랜잭션을 읽기 전용으로 구성했다.
- 서버 기본 시간대와 무관하게 `Clock`을 서울 시간대로 변환해 다가오는 축제의 오늘 날짜를 계산한다.
- 컨트롤러에 `MethodArgumentTypeMismatchException` 처리기를 두어 `limit=abc`, `limit=3.5` 같은 입력도 축제 API의 오류 계약으로 변환한다.
- 컨트롤러 전용 오류 응답을 생성할 수 있도록 `ErrorResponse.of(errorCode, requestURI)` 팩토리를 추가했다.

## 리뷰 반영 내용

### 다가오는 축제 장소 정보

- 홈 HeroPanel에서 사용하는 장소명이 초기 응답에 빠져 있던 문제를 반영했다.
- 기존 단일 카드 응답을 조회 목적별 DTO로 분리하고, 다가오는 축제 응답에만 `venueName`을 추가했다.
- 실제 HTTP 응답 테스트에서 다가오는 축제에는 `venueName`이 있고 최근 등록 축제에는 없는 계약을 검증했다.

### 잘못된 limit 형식의 400 계약

- 숫자가 아닌 쿼리 파라미터가 서비스 검증 전에 바인딩 실패하는 경우를 별도로 처리했다.
- `GET /api/festivals/upcoming?limit=abc`와 `GET /api/festivals/recent?limit=3.5`가 HTTP 400 및 `FESTIVAL_INVALID_LIMIT`를 반환하는 컨트롤러 테스트를 추가했다.
- 범위 경계와 초과·미달 검증 테스트도 함께 유지해 두 API의 서로 다른 상한을 검증한다.
