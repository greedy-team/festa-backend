### 📌 작업 개요

에러 응답 형식을 네 필드로 통일하고, 공통 예외 · 에러 코드 규약 · 전역 예외 처리를 추가했다.
첫 API가 들어가는 순간 형식이 굳으므로, API보다 먼저 형식을 코드로 확정하는 것이 목적이었다.

### 🔍 현재 문제점

- 에러 응답 형식이 코드에 없었다. 회의에서 합의만 하고 구현으로 옮기지 않은 상태였다
- 성공 응답은 화면마다 다르게 쓰이니 제각각이어도 되지만, 에러는 "터졌다"는 같은 사건이라
  형식이 같아야 프론트가 한 번만 처리한다

### ✅ 구현 내용

#### 에러 응답 형식 정의

- **파일**: `global/exception/ErrorResponse.java`
- **변경 내용**: `errorCode` · `message` · `status` · `instance` 네 필드 record
- **이유**: 필드를 넷으로 고정한다. 다섯 번째 필드를 만들지 않기 위해 필드별 오류 배열도 두지 않았다

#### 에러 코드 규약

- **파일**: `global/exception/ErrorCode.java`(인터페이스), `global/exception/CommonErrorCode.java`(공통 코드 12개)
- **변경 내용**: `name()` · `getMessage()` · `getStatus()`를 요구하는 인터페이스를 두고,
  공통 코드를 그 구현 enum으로 정의
- **이유**: 코드를 공통과 도메인별로 나누어 관리하되 하나의 규약으로 묶는다.
  여러 명이 서로 다른 도메인을 동시에 작업할 때 **코드가 한 파일에 몰려 충돌하는 것**을 막는다

공통 코드는 파라미터 오류를 하나로 묶지 않고 개별로 나눴다 — `INVALID_PAGE`, `INVALID_PAGE_SIZE`,
`INVALID_DATE_RANGE`, `INVALID_IMAGE_FORMAT`, `INVALID_REQUEST_BODY`, `INVALID_PATH_VARIABLE`.
에러 코드 하나가 사용자 문구 하나에 대응하면 프론트가 응답 본문을 파헤치지 않아도 된다.
인증·권한·조회 실패·메서드 오류·서버 오류는 각각 `UNAUTHORIZED` · `TOKEN_EXPIRED` · `FORBIDDEN` ·
`RESOURCE_NOT_FOUND` · `METHOD_NOT_ALLOWED` · `INTERNAL_SERVER_ERROR`로 뒀다.

#### 공통 예외

- **파일**: `global/exception/FestaException.java`
- **변경 내용**: `ErrorCode`를 들고 다니는 `RuntimeException` 하나. 메시지를 덮어쓰는 생성자를 함께 둠
- **이유**: 전역 예외 처리가 모든 예외를 같은 방식으로 다루므로 도메인별로 예외 클래스를 나눌 이유가 없다

#### 전역 예외 처리

- **파일**: `global/exception/GlobalExceptionHandler.java`
- **변경 내용**: `@RestControllerAdvice`로 `FestaException`과 `Exception`을 받아 `ErrorResponse`로 변환.
  `instance`는 `request.getRequestURI()`로 일괄 주입
- **이유**: 경로를 개별 처리 지점에 맡기면 누락이 생긴다. 한 곳에서 채운다

`FestaException`은 `log.warn`에 코드 이름과 메시지를 남기고 코드가 정한 상태로 나간다.
그 밖의 예외는 `log.error`로 스택트레이스를 남기고 500으로 나간다.
**로그 레벨이 두 예외 채널을 가르는 신호**다 — `error`가 찍혔다면 우리가 예상하지 못한 경로라는 뜻이다.

### 🧭 결정 기록 (ADR)

#### `instance`에 경로 템플릿이 아니라 치환된 실제 경로를 담음

- **문제**: `/api/festivals/{id}/summary`와 `/api/festivals/42/summary` 중 무엇을 담을지
- **선택**: 값이 치환된 실제 요청 경로
- **대안**: 경로 템플릿 — 어느 엔드포인트인지만 알 뿐 **어느 호출이 실패했는지**는 알 수 없다
- **트레이드오프**: 경로에 식별자가 들어가므로 로그·응답에 리소스 id가 노출된다

#### 예외 클래스를 도메인별로 나누지 않음

- **문제**: 도메인마다 예외 클래스를 둘지
- **선택**: `FestaException` 하나. 구분은 `ErrorCode`가 한다
- **대안**: 도메인별 예외 — 핸들러가 도메인 수만큼 늘어나는데 처리 내용은 전부 같다
- **트레이드오프**: 타입으로 잡아 분기하는 것이 불가능해진다. 필요하면 `ErrorCode`로 분기한다
- ⭐ **볼트 승격 권장** — 모든 도메인 구현이 따라야 하는 예외 규약이다

#### 에러 코드 이름에 도메인 접두사를 붙임

- **문제**: 코드 목록이 파일로 나뉘면 이름이 겹칠 수 있다
- **선택**: 도메인 접두사(`HOST_NOT_FOUND` 형태)를 붙여 코드 문자열이 전역에서 유일해지게 한다
- **대안**: 접두사 없음 — 두 도메인이 각자 `NOT_FOUND`를 정의하면 프론트가 구분할 수 없다
- **트레이드오프**: 이름이 길어진다

#### 필드별 오류 배열을 두지 않음

- **문제**: 검증 실패 시 어떤 필드가 틀렸는지 전달할지
- **선택**: 두지 않는다. 대신 파라미터마다 개별 에러 코드를 준다
- **대안**: `fieldErrors` 배열 추가 — 응답을 네 필드로 고정하기로 한 결정과 충돌한다
- **트레이드오프**: 한 요청에서 여러 필드가 동시에 틀리면 첫 번째만 알려주게 된다

### 🧪 테스트 및 검증

이 작업에는 테스트가 포함되지 않았다. 형식만 정의하고 이를 사용하는 API가 아직 없어
실제 응답을 만들어 볼 대상이 없었기 때문이다. 규약이 실제로 동작하는지는 첫 API인 이슈 #22에서 확인됐다.

### 📌 참고사항

- **정의만 되고 아직 내보낼 경로가 없는 코드가 있다.** `GlobalExceptionHandler`는 `FestaException`과
  `Exception` 두 핸들러만 두므로, 스프링이 던지는 표준 예외(요청 본문 파싱 실패, 경로 변수 타입 불일치,
  지원하지 않는 메서드, 매핑 없는 경로)는 전부 catch-all에 걸려 **500 `INTERNAL_SERVER_ERROR`로 나간다.**
  `INVALID_REQUEST_BODY` · `INVALID_PATH_VARIABLE` · `METHOD_NOT_ALLOWED` · `RESOURCE_NOT_FOUND`는
  이를 매핑하는 핸들러가 추가돼야 실제로 응답에 등장한다
- 메시지는 프론트 개발자가 디버깅할 때 보는 값이다. 사용자에게 그대로 노출하지 않으며,
  사용자 문구는 프론트가 에러 코드별로 따로 준비한다
- 도메인별 에러 코드와 파라미터 검증 매핑은 각 API 이슈에서 이 규약에 맞춰 추가한다.
  어떤 코드가 어떤 파라미터에 붙을지는 API가 정해져야 알 수 있다
