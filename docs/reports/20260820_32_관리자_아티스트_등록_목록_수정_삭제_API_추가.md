### 📌 작업 개요

관리자용 아티스트 CRUD API 4종 추가. 주최 API(#22)가 만든 페이지 응답·에러 규약 위에
아티스트 도메인을 얹고, 별칭(`ArtistAlias`) 관리를 함께 다룬다.

**보고서 파일**: `docs/reports/20260820_32_관리자_아티스트_등록_목록_수정_삭제_API_추가.md`

### 🎯 구현 목표

- 등록 `POST /admin/artists` · 목록 `GET /admin/artists` · 수정 `PATCH /admin/artists/{id}` · 삭제 `DELETE /admin/artists/{id}`
- 별칭 등록·교체·삭제 — 임포트가 라인업의 이름을 아티스트에 맞출 때 쓰는 키
- 출연 횟수 집계와 그에 따른 정렬

### ✅ 구현 내용

#### 컨트롤러

`ArtistAdminController` — `/admin/artists`. `/api` 접두사를 붙이지 않는다.

`Pageable`을 바인딩하지 않고 `page`·`size`·`sort`를 개별 파라미터로 받는다. 이유는 아래 결정 기록 참고.
`genre`·`sort`는 `String`으로 받아 컨트롤러에서 열거값으로 파싱하고, 실패 시 도메인 에러 코드를 던진다.
빈 문자열은 미지정으로 취급한다 — 프론트가 필터를 해제할 때 `?genre=`로 보내는 경우가 흔하다.

#### 서비스

`ArtistService` — 등록·목록·수정·삭제.

- 대표명과 별칭은 모두 `trim` 후 검증·저장한다. 빈 값은 `null`로 정규화한다
- 대표명·별칭 중복 검사는 `artist.name`과 `artist_alias.name` **양쪽**을 본다. 두 테이블이 각자 UNIQUE라 DB가 교차 중복을 막지 못한다
- 별칭 목록은 요청 안 중복 제거, 대표명과 같은 값 제외
- 수정 시 별칭은 **차집합으로 교체**한다

#### 리포지토리

`ArtistRepository` — 목록 집계 쿼리와 중복 검사.
`ArtistAliasRepository` — 별칭 조회·중복 검사·삭제.
`ArtistWithAppearanceCount` — 집계 결과 프로젝션.

목록은 `LEFT JOIN`으로 라인업을 세되 **발행되고 이미 끝난 축제만** 집계한다.
별칭 조회는 `findByArtistIdIn`으로 묶어 N+1을 피한다.

#### 에러 코드

`ArtistErrorCode` 9개. 400 다섯(`ARTIST_INVALID_NAME`·`ARTIST_INVALID_ALIAS`·`ARTIST_INVALID_QUERY`·`ARTIST_INVALID_GENRE_TYPE`·`ARTIST_INVALID_SORT_TYPE`),
409 셋(`ARTIST_DUPLICATE_NAME`·`ARTIST_DUPLICATE_ALIAS`·`ARTIST_HAS_APPEARANCES`), 404 하나(`ARTIST_NOT_FOUND`).

권한 없음(403)은 만들지 않았다. 관리자 권한을 나누지 않기로 해서 관리자 API는 인증만 요구한다.

### 🧭 결정 기록 (ADR)

#### 목록에서 `Pageable`을 바인딩하지 않는다

API 명세의 `sort`는 열거값 3종인데 Spring의 `Pageable`은 같은 파라미터를 `필드,방향`으로 해석한다.
`Pageable`을 쓰면 `?sort=APPEARANCES`가 "APPEARANCES라는 속성으로 정렬"이 되어 실행 시점에 깨지고,
명세가 요구하는 400 대신 500이 나간다. `size` 범위 위반은 예외 없이 조용히 잘리고 `page` 음수는 500이 된다.

즉 명세가 정의한 400 세 개(`INVALID_PAGE`·`INVALID_PAGE_SIZE`·`ARTIST_INVALID_SORT_TYPE`)가
하나도 발생하지 않는다. 그래서 값을 직접 받아 검증한 뒤 `PageRequest`를 만든다.

주최 API는 `Pageable`을 바인딩하고 있어 같은 문제를 안고 있을 수 있다. 확인과 수정은 이 이슈 범위 밖이다.

#### 별칭은 전부 지우고 다시 넣지 않고 차집합으로 교체한다

Hibernate는 flush 시 INSERT를 DELETE보다 먼저 실행한다. 별칭을 통째로 지우고 다시 넣으면
바뀌지 않은 별칭이 INSERT되는 시점에 아직 DELETE가 나가지 않아 `uq_artist_alias_name` 위반이 난다.

관리자가 별칭을 건드리지 않고 저장하는 것이 가장 흔한 요청이라, 이 방식을 택하면 그 순간부터 매번 터진다.
차집합으로 처리하면 안 바뀐 별칭을 아예 건드리지 않아 문제가 발생하지 않는다.

#### 출연 횟수와 삭제 판정은 다른 기준을 쓴다

출연 횟수는 발행되고 끝난 축제만 센다(`published_at IS NOT NULL`, `end_date < CURRENT_DATE`).
반면 삭제 가능 여부는 **FK가 참조 중인지**를 묻는 것이라 발행·종료와 무관하게 전부 세야 한다.

집계 조건을 삭제 가드에 그대로 쓰면 미발행 축제에 출연 중인 아티스트가 삭제되고 FK 위반으로 500이 난다.
그래서 `countAppearancesByArtistId`(조건 있음)와 `countLineupsByArtistId`(조건 없음)로 나눴다.

#### 관리자 요청에서 아티스트 이미지를 받지 않는다

아티스트 사진을 쓰지 않고 기본 이미지로 대체하기로 한 결정에 따른다.
응답 필드는 남기되 값은 항상 비어 있고, 요청 본문에는 필드를 두지 않는다.
`Artist.update` 호출에서 이미지 자리에 `null`을 넘겨 관리자가 이 값을 바꾸지 않는다는 것이 코드에 드러나게 했다.

#### `PATCH`의 `otherNames`는 `null`과 `[]`를 구별한다

배열이라 상태가 셋이고 각각의 의미를 프론트와 합의했다.

| 요청 | 동작 |
| --- | --- |
| 미전송 · `null` | 기존 별칭 유지 |
| `[]` | 전부 삭제 |
| `["다듀"]` | 그걸로 교체 |

별칭을 전부 지우려면 `[]`를 명시적으로 보내야 한다.
빈 배열을 `undefined`로 바꾸는 직렬화가 있으면 삭제가 무시된다.

명세에 없는 계약이라 별도로 공유가 필요하다.

### 🔧 주요 변경사항 상세

#### 대표명·별칭 교차 중복

`artist.name`과 `artist_alias.name`은 다른 테이블이고 각자 UNIQUE라 DB가 서로를 모른다.
막지 않으면 임포트가 그 이름으로 아티스트를 찾을 때 두 건이 나와 어느 쪽인지 판단할 수 없다.

- 등록 — 대표명과 별칭 모두 양쪽 테이블을 조회
- 수정 — `...AndIdNot` 변형을 써서 자기 자신은 제외. 전부 검사하면 기존 값을 다시 보낼 때마다 409가 난다
- 수정 시 이름만 바꿔 자기 별칭과 같아지는 경우 — 그 별칭을 제거한다. `otherNames`를 함께 보낸 경우는 정규화 단계가 이미 걸러낸다

대소문자는 구분한다. `LOWER()` 유니크 인덱스가 필요해 마이그레이션이 붙는 일이라 별도로 다룬다.

#### 목록 검색어 파라미터의 타입 캐스팅

검색어 없이 목록을 조회하면 500이 났다.

```
ERROR: function lower(bytea) does not exist
```

`'%' || ? || '%'`에서 `?`가 `null`이면 Postgres가 파라미터 타입을 정하지 못해 `bytea` 연결로 해석하고,
`lower(bytea)`라는 없는 함수를 찾는다. JPQL에서 `CAST(:q AS String)`으로 타입을 명시해 해결했다.

검색어 없이 목록을 여는 것이 가장 흔한 요청이라 관리자 화면 첫 진입부터 실패하는 상태였다.
컴파일도 통과했고 목 기반 테스트도 전부 통과한 상태에서 실제 Postgres 테스트만 잡아냈다.

#### 부분 수정 메서드 일원화

`Artist`의 부분 수정을 #43에서 추가된 `update(name, genre, instagramUrl, needsReview)` 하나로 합쳤다.
처음에는 필드별 변경 메서드 4개로 구현했으나, 같은 목적의 메서드가 둘이 되면
어느 쪽을 쓰느냐에 따라 `null` 처리가 달라진다.

판정은 엔티티가 한다 — `null`은 미전송, 빈 문자열은 비우기, 값은 변경.
서비스는 검증과 별칭 처리만 맡는다.

### 📌 참고사항

**범위 밖으로 둔 것**

- 아티스트 병합(`POST /admin/artists/merge`)과 병합 후보 조회는 #36으로 분리했다.
  되돌릴 수 없는 작업이라 확인 절차를 따로 정해야 한다
- 요청 본문의 잘못된 열거값이 400이 아니라 500으로 나간다.
  `HttpMessageNotReadableException` 핸들러가 없어서이며, 쿼리 파라미터는 막았고 본문은 후속으로 둔다
- 대표명과 별칭의 대소문자 교차 중복

**집계 뷰**

출연 횟수는 조회 시점에 계산한다. 집계 뷰(`artist_stat`)가 아직 없어
주최 목록이 축제 수를 세는 것과 같은 방식으로 처리했다.
뷰가 만들어지면 정렬에 쓰는 `JpaSort.unsafe`를 걷어낼 수 있다 —
집계값이 조회 전용 엔티티의 실제 필드가 되기 때문이다.

**헬스 엔드포인트 테스트**

`HealthEndpointSecurityTest`는 JPA 자동설정을 끄고 리포지토리를 목으로 하나씩 열거한다.
이번에 리포지토리 2개가 늘어 목을 추가했는데, 구조상 리포지토리를 새로 만들 때마다 같은 자리에서 깨진다.
