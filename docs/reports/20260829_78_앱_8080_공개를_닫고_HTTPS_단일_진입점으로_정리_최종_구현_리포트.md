# 앱 8080 공개 차단과 HTTPS 단일 진입점 정리 최종 구현 리포트

## 작업 개요

Issue #78과 PR #94를 통해 배포 서버의 앱 포트 8080을 루프백 인터페이스에만 바인딩하고, 외부 요청은 Caddy가 TLS를 종료하는 HTTPS 경로로만 받도록 정리했다. 이에 맞춰 GitHub Actions CD에서 공개 8080을 직접 호출하던 외부 헬스 체크를 제거하고, 서버 내부 앱 검사와 공개 HTTPS 검사의 역할을 분리했다.

이 리포트는 PR 초안이 아니라 최신 `develop`의 merge commit `15ef1f45fbf2fd8275485d459fd1c1b5cf25975e`에 반영된 파일, 최종 review thread, merge 후 CD와 실제 외부 요청 결과를 기준으로 작성했다.

- 관련 Issue: #78
- 관련 PR: #94
- 최종 PR head: `e27a4850838ee7d6eb028d7464506ed2ec82a830`
- develop merge commit: `15ef1f45fbf2fd8275485d459fd1c1b5cf25975e`

## 구현 범위

- 배포용 Compose의 앱 포트 바인딩을 `8080:8080`에서 `127.0.0.1:8080:8080`으로 변경
- 인터넷에서 평문 HTTP로 앱 8080에 직접 접근하는 경로 차단
- Compose 내부 Caddy의 `app:8080` reverse proxy 경로 유지
- 배포 서버 내부 `localhost:8080` health check와 앱 이미지 자동 롤백 유지
- GitHub Actions 러너가 `$OCI_HOST:8080`을 호출하던 외부 헬스 체크 제거
- 공개 서비스 경로의 `HTTPS 서빙 확인`을 통과한 뒤에만 정상 이미지를 기록하는 순서 유지

애플리케이션 코드, API 계약, DB 스키마와 로컬 개발용 Compose는 변경하지 않았다.

## 외부 진입점 정리

`deploy/compose.yaml`의 앱 서비스는 호스트의 모든 인터페이스가 아니라 `127.0.0.1:8080`에만 게시된다. 따라서 서버 자신의 `localhost:8080` 요청은 계속 동작하지만 외부 클라이언트는 서버 IP의 8080으로 직접 접속할 수 없다.

Caddy는 호스트 포트 바인딩을 사용하지 않고 Compose 네트워크에서 `app:8080`으로 접근하므로 영향이 없다. 공개 요청 경로는 다음 하나로 정리됐다.

`https://api.every-festa.com:443` → Caddy TLS 종료 → Compose 네트워크 `app:8080`

이 변경으로 관리자 로그인 요청의 아이디와 비밀번호가 평문 HTTP 8080을 통해 전송될 수 있던 경로가 제거됐다.

## CD health check와 롤백 구조

변경 전에는 앱을 세 경로에서 확인했다.

1. 배포 서버 내부 `http://localhost:8080/actuator/health`
2. GitHub Actions 러너의 `http://$OCI_HOST:8080/actuator/health`
3. 공개 도메인의 `https://api.every-festa.com/actuator/health`

8080을 루프백에만 바인딩하면 2번은 반드시 실패하므로 PR #94에서 제거했다. 최종 구조는 다음과 같다.

- `컨테이너 재기동`: SSH로 실제 `$OCI_HOST`에 접속해 `localhost:8080`을 검사한다. 실패하면 로그를 출력하고 `.last-successful-image`로 자동 롤백한다.
- `HTTPS 서빙 확인`: 공개 도메인을 통해 인증서, 443, Caddy와 앱 연결을 검사한다. 실패하면 배포를 실패 처리하지만 앱 이미지는 롤백하지 않는다.
- `정상 배포 이미지 기록과 정리`: 위 두 검사가 모두 성공한 뒤에만 새 이미지를 정상 이미지로 기록한다.

HTTPS 계층 장애는 앱 이미지를 되돌려도 해결되지 않으므로 HTTPS 검사 실패 시 롤백하지 않는 기존 #68의 판단을 유지했다. 제거된 외부 8080 검사가 갖던 두 번째 자동 롤백 경로는 사라졌지만, 실제 배포 대상 앱의 기동과 롤백은 서버 내부 검사로 계속 보장된다.

## 리뷰 반영 내용

### HTTPS 검증 대상과 실제 배포 대상의 분리 가능성

- 지적: `HTTPS 서빙 확인`은 `$OCI_HOST`가 아니라 DNS가 가리키는 서버를 검사한다. 향후 `main`이 A1에 배포되고 도메인이 E2를 가리키면 A1의 443이 실패해도 E2의 200 응답으로 배포가 성공할 수 있다.
- 확인: 현재 GitHub Environment는 `development` 하나이며 CD 이력은 모두 `develop` 배포다. `production` Environment는 없고 `OCI_HOST`·`OCI_USER`·`OCI_SSH_PRIVATE_KEY`는 저장소 레벨 시크릿이다. 현재 DNS `api.every-festa.com`과 개발 배포 대상은 E2 `161.33.7.55`로 일치한다.
- 현재 PR 판정: 실제 배포 대상 앱은 SSH 내부 `localhost:8080` 검사로 계속 검증되고, 현 단일 환경에서는 공개 HTTPS 검사 대상도 같은 E2다. 따라서 #78 범위의 차단 사유는 아니다.
- 후속 분리: A1/production 도입 시 필요한 환경별 시크릿·도메인·Caddy·DNS와 `curl --resolve` 검증을 Issue #99로 분리했다.

리뷰어는 위 답변과 Issue #99의 완료 조건을 확인한 뒤 현재 PR 범위에서는 진행 가능하다고 답변하고 review thread를 정리했다. 코드 수정이 아니라 현재 환경의 검증과 후속 작업 분리로 반영된 리뷰다.

## 후속 Issue #99

Issue #99 `A1 프로덕션 배포 서버 온보딩`은 다음 항목을 한 전환 작업으로 묶는다.

- `development`와 `production` Environment별 OCI 접속 시크릿 분리
- production Environment와 `DEPLOY_ENABLED` 및 앱 시크릿 구성
- Caddy 도메인 하드코딩을 `PUBLIC_DOMAIN` 환경 변수로 전환
- 환경별 `PUBLIC_BASE_URL`과 DNS 전환
- HTTPS 검사에 `--resolve "$PUBLIC_DOMAIN:443:$OCI_HOST"`를 적용해 연결 대상을 방금 배포한 서버로 고정
- A1의 443을 차단했을 때 E2가 대신 200을 반환하지 않고 검사가 실패하는지 확인

이 항목들은 A1 프로비저닝, 인증서 발급, DNS와 시크릿 전환 순서가 서로 의존한다. 현재 E2 단일 환경에서는 `--resolve`만 먼저 넣어도 동작 차이가 없으므로 #94에 부분 반영하지 않고 #99에서 함께 처리하는 것이 적절하다.

서버 방화벽과 OCI VCN Security List의 8080 인그레스 규칙 제거도 코드 밖 후속 작업이다. Compose 바인딩만으로 현재 외부 접근은 차단됐지만, 인그레스 규칙을 남기면 다른 프로세스가 향후 8080을 게시할 때 다시 노출될 수 있다.

## 제한사항 및 후속 작업

- 현재 HTTPS 검사는 DNS가 가리키는 서버를 확인하며 `$OCI_HOST`에 연결 대상을 강제하지 않는다. E2 단일 환경에서는 일치하지만 A1 도입 전에 Issue #99를 완료해야 한다.
- `production` Environment와 A1 배포 경로는 아직 없다. 현재 CD 실행은 `develop`→E2뿐이다.
- 서버 방화벽과 OCI VCN Security List의 8080 인그레스 규칙은 저장소 밖에서 별도로 제거해야 한다.
- HTTPS 검사 실패는 앱 이미지를 자동 롤백하지 않는다. TLS·Caddy·DNS 문제는 앱 이미지 롤백으로 복구되지 않는다는 기존 정책이다.
- 443이 장애 나면 외부 8080 우회 경로가 없으므로 SSH로 서버에 직접 접속해 복구해야 한다.
