### 📌 작업 개요

사용자용 아티스트 조회 API 두 개를 추가했다 — `GET /api/artists`(목록)와
`GET /api/artists/{id}`(상세). 인증이 없다.

프론트의 아티스트 목록·상세 화면은 이미 완성돼 있었는데 백엔드에 대응 API가 없어
MSW 목에 기대고 있었다. 그 자리를 실물로 바꾼 작업이다.

**작업이 리네임을 함께 안고 있었다.** `develop`의 `ArtistService`는 이름과 달리
관리자 CRUD 전용이었다. 공개 조회 서비스와 이름이 정면으로 부딪히므로,
#57이 정한 `<도메인>AdminService` 규칙을 Artist에도 적용해 `ArtistAdminService`로 옮기고
빈 이름을 공개 서비스가 가져갔다.

### 🎯 구현 목표

- 목록은 검색(`q`) · 장르 필터 · 정렬(`APPEARANCES` 기본 / `NAME`)과 페이지네이션
- 집계와 노출은 **발행된 축제만** 쓴다. 미발행은 어디에도 드러나지 않는다
- 「오늘」을 주입된 `Clock` + `Asia/Seoul`로 한 번 계산해 쿼리에 넘긴다 — `CURRENT_DATE` 금지
- 상세는 예정 공연·출연 이력을 각각 최대 5건 + 자르기 전 `total`

#### 목록 조회 쿼리

- **파일**: `artist/repository/ArtistRepository.java`(+86),
  `artist/repository/ArtistRecentFestivalRow.java`

- **이유**: 정렬이 `ORDER BY`에만 반영되므로 두 벌로 두었고, 최근 축제를 아티스트마다 조회하면
  페이지 크기만큼 쿼리가 늘어난다

별칭 검색을 **`JOIN`이 아니라 `EXISTS` 서브쿼리**로 썼다.

```sql
AND (:q IS NULL
     OR LOWER(a.name)  LIKE ... ESCAPE '\'
     OR EXISTS (SELECT 1 FROM ArtistAlias al WHERE al.artist = a AND LOWER(al.name) LIKE ...))
```

별칭 테이블을 조인하면 별칭이 3개인 아티스트가 결과에 3번 나오고 `totalElements`도 그만큼 부푼다.
`EXISTS`는 행을 늘리지 않는다. `ESCAPE`를 지정해 검색어의 `%` · `_`가 와일드카드로 새지 않게 했다.

출연 수는 `COUNT(DISTINCT f)`다 — 같은 축제에 이틀 출연해도 1회로 센다.
발행·종료 조건은 `LEFT JOIN`의 `ON` 절에 두어, 조건에 맞는 출연이 없어도
아티스트가 목록에서 사라지지 않고 `appearanceCount: 0`으로 남는다.

#### 라인업 `day` 범위 검증

- **파일**: `importer/service/ImportPreviewService.java`(+34)

  `LINEUP_DAY_OUT_OF_RANGE` blocker

`performanceDate <= endDate`를 함께 확인해 이미 저장된 행에도 방어가 걸린다.

### 🧭 결정 기록 (ADR)

#### `page` · `size`를 `String`으로 받아 직접 파싱

- **문제**: `int`로 선언하면 `?page=abc`에서 스프링이 타입 변환 예외를 던진다.
  이슈를 쓸 당시 그 예외를 받는 핸들러가 없어 **공통 에러 형식이 아니라 500**으로 나갔다
- **선택**: `String`으로 받고 컨트롤러에서 파싱해 `INVALID_PAGE` · `INVALID_PAGE_SIZE`를 던진다
- **대안**: 전역 핸들러를 추가 — 이슈가 명시적으로 **소유 범위 밖**으로 선을 그었다.
  Artist·Lineup 범위를 넘어 전역 예외 정책을 임의로 바꾸지 않기로 했다
- **트레이드오프**: 타입이 계약을 말해주지 않아 시그니처만 봐서는 숫자인지 알 수 없고,
  같은 저장소의 다른 목록 API와 방식이 갈린다. 아래 참고사항 참조

#### 별칭 검색을 조인이 아니라 `EXISTS`로

- **문제**: 대표명과 모든 별칭을 함께 검색해야 하는데, 별칭은 1:N이다
- **선택**: `EXISTS` 서브쿼리
- **대안**: `LEFT JOIN ArtistAlias` — 별칭 수만큼 행이 늘어 **같은 아티스트가 여러 번 나오고
  `totalElements`가 부푼다.** `DISTINCT`로 덮으면 페이지 크기와 카운트가 또 어긋난다
- **트레이드오프**: 별칭 자체를 응답에 실을 수 없다. 목록은 별칭을 내리지 않으므로 문제가 없다

#### 「오늘」을 한 번 계산해 쿼리에 넘긴다

- **문제**: 기존 집계 쿼리가 `CURRENT_DATE`를 썼다. `ClockConfig`는 UTC이고 DB 타임존은
  고정돼 있지 않아 **KST 00~09시에 하루가 어긋난다**
- **선택**: 주입된 `Clock` + `Asia/Seoul`로 한 번 구해 `:today` 파라미터로 넘긴다
- **대안**: DB 타임존 고정 — 인프라 설정에 의존하게 되고 테스트에서 고정할 수 없다
- **트레이드오프**: 없음에 가깝다. 한 요청 안에서 목록 집계 · 예정 · 이력이 **같은 기준일**을 쓴다
- ⭐ **볼트 승격 권장** — 날짜 경계를 KST로 못박는 규칙이고 다른 공개 API도 같은 함정을 밟는다

#### `day` 검증을 조회가 아니라 임포트에 넣는다

- **문제**: `day`가 축제 기간을 넘으면 상세가 이상한 날짜를 만든다
- **선택**: 임포트 미리보기에서 blocker로 막는다. 이슈의 소유 범위 밖이지만 원천이 거기다
- **대안**: 조회에서만 걸러내기 — 잘못된 행이 DB에 계속 쌓이고, 그 행을 쓰는 다음 화면이
  같은 문제를 다시 만난다
- **트레이드오프**: 이 PR이 임포트 코드를 건드린다. 조회 쪽 방어도 함께 남겨 이미 저장된 행을 덮었다

### 📌 참고사항

**`imageUrl`은 목록·상세 모두 항상 `null`이다.**
`ArtistListItemResponse.from()`과 상세 응답 조립 양쪽에서 `null`이 하드코딩돼 있다.
`Artist` 엔티티에는 `imageUrl` 컬럼이 있고 임포트가 값을 채우는데도 API로는 나가지 않는다.

**이것은 누락이 아니라 결정과 일치한다.** DEC-0063이 *"아티스트 얼굴 사진·공식 사진·앨범 커버를
화면에 쓰지 않는다"*, *"아티스트 프로필 자리는 기본 이미지(플레이스홀더)로 채운다"*로 정했다.
저작권·초상권 축을 함께 눕히기 위한 판정이다.

**다만 이슈 본문은 그 사실을 적지 않았다.** 목록 항목과 상세 최상위 계약에 `imageUrl`이
그냥 들어 있어, 프론트가 값이 올 것으로 기대하기 쉽다. 필드를 남긴 채 항상 `null`을 내는 것이
의도라면 계약에 「항상 `null`, 플레이스홀더는 프론트가 갖는다」가 적혀야 한다.

**`page` · `size`가 필수다 — 이 저장소의 다른 목록 API와 다르다.**
생략하면 기본값이 아니라 `INVALID_PAGE` · `INVALID_PAGE_SIZE` 400이 나간다
(`Integer.parseInt(null)`이 그대로 예외를 던진다). 반면 관리자 커버리지·임포트 이력은
`@RequestParam(defaultValue = "0"/"20")`으로 생략을 허용하고, 관리자 주최 목록은 `Pageable`을 받는다.
**같은 서비스의 목록 API 넷이 페이지 파라미터를 세 가지 방식으로 다룬다.**

**이슈가 전제한 「전역 변환 핸들러 미연결」은 그 사이 해소됐다.**
이슈 본문은 *"`INVALID_PATH_VARIABLE`의 전역 변환 핸들러가 아직 실제로 연결돼 있지 않다"*며
`String` 파싱을 택한 근거로 삼았는데, 현재 `develop`의 `GlobalExceptionHandler`에는
`MethodArgumentTypeMismatchException` 핸들러가 있다(이 PR이 넣은 것은 아니다).
그래서 `/api/artists/abc`는 실제로 `INVALID_PATH_VARIABLE` 400을 낸다 —
상세는 `@PathVariable Long id`를 그대로 쓰고도 계약을 지킨다.
**목록의 `String` 파싱은 이제 없어도 되는 우회로가 됐다.** 정리할지는 별도 판단이다.

**임포트 코드 변경은 이슈의 소유 범위 밖이다.**
`ImportPreviewService`는 이슈가 나열한 소유 범위(`ArtistRepository` · `LineupRepository` ·
`ArtistErrorCode` · `artist/*`)에 없다. 상세 계약을 지키기 위한 원천 방어이므로 방향은 타당하나,
리뷰어가 임포트 회귀를 함께 봐야 하는 PR이 됐다.

- **출연 이력은 축제 단위로 접힌다.** 같은 축제에 이틀 출연해도 이력에는 한 줄이고,
  `total`도 접은 뒤의 수다. 목록의 `appearanceCount`가 `COUNT(DISTINCT f)`인 것과 같은 기준이다
- **예정 공연은 접지 않는다.** 같은 축제의 1일차·3일차에 서면 두 줄이 나온다.
  「언제 보러 가면 되나」가 예정의 질문이라 접으면 정보가 사라진다
- 프론트 목이 예정/과거를 모두 `performanceDate`로 가르는 것과 달리, 구현은 정본 문서 계약대로
  이력을 `festival.endDate < 오늘`로 가른다. 이슈가 *"임의로 새 기준을 만들지 않는다"*고
  명시한 자리이며, 연동 시 함께 확인해야 한다
