# 주최 목록 page·size 계약과 정렬 통일 최종 구현 리포트

## 작업 개요

Issue #102와 PR #103을 통해 `GET /api/admin/hosts`만 Spring `Pageable`을 직접 받던 구조를 다른 페이지네이션 목록 API와 같은 `page`·`size` 계약으로 통일했다. 기존에는 잘못된 범위가 조용히 기본값이나 Spring 상한으로 바뀌고, 정렬이 없어 페이지를 넘길 때 항목이 겹치거나 빠질 수 있었다.

이 리포트는 최신 `develop`의 merge commit `303409a6f3cc776806f0f8ebcc330178ab281796`에 반영된 코드, 최종 review thread와 GitHub Actions 결과를 기준으로 작성했다.

- 관련 Issue: #102
- 관련 PR: #103
- 최종 PR head: `d14b2c295a16b9f86b6333e9a339ecdc3b10218b`
- develop merge commit: `303409a6f3cc776806f0f8ebcc330178ab281796`

## 문제 분석

관리자 목록 API 6개 중 주최 목록만 `Pageable`을 컨트롤러에서 직접 받아 다음 계약이 어긋나 있었다.

- `size=1000`은 그대로 통과하고 `size=5000`은 Spring 상한 2000으로 축소돼 최대 2000건을 반환했다.
- `size=0`과 `page=-1`은 오류 없이 기본값으로 바뀌었다.
- Swagger가 `INVALID_PAGE`·`INVALID_PAGE_SIZE` 400을 문서화했지만 실제 서비스에는 대응 검증이 없었다.
- 정렬되지 않은 `Pageable`과 `ORDER BY` 없는 JPQL을 조합해 페이지 경계의 순서를 보장하지 못했다.
- 임의의 `sort` 프로퍼티가 Spring Data까지 전달될 수 있었다.

## 구현 범위

- `HostAdminController.findAll`의 `Pageable`을 `page`·`size` 요청 파라미터로 교체
- 기본값을 `page=0`, `size=20`으로 고정
- `HostAdminService.findAll`에 `page >= 0`, `size 1~50` 범위 검증 추가
- 서비스에서 `PageRequest.of(page, size)` 생성
- `HostRepository.findAllWithFestivalCount`에 `ORDER BY h.id DESC` 추가
- 임의 `sort` 파라미터를 목록 계약에서 제거
- 컨트롤러 기본값·전달값, 서비스 경계값, 실제 PostgreSQL 정렬·페이지 경계 테스트 추가

## 최종 API 계약

```http
GET /api/admin/hosts?page=0&size=20
```

| 항목 | 계약 |
| --- | --- |
| `page` | 기본값 0, 음수면 `INVALID_PAGE` 400 |
| `size` | 기본값 20, 1~50 밖이면 `INVALID_PAGE_SIZE` 400 |
| 정렬 | `host.id DESC` 고정 |
| `sort` | 별도 정렬 요구가 없어 받지 않음 |

정상 범위의 요청과 응답 DTO는 유지했다. 의도한 외부 동작 변경은 범위 밖 값을 200으로 보정하지 않고 400으로 거부하는 것이다.

## 구현 내용

### Controller 입력 계약 통일

- **파일**: `src/main/java/com/greedy/festa/host/controller/HostAdminController.java`
- **변경 내용**: `Pageable` 대신 `@RequestParam(defaultValue = "0") int page`, `@RequestParam(defaultValue = "20") int size`를 받는다.
- **이유**: 다른 관리자 목록과 같은 입력 모양을 사용하고 원본 숫자를 서비스 검증까지 보존한다.

### Service 범위 검증

- **파일**: `src/main/java/com/greedy/festa/host/service/HostAdminService.java`
- **변경 내용**: 음수 page는 `INVALID_PAGE`, 1~50 밖의 size는 `INVALID_PAGE_SIZE`로 거부하고 검증 후 `PageRequest`를 생성한다.
- **이유**: Swagger에 적힌 400 계약을 실제 동작으로 만들고 과도한 페이지 조회를 차단한다.

### Repository 고정 정렬

- **파일**: `src/main/java/com/greedy/festa/host/repository/HostRepository.java`
- **변경 내용**: 주최와 축제 수를 묶는 JPQL에 `ORDER BY h.id DESC`를 추가했다.
- **이유**: 등록 역순 문서 계약을 구현하고 `LIMIT`·`OFFSET` 페이지 사이에서 항목이 겹치거나 누락되는 문제를 막는다.

## 결정 기록 (ADR)

### 주최 목록 정렬을 id 내림차순으로 고정

- **문제**: 정렬이 없어 페이지 경계의 결과가 안정적이지 않고 Swagger의 "등록 역순" 설명과 달랐다.
- **선택**: 쿼리에 `ORDER BY h.id DESC`를 고정한다.
- **대안**: `HostAdminSortType`을 새로 만들어 `sort`를 공개한다.
- **트레이드오프**: 호출자가 다른 정렬을 선택할 수 없지만 현재 요구가 없는 정렬 어휘와 검증 분기를 만들지 않는다.

## 리뷰 논의 및 반영 내용

### 숫자가 아닌 page·size의 500 응답

- 지적: `page`·`size`를 `int`로 받으면 `?page=abc`·`?size=abc`가 서비스에 도달하기 전에 `MethodArgumentTypeMismatchException`을 내며, 현재 전역 처리에서는 쿼리 파라미터 타입 불일치가 500이 된다.
- 판정: 주최 목록만의 문제가 아니라 같은 형태의 모든 목록 API에 공통인 전역 계약 문제라 PR #103 범위에서 부분 수정하지 않았다.
- 후속: Issue #114 「쿼리 파라미터 타입 불일치가 기본 500이라, 400은 목록마다 손으로 붙이고 있다」로 분리했다.

그 외 리뷰 finding은 없으며, 구현 코드 변경을 요구한 리뷰 항목도 없다.
