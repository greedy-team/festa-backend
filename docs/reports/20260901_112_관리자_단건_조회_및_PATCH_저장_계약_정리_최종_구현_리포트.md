# 관리자 단건 조회 및 PATCH 저장 계약 정리 최종 구현 리포트

## 작업 개요

Issue #112와 PR #113을 통해 Festival·Lineup·Host·Artist 네 도메인에 관리자 단건 조회(`GET .../{id}`)를 추가하고, PATCH에서 값을 비우거나 보내지 않았을 때의 동작을 도메인마다 통일했다. 기존에는 도메인별로 필드 생략·명시적 `null`·빈 문자열의 취급이 갈려 있어 프론트가 저장 결과를 예측하기 어려웠다.

이 리포트는 최신 `develop`의 merge commit `7ee4d2714273201caa0d1db91c7dfbe67e512927`에 반영된 코드, 최종 review thread와 GitHub Actions 결과를 기준으로 작성했다. 구현 도중 #111(Festival·Lineup 관리자 CRUD 추가)이 먼저 병합되면서 이 브랜치의 Festival/Lineup 관련 구현이 한 번 갈아엎어졌는데, 그 중간 상태는 반영하지 않았다.

- 관련 Issue: #112
- 관련 PR: #113
- 최종 PR head: `fcfc79e62c0570fefc46390b7bd60f51e2acdf05`
- develop merge commit: `7ee4d2714273201caa0d1db91c7dfbe67e512927`

## 문제 분석

- 관리자 수정 화면은 현재 값을 먼저 불러온 뒤 통째로 고쳐 저장해야 하는데, 단건 조회 API가 Artist·Host·Festival·Lineup 중 하나도 준비돼 있지 않았다.
- Artist·Host의 기존 PATCH는 "보내온 항목만 반영"하는 부분 수정이었고, Festival·Lineup은 이 브랜치 작업 중 #111이 별도로 "전체 교체" 구조를 확정해 병합했다 — 같은 저장소 안에 두 가지 PATCH 철학이 공존할 뻔했다.
- Festival은 문자열 필드만 명시적 `null`을 400으로 막고 `latitude`·`externalVisitor` 같은 비-문자열은 `null`을 조용히 삭제로 받아, 같은 요청 안에서 `description: null`은 튕기고 `latitude: null`은 지워지는 모순이 있었다.
- Artist·Host는 초안 단계에서 `instagramUrl`에 생략은 400·명시적 `null`은 삭제라는 3-상태 구분을 뒀는데, 이를 구현하려고 되살린 presence 플래그·`@JsonIgnore` 게터가 실제로는 결과에 영향을 주지 않는 경우가 대부분이었다.
- Festival·Lineup의 단건 조회 응답(`FestivalAdminDetailResponse`, `LineupAdminDetailResponse`)이 목록/생성/수정 응답과 다른 DTO였다.

## 구현 범위

- Festival·Lineup·Host·Artist 관리자 단건 조회 4종 추가
- Festival: `FestivalRepository.findDetailById`(host `LEFT JOIN FETCH`) 추가, `FestivalResponse`에 `hostName`·`lineupCount` 추가로 GET·POST·PATCH 응답 통합
- Lineup: `LineupResponse`에 `festivalName`·`artistName` 추가로 GET·POST·PATCH 응답 통합
- Artist·Host의 `*UpdateRequest`를 presence 플래그·`@JsonIgnore` 없는 plain record로 정리
- Artist·Host의 PATCH를 "생략과 명시적 null을 구분하지 않는다"로 통일
- Artist entity `update()`의 도달 불가능한 `name` null 가드와 사용되지 않던 `instagramUrl` 파라미터 제거, `changeInstagramUrl()`로 역할 분리
- Host `update()`의 필드별 `if (xxx != null)` 조건부 반영을 전부 제거해 모든 필드를 무조건 반영하도록 통일
- Swagger 설명을 최종 코드 계약과 재대조해 필수/삭제/유지 규칙과 시크릿 게스트 응답 계약을 명시

Festival·Lineup의 core PATCH 로직(엔티티 `update()`, `*UpdateRequest`)은 #111에서 이미 "생략·null 모두 삭제, 필수만 400"으로 확정돼 있었다 — 이 PR에서 다시 건드리지 않고 그대로 재사용했다. 이 PR이 Festival·Lineup에 실제로 더한 것은 단건 조회와 응답 DTO 통합뿐이다.

## 최종 계약

### 관리자 단건 조회

| 대상 | 엔드포인트 | 응답 DTO | 404 |
| --- | --- | --- | --- |
| Festival | `GET /api/admin/festivals/{id}` | `FestivalResponse`(POST·PATCH와 공유) | `FESTIVAL_NOT_FOUND` |
| Lineup | `GET /api/admin/festivals/{festivalId}/lineups/{lineupId}` | `LineupResponse`(POST·PATCH와 공유) | `LINEUP_NOT_FOUND`(그 축제의 라인업이 아니어도 404) |
| Host | `GET /api/admin/hosts/{id}` | `HostResponse`(기존 응답 재사용) | `HOST_NOT_FOUND` |
| Artist | `GET /api/admin/artists/{id}` | `ArtistResponse`(기존 응답 재사용) | `ARTIST_NOT_FOUND` |

Import 관련 리소스와 AdminAuth는 일반 관리자 수정 CRUD가 아니므로 대상에서 제외했다. Lineup의 경로는 이슈 본문의 `GET /api/admin/lineups/{id}`가 아니라 기존 중첩 경로(`/api/admin/festivals/{festivalId}/lineups/{lineupId}`) 그대로 확정됐다 — Lineup은 festival 없이 단독으로 존재할 수 없어 다른 CRUD 엔드포인트와 경로 모양을 맞췄다.

Artist·Host는 기존 CRUD 응답(`ArtistResponse`·`HostResponse`)을 그대로 재사용했고, Festival·Lineup은 단건 조회 전용 DTO(`FestivalAdminDetailResponse`·`LineupAdminDetailResponse`)를 만드는 대신 #111의 `FestivalResponse`·`LineupResponse`에 부족했던 필드(`hostName`·`lineupCount`, `festivalName`·`artistName`)를 옮겨 하나로 합쳤다 — 같은 자원인데 GET과 PATCH의 응답 모양이 달라지는 문제를 피했다.

### Festival PATCH

| 구분 | 필드 | 값을 보냄 | 비우거나 생략함 |
| --- | --- | --- | --- |
| 필수 | `name`, `startDate`, `endDate`, `hostId` | 수정 | 400 |
| 선택 문자열 | `importKey`, `posterUrl`, `description`, `venueName`, `address`, `admissionNote`, `instagramUrl` | 수정 | 삭제 |
| 선택 비문자열 | `latitude`, `longitude`, `ticketOpenAt`, `externalVisitor`, `verification`, `ticketType` | 수정 | 삭제 |

발행된 축제는 예외다 — `latitude`·`longitude`를 비우면 `FESTIVAL_PUBLISHED_COORDINATES_REQUIRED`(409)로 막는다.

### Lineup PATCH

| 필드 | 값을 보냄 | 비우거나 생략함 |
| --- | --- | --- |
| `day`, `displayOrder` | 수정(1 미만·축제 기간 밖이면 400) | 400 |
| `artistId` | 해당 Artist로 수정 | 시크릿 게스트로 저장(응답의 `artistId`·`artistName`도 `null`) |

### Artist PATCH

| 필드 | 값을 보냄 | 비우거나 생략함 |
| --- | --- | --- |
| `name` | 수정 | 400 |
| `instagramUrl` | 수정 | 삭제 |
| `otherNames` | 배열 전체로 교체 | `[]`이면 전체 삭제, 생략하거나 `null`이면 기존 별칭 유지 |
| `genre`, `needsReview` | 수정 | 기존 값 유지 |

### Host PATCH

| 필드 | 값을 보냄 | 비우거나 생략함 |
| --- | --- | --- |
| `name`, `region` | 수정 | 400 |
| `instagramUrl`, `shortName`, `logoUrl`, `bannerUrl`, `homepageUrl` | 수정 | 삭제 |

네 표 모두 최종 merge 코드(`ArtistAdminService`·`HostAdminService`·`FestivalAdminService`·`LineupAdminService`, 각 entity의 `update()`/`change*()`)와 대조해 확인했다.

## 구현 내용

### Festival·Lineup 단건 조회 — #111 CRUD 위에 얹기

- **파일**: `FestivalAdminService.java`, `FestivalRepository.java`, `LineupAdminService.java`
- **변경 내용**: `FestivalAdminService.findOne()`은 `findDetailById`(host `LEFT JOIN FETCH`)로 조회해 `FestivalResponse.of(festival, lineupRepository.countByFestivalId(id))`를 반환한다. `LineupAdminService.findOne()`은 기존 `findByIdAndFestivalId`를 그대로 재사용해 `festivalId` 불일치를 404로 걸러낸다.
- **이유**: #111이 이미 만든 `update()`·`create()`·`delete()`와 리포지토리 조회 관용구를 다시 만들지 않고, 조회 한 메서드만 얹었다.

### FestivalResponse·LineupResponse 응답 통합

- **파일**: `FestivalResponse.java`, `LineupResponse.java`
- **변경 내용**: `FestivalResponse`에 `hostName`(호스트 없으면 `null`), `lineupCount`를 추가했다. `LineupResponse`에 `festivalName`, `artistName`(시크릿 게스트면 `null`)을 추가했다.
- **이유**: 리뷰에서 "단건 조회 전용 DTO를 새로 만들면 같은 자원의 GET과 PATCH 응답 모양이 달라진다"는 지적을 받아, 전용 DTO(`FestivalAdminDetailResponse`, `LineupAdminDetailResponse`) 대신 기존 응답에 부족한 필드를 옮기는 쪽을 택했다.

### Artist·Host UpdateRequest — plain record로 되돌리기

- **파일**: `ArtistUpdateRequest.java`, `HostUpdateRequest.java`
- **변경 내용**: 생략 여부를 추적하던 `*Present` boolean 필드, 커스텀 setter, `@JsonIgnore`/`@Schema(hidden = true)` 게터를 전부 제거하고 필드 선언만 있는 record로 되돌렸다.
- **이유**: 리뷰에서 `!isNamePresent() || name() == null` 같은 조건이 앞 조건이 항상 뒤 조건을 함의해 실질적인 분기가 아니라는 지적을 받았다. `instagramUrl`처럼 정말 생략/명시적 null을 구분해야 했던 필드도, 이후 "구분 자체를 없앤다"는 결정으로 플래그가 필요 없어졌다.

### Artist·Host update() — 무조건 반영으로 통일

- **파일**: `Artist.java`, `ArtistAdminService.java`, `Host.java`(변경 없음, 기존 `change*()` 재사용), `HostAdminService.java`
- **변경 내용**: `HostAdminService.update()`는 `name`·`region`·`shortName`·`logoUrl`·`bannerUrl`·`instagramUrl`·`homepageUrl` 7개 필드 전부에 걸려 있던 `if (request.xxx() != null)` 조건을 제거하고 매번 무조건 반영한다. `Artist.update()`는 도달할 일이 없던 `if (name != null)` 가드와 쓰이지 않던 `instagramUrl` 파라미터를 제거했다.
- **이유**: `HostAdminService.update()`가 이미 이름 검증(`validateName`)에서 `null`을 걸러낸 뒤 호출하므로 엔티티의 가드는 항상 참인 조건이었다. `Artist.update()`도 서비스가 `request.name()`이 `null`이면 400을 던진 뒤에만 호출해, 엔티티에 도달하는 `name`은 항상 값이 있다.

### 시크릿 게스트 nullable 계약 명시

- **파일**: `LineupAdminController.java`
- **변경 내용**: `@Tag` 설명에 "artistId를 비우면 시크릿 게스트이며 자리는 유지되고, 응답의 artistId·artistName도 null이다"를 추가했다.
- **이유**: 기존 설명은 요청 쪽(`artistId`를 비우면 시크릿 게스트) 계약만 있었고, 응답에서 `artistId`·`artistName`이 `null`로 내려간다는 사실은 코드를 봐야만 알 수 있었다.

## 결정 기록 (ADR)

### PATCH에서 생략과 명시적 null을 구분하지 않는다

- **문제**: Festival은 문자열만 명시적 `null`을 400으로 막고 비-문자열은 `null`을 삭제로 받아, 같은 요청 안에서 `description: null`은 튕기고 `latitude: null`은 지워지는 모순이 있었다. Artist·Host도 초안 단계에서 `instagramUrl`에 "생략=400, 명시적 null=삭제"라는 3-상태 구분을 두고 있었다.
- **선택**: 모든 PATCH 필드에서 생략과 명시적 `null`을 같은 값으로 취급한다. 필수값은 두 경우 모두 400, 삭제 가능한 값은 두 경우 모두 삭제.
- **대안**:
  - 필드를 `JsonNode`로 받아 생략(자바 `null`)과 명시적 `null`(`NullNode`)을 구분 — 리뷰에서 제안됐으나, 구분이 실제로 필요한 자리가 없어 채택하지 않았다.
  - 필드별 `*Present` boolean 플래그 유지 — 대부분의 플래그가 실제 분기에 영향을 주지 않는다는 점이 리뷰에서 드러나 제거했다.
- **트레이드오프**: `instagramUrl`은 한동안 "생략은 400, 명시적 null은 삭제"라는 중간 계약을 거쳤으나, 최종적으로는 다른 삭제 가능 문자열과 같은 "생략·null·공백 모두 삭제"로 재통일됐다. 프론트가 필드를 아예 보내지 않아도 되게 됐지만, "선택값을 명시적으로 비웠다"와 "그냥 안 보냈다"를 서버가 구분해 다르게 반응할 수는 없다.
- ⭐ 볼트 승격 권장 — 이후 다른 도메인의 PATCH 설계 전체에 적용될 기준이다.

### Artist otherNames·genre·needsReview는 예외적으로 유지 계약을 쓴다

- **문제**: "필수는 400, 삭제 가능한 값은 삭제" 두 규칙만으로는 Artist의 모든 필드를 설명할 수 없었다. `otherNames`는 컬렉션이라 생략과 빈 배열의 의미가 다르고, `needsReview`는 DB `NOT NULL` 컬럼이라 애초에 `null`을 저장할 수 없다.
- **선택**: `otherNames`는 생략·`null`이면 기존 별칭 유지, `[]`이면 전체 삭제, 값이 있으면 그 배열로 교체한다. `genre`·`needsReview`는 생략·`null`이면 기존 값을 유지한다.
- **근거**: 이슈 #112 본문에 이 예외가 처음부터 명시돼 있었고, 구현·리뷰 전 과정에서 이 규칙 자체에 대한 이견은 없었다.
- 해당 없음 — 볼트 승격은 다른 도메인에 같은 모양(컬렉션 필드, NOT NULL 선택값)의 필드가 생길 때 판단.

## 리뷰 논의 및 반영 내용

### Festival·Lineup 수정 로직 중복

- 지적: `FestivalAdminService`·(당시 artist 패키지 안에 있던) `LineupAdminService`의 수정 로직이 #111과 중복이다. 수정 관련 결정은 #111 쪽으로 통일하는 게 좋겠다.
- 반영: 이 브랜치가 만들었던 Festival·Lineup 수정 구현을 전부 제거하고 #111의 `FestivalAdminService.update()`·`LineupAdminService.update()`를 그대로 사용했다. 이 PR에는 단건 조회 `findOne()`만 남겼다.

### FestivalUpdateRequest의 타입별 null 처리 차이

- 지적: 문자열만 명시적 `null`을 400으로 막아, 같은 요청에서 `latitude: null`은 삭제되고 `description: null`은 튕긴다. `latitude`·`externalVisitor` 같은 비-문자열 세터만 presence 플래그가 없어 필드명을 잘못 보내면 좌표가 조용히 지워지고 200이 나갈 수 있다.
- 반영: `FestivalUpdateRequest`의 `JsonNode`/presence 플래그 방식을 제거하고 #111의 plain record 구조로 교체해, 타입별 null 처리 차이와 presence 플래그 누락 문제를 함께 없앴다.

### FestivalAdminDetailResponse가 #111 FestivalResponse와 별개 DTO

- 지적: #111에 이미 `FestivalResponse`가 있어 그대로 두면 같은 축제인데 GET과 PATCH 응답 형태가 달라진다. `hostName`·`lineupCount`처럼 단건 조회 응답에만 있던 값을 옮겨 하나로 합치는 게 좋겠다.
- 반영: `FestivalAdminDetailResponse`를 제거하고 `hostName`·`lineupCount`를 `FestivalResponse`로 옮겨 GET·POST·PATCH가 같은 DTO를 쓰도록 정리했다.

### ArtistUpdateRequest·HostUpdateRequest의 무의미한 presence 플래그

- 지적: `!isNamePresent() || name() == null`은 앞 조건이 참이면 뒤 조건도 항상 참이라 `name() == null` 하나로 결과가 같다. `instagramUrl`, `LineupUpdateRequest`의 `dayPresent`·`displayOrderPresent`도 마찬가지다. 세 상태 구분이 꼭 필요하면 `JsonNode`를 컴포넌트로 쓴 record도 대안이 된다.
- 반영(1차): 실제 결과에 영향을 주지 않는 `namePresent` 등은 제거했다. `instagramUrl`은 생략=400·명시적 null=삭제를 구분해야 해서 presence 처리를 유지했다.
- 반영(2차, 최종): 이후 "생략과 명시적 null을 구분하지 않는다"로 원칙 자체를 넓히면서 `instagramUrl`의 presence 플래그도 마저 제거했다. 최종적으로 Artist·Host의 `*UpdateRequest`에는 presence 관련 코드가 전혀 남지 않았다.

### HostAdminService의 instagramUrl 400 vs region 400

- 지적: `instagramUrl`은 컬럼이 nullable이라 명시적 `null`도 삭제로 받는 게 맞는데 당시 400이었다. `region`은 `NOT NULL`이라 400이 맞지만 Swagger 설명에 region·shortName 규칙이 빠져 있었다.
- 반영: `instagramUrl`의 명시적 `null`을 삭제로 바꿨고, `region`의 400 계약은 유지한 채 Swagger 설명에 규칙을 채웠다. 이후 나머지 필드도 같은 "무조건 반영" 구조로 통일됐다.

### Artist entity update()의 쓰이지 않는 instagramUrl 파라미터

- 지적: `changeInstagramUrl()`이 새로 생기면서 `update()`의 `instagramUrl` 파라미터가 호출부에서 `null`만 받아 안쪽 `if` 블록이 실행될 일이 없다.
- 반영: 파라미터를 제거하고 인스타그램 URL 변경은 `changeInstagramUrl()`로 완전히 분리했다.

### LineupAdminController·LineupAdminDetailResponse 중복

- 지적: artist 패키지 안의 `LineupAdminController`도 #111과 중복이고, `LineupAdminDetailResponse`의 `festivalName`·`artistName`은 #111 `LineupResponse`에 없는 값인데 편집 화면에는 필요하다.
- 반영: artist 패키지의 `LineupAdminController`를 제거하고 생성·수정·삭제는 #111의 중첩 경로 컨트롤러(`lineup` 패키지)에 단건 조회만 추가했다. `festivalName`·`artistName`은 `LineupResponse`로 옮기고 `LineupAdminDetailResponse`는 제거했다.

리뷰에서 제기된 항목은 모두 최종 코드에 반영됐으며 의도적으로 미반영한 finding은 없다.

## Swagger 계약 정리

병합 이후 최종 코드를 다시 대조해 Controller·Request DTO·Response DTO·ErrorCode 전체를 점검했다.

- Festival 수정: "보낸 것이 전부이고 생략한 필드는 비워진다"는 기존 문구가 필수 필드(`name`·`startDate`·`endDate`·`hostId`)는 실제로 400이라는 사실을 감추고 있었다 — 필수/삭제 규칙을 분리해 명시했다.
- Lineup 등록·수정: `day`·`displayOrder`가 필수라는 점(생략·1 미만·기간 밖이면 400)을 명시하고, 시크릿 게스트일 때 응답의 `artistId`·`artistName`이 `null`이라는 점을 Tag 설명에 추가했다.
- Artist 등록: `name` 필수·400 규칙을 추가했다. Artist 수정: `otherNames`의 생략/`null`(유지)·빈 배열(전체 삭제)·값 있는 배열(교체) 3-way 계약을 구체화했다.
- Host 등록: 지금까지 비어 있던 `@Operation` description에 `name`·`region` 필수·400 규칙을 추가했다.
- `FestivalAdminDetailResponse`·`LineupAdminDetailResponse`·`*Present` 플래그·구 flat Lineup PATCH 경로·"생략은 400, 명시적 null은 삭제" 문구를 전체 소스에서 검색했고, 남아 있는 잔재는 없었다.
- 각 컨트롤러의 `@ApiResponse` 400/404/409 목록을 서비스 코드의 실제 `throw` 지점과 전부 대조했고 추가·제거할 항목은 없었다.

## 제한사항 및 후속 작업

- `LineupRepository.findDetailById`(festival·artist `JOIN FETCH`)는 이번에 추가됐지만 `LineupAdminService.findOne()`은 기존 `findByIdAndFestivalId`(fetch join 없음)를 그대로 쓴다 — 응답 매핑 시 `festival`·`artist`가 지연 로딩으로 각각 한 번씩 더 조회된다. 동작은 정확하지만 `findDetailById`가 실제로는 호출되지 않는 죽은 코드로 남아 있다.
- `HostAdminService.create()`는 `update()`와 달리 `shortName`·`logoUrl`·`bannerUrl`·`instagramUrl`·`homepageUrl`에 `blankToNull()`을 적용하지 않는다 — 등록 시 빈 문자열을 보내면 `null`이 아니라 `""`가 그대로 저장된다(Festival·Artist의 `create()`는 두 곳 다 정상 적용). 이번 범위는 PATCH 계약과 단건 조회라 create() 로직은 건드리지 않았다.
- 노션 API 명세와 에러 코드 표는 갱신하지 않았다 — 이 계약은 코드와 Swagger가 원본이다.
- DB 스키마, 인증·배포 설정, 프론트엔드 코드는 변경하지 않았다.
