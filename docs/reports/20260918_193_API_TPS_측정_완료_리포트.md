# API TPS 측정 완료 리포트

## 측정 목적

5차 데모데이 요구사항인 공개 API TPS를 측정했다. 모든 측정은 로컬 Docker Desktop의 독립된 app + PostgreSQL 17 환경에서만 수행했다. production 및 shared development에는 부하를 주지 않았다.

- 측정 대상 SHA: `450d093ef941a7c35289f1ed0800afca787a3d11`
- Docker Desktop: 29.7.2
- JVM: 21
- 시나리오: 기존 #191/#192 k6 `mixed` 시나리오와 고정 manifest/search corpus
- 방식: 단계별 warm-up 후 constant-arrival-rate 3분 본 측정

50 RPS는 목표 9,000건 대비 2,144건만 처리했다. 원본 k6 summary artifact는 exact dropped iterations를 보존하지 않으므로, 처리량 차이를 dropped iterations 수로 표현하지 않는다. 다만 목표 처리량 대비 명확한 미달, max VU 도달, threshold 실패 13건으로 과부하 상태를 확인했다.

| 5 | festival_upcoming | 108 | 43.86ms | 85.52ms | 104.46ms |
| 5 | festival_recent | 90 | 49.10ms | 98.33ms | 166.90ms |
| 5 | festival_list | 162 | 62.63ms | 185.44ms | 263.34ms |
| 5 | festival_detail | 108 | 16.76ms | 34.56ms | 55.68ms |

`search`는 5/10/50 RPS 모두 가장 높은 tail latency를 보였고, `artist_list`가 두 번째 주요 병목이었다. 5 RPS부터 두 endpoint의 p95가 초 단위였고, 10 RPS부터 다른 API까지 tail latency가 증가했다. 50 RPS에서는 전체 endpoint가 queueing 영향을 받아 수 초대 응답을 보였다.

## 해석과 범위

이번 결과는 **로컬 isolated Docker + 해당 fixture + mixed workload**에서 관측한 값이다. `11.460 TPS`를 서버 최대 TPS로 해석하지 않는다.

기존 k6 artifact만으로는 CPU, JVM GC, Hikari connection pool, PostgreSQL CPU/I/O 또는 개별 SQL 실행계획 중 무엇이 병목인지 단정할 수 없다. 그 원인 분리에는 별도 런타임 지표와 DB 관측이 필요하다.

기존 #192 BEFORE/AFTER 쿼리 비교 결과와 이번 TPS 결과는 목적과 측정 조건이 다르므로 혼동하지 않는다. raw k6 결과는 Git에 추가하지 않았다.
