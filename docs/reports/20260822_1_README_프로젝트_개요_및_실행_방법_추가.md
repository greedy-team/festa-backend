### 📌 작업 개요

`# FESTA` 한 줄뿐이던 `README.md`에 프로젝트 개요·기술 스택·로컬 실행 방법·협업 규칙을 추가했다.
저장소를 처음 여는 사람이 무엇을 하는 프로젝트이고 어떻게 띄우는지를 README 하나로 알 수 있게 하는 것이 목표였다.

### 🎯 구현 목표

- 프로젝트 한 줄 소개와 기술 스택 명시
- 로컬 실행 명령 안내
- 협업 규칙 안내

### ✅ 구현 내용

#### README 본문 작성

- **파일**: `README.md`
- **변경 내용**: 소개 문단, 기술 스택 목록, 로컬 실행 명령, 협업 규칙 절을 추가 (24줄)
- **이유**: 저장소에 진입점 문서가 없어 스택도 실행 방법도 코드를 읽어야만 알 수 있었다

기재한 스택은 Spring Boot 4.1 · Java 21, Gradle 9.6 (Kotlin DSL), Spring Data JPA · Spring Security · OAuth2 Client이다.
실행 명령은 `./gradlew bootRun`(애플리케이션 실행)과 `./gradlew build`(빌드 + 테스트) 두 개만 남겼다.

협업 규칙 절은 이슈 → 브랜치 → 커밋 → PR → 릴리스가 자동으로 이어진다는 흐름과, 그 흐름의 시작이
**이슈 생성**이라는 점을 먼저 적었다. 이슈를 만들면 봇이 브랜치명과 커밋 메시지를 댓글로 알려주기 때문이다.
이어서 세 줄로 요약했다 — 작업 브랜치는 `develop`에서 분기해 `develop`으로 PR, 브랜치명은 `타입_이슈번호_제목슬러그`,
배포는 `develop` → `main` PR로만.

### 🧭 결정 기록 (ADR)

#### 협업 규칙을 링크가 아니라 본문 요약으로 넣음

- **문제**: 이슈는 "협업 규칙 문서 링크"를 담으라고 했는데, 이 시점의 저장소에는 링크할 규칙 문서가 없었다.
  `TEAM-CONVENTIONS.md`는 이 작업보다 뒤인 이슈 #9에서 만들어진다
- **선택**: 규칙 문서를 기다리지 않고 README 본문에 3줄 요약을 직접 적었다
- **대안**:
  - 규칙 문서가 생길 때까지 협업 규칙 절을 비워둠 — README를 여는 사람이 가장 먼저 필요한 정보가 빠진다
  - README에 규칙 전문을 옮겨 적음 — 나중에 `TEAM-CONVENTIONS.md`가 생기면 같은 규칙이 두 곳에 복사돼 어긋난다
- **트레이드오프**: 요약본과 `TEAM-CONVENTIONS.md`가 갈라질 수 있다. 요약은 세 줄로 최소화하고
  상세는 규칙 문서에 맡기는 형태로 남겼다

### 🧪 테스트 및 검증

문서 변경이라 자동 검증 대상이 아니다. 기재한 `./gradlew bootRun` · `./gradlew build` 두 명령이
실제 동작하는지 확인하는 것으로 갈음했다.

### 📌 참고사항

- 이슈가 요청한 "협업 규칙 문서 링크"는 이 작업에서 링크가 아니라 요약으로 대체됐다.
  규칙 문서는 이슈 #9(`AGENTS.md` · `TEAM-CONVENTIONS.md`)에서 만들어졌다
- README 하단의 `AUTO-VERSION-SECTION`은 릴리스 워크플로우가 관리하는 영역이라 손대지 않았다
