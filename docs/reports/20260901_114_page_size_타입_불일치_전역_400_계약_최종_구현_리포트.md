# page·size 타입 불일치 전역 400 계약 최종 구현 리포트

## 작업 개요

Issue #114와 PR #115를 통해 Spring MVC 인자 바인딩 단계에서 발생하는 `page`·`size` 타입 불일치를 전역 예외 처리로 통일했다. 기존에는 `?page=-1`처럼 숫자로 바인딩된 뒤 서비스 범위 검증에 걸리는 요청은 400이었지만, `?page=abc`처럼 바인딩 자체가 실패하는 요청은 컨트롤러에 진입하지 못하고 500 `INTERNAL_SERVER_ERROR`로 응답할 수 있었다.

이 리포트는 최신 `develop`의 merge commit `f60d9b658a992f4634bb076bb8100cd16ffc303b`에 실제로 반영된 코드, Issue #114, PR #115 본문과 리뷰 반영 결과, GitHub Actions 결과를 기준으로 작성했다. PR 과정에서 사용 후 삭제한 일회용 probe는 최종 저장소의 영구 테스트와 구분해 기록했다.

- 관련 Issue: #114
- 관련 PR: #115
- 최종 PR head: `288f17fb91cd37bfd85140f0ad70e3479b015646`
- develop merge commit: `f60d9b658a992f4634bb076bb8100cd16ffc303b`

## 문제 분석

목록 API는 `page`와 `size`를 `int`로 받는다. 음수 `page`나 허용 범위 밖 `size`는 컨트롤러 진입 후 서비스 검증에서 `INVALID_PAGE`·`INVALID_PAGE_SIZE`로 변환되지만, 숫자가 아닌 값은 그보다 앞선 Spring MVC 바인딩 단계에서 `MethodArgumentTypeMismatchException`을 발생시킨다.

기존 `GlobalExceptionHandler`는 같은 예외 중 `@PathVariable` 타입 불일치만 `INVALID_PATH_VARIABLE` 400으로 처리하고, 쿼리 파라미터 타입 불일치는 catch-all 500으로 남겼다. 공개 Festival 목록은 컨트롤러 로컬 맵으로 `page`·`size`를 별도 처리하고, 공개 Artist 목록은 문자열을 직접 파싱하는 등 같은 계약이 API마다 다른 방식으로 보완돼 있었다. 그 결과 로컬 처리를 추가하지 않은 관리자 Festival·Artist·Import·Host 목록은 문서에는 400을 적고 실제 타입 불일치에는 500을 줄 수 있었다.

Controller별 처리는 새 목록이 생길 때마다 같은 분기를 빠뜨릴 수 있다. 반면 `page`와 `size`는 도메인과 무관하게 의미와 공통 에러 코드가 이미 같으므로 전역 핸들러가 맡는 것이 자연스럽다. 이는 `Pageable`을 API에 직접 노출하지 않고 명시적인 `page`·`size`를 받는 기존 결정과, 파라미터 오류를 구분 가능한 개별 코드로 반환하는 오류 계약을 실제 HTTP 바인딩 경계까지 완성한다.

## 최종 계약

| 입력 | 처리 위치 | 최종 응답 |
| --- | --- | --- |
| `?page=abc` | `GlobalExceptionHandler` | 400 `INVALID_PAGE` |
| `?size=abc` | `GlobalExceptionHandler` | 400 `INVALID_PAGE_SIZE` |
| `?page=-1` | 기존 서비스 범위 검증 | 400 `INVALID_PAGE` |
| 허용 범위 밖 `size` | 기존 서비스 범위 검증 | 400 `INVALID_PAGE_SIZE` |
| 정상 `page`·`size` | 기존 Controller → Service 흐름 | 기존 목록 응답 유지 |

에러 응답은 기존 공통 `ErrorResponse`를 사용하므로 `errorCode`·`message`·`status`·`instance` 네 필드 계약을 유지한다. 이번 변경은 관리자 전용 우회 처리가 아니라 `GlobalExceptionHandler`를 거치는 전체 API에 적용된다.

## 구현 내용

### GlobalExceptionHandler — 공통 page·size 분기

- **파일**: `src/main/java/com/greedy/festa/global/exception/GlobalExceptionHandler.java`
- **변경 내용**: `COMMON_QUERY_PARAM_ERROR_CODES`에 `page`→`CommonErrorCode.INVALID_PAGE`, `size`→`CommonErrorCode.INVALID_PAGE_SIZE`를 정의했다. `MethodArgumentTypeMismatchException` 처리 순서는 `@PathVariable` → 공통 쿼리 파라미터 → 처리되지 않은 타입 불일치로 확정됐다.
- **이유**: `page`·`size`는 목록 도메인이 달라도 같은 뜻과 에러 코드를 사용하므로 전역에서 안전하게 판정할 수 있다. 컨트롤러 메서드에 도달하기 전에 발생하는 예외라 서비스 검증만으로는 처리할 수 없다.

`@PathVariable` 타입 불일치는 기존처럼 400 `INVALID_PATH_VARIABLE`이다. `page`·`size`가 아닌 쿼리 파라미터는 전역에서 임의의 도메인 코드를 정하지 않는다. 예를 들어 `limit`은 Festival과 Artist가 서로 다른 코드를 사용하고, `published`·`needsReview`·`hostId`·`year`도 각 API의 의미가 다르다. 해당 컨트롤러에 로컬 처리가 있으면 그 계약을 따르고, 없으면 현재 코드상 500 `INTERNAL_SERVER_ERROR`로 남는다.

### FestivalController — 중복 공통 분기 제거

- **파일**: `src/main/java/com/greedy/festa/festival/controller/FestivalController.java`
- **변경 내용**: 로컬 `QUERY_PARAM_ERROR_CODES`에서 `page`·`size`를 제거했다. 로컬 `@ExceptionHandler` 자체와 `limit`·`hostId`·`year`·`artistId` 매핑은 유지했다. 로컬 맵이 모르는 파라미터는 주입된 `GlobalExceptionHandler`에 위임한다.
- **이유**: 공통 `page`·`size`만 전역 책임으로 옮기고, 도메인별 오류 코드가 필요한 Festival 파라미터의 기존 400 계약은 깨뜨리지 않기 위해서다.

따라서 "FestivalController의 로컬 타입 불일치 처리 전체 제거"가 최종 구현은 아니다. 중복된 `page`·`size` 두 항목만 제거됐고, 공개 Festival API의 나머지 타입 불일치 계약은 기존 로컬 처리로 유지된다.

### 로그 책임 정리

- 400으로 분류되는 경로 변수와 `page`·`size` 타입 불일치는 warn 레벨로 에러 코드, HTTP 메서드, URI, 파라미터 이름, 입력값을 남긴다.
- 처리되지 않은 타입 불일치는 error 레벨로 같은 요청 정보를 남기고 예외 스택트레이스도 유지한다.

이 예외는 컨트롤러 진입 전에 발생해 스택트레이스만으로 어느 API 요청인지 찾기 어렵다. 400 분기에서는 스택트레이스를 남기지 않으므로 요청 식별 정보를 전역 핸들러가 책임지도록 했다.

### Swagger 공통 설명

- **파일**: `src/main/java/com/greedy/festa/global/config/SwaggerConfig.java`
- **변경 내용**: OpenAPI `Info.description`에 숫자가 아닌 `page`·`size`는 각각 400 `INVALID_PAGE`·`INVALID_PAGE_SIZE`, 음수 `page`와 범위 밖 `size`도 같은 코드를 사용한다는 공통 설명을 추가했다.
- **이유**: 각 Controller의 400 응답 코드 나열만으로는 타입 불일치와 범위 오류가 같은 코드로 수렴한다는 점을 알 수 없었다. 전역 계약을 공통 문서 위치에 한 번만 명시했다.

## 결정 기록 (ADR)

### page·size만 전역에서 처리한다

- **문제**: 모든 `MethodArgumentTypeMismatchException`을 하나의 공통 400 코드로 바꾸면 도메인별 파라미터 오류 계약을 잃는다.
- **선택**: 저장소 전역에서 의미가 같은 `page`와 `size`만 이름으로 구분해 공통 코드로 매핑한다. 나머지는 기존 컨트롤러 로컬 계약을 우선하고, 계약이 없는 경우 현재 500 동작을 유지한다.
- **대안**: 모든 타입 불일치를 공통 400으로 변환 — `limit`처럼 도메인별 코드가 갈리는 값을 구분할 수 없어 채택하지 않았다.
- **트레이드오프**: 공통 페이지네이션 계약은 빠뜨릴 수 없게 됐지만, 다른 타입 있는 쿼리 파라미터는 아직 API별 판단이 필요하다.
- 해당 없음 — 이번 결정은 기존 개별 에러 코드와 전역 오류 응답 원칙을 구현한 것이며 별도 신규 볼트 결정으로 승격하지 않는다.

## 기존 결정과의 관계

- `Pageable`을 Controller 계약에 직접 노출하지 않고 `page`·`size`를 받으며 정렬은 서버가 고정한다는 기존 결정의 입력 경계를 보완했다. 타입이 틀린 값도 조용히 무시하지 않고 계약된 오류로 응답한다.
- 파라미터 오류를 공통 오류 하나로 뭉치지 않고 구분 가능한 개별 코드로 반환한다는 결정에 따라 `page`와 `size`를 각각 `INVALID_PAGE`·`INVALID_PAGE_SIZE`로 나눈다.
- 모든 오류를 `errorCode`·`message`·`status`·`instance` 네 필드로 반환한다는 결정은 `GlobalExceptionHandler.toResponse()` 재사용으로 유지된다.
- 전역 핸들러는 도메인과 무관한 공통 계약만 소유한다. 도메인마다 뜻과 코드가 다른 파라미터까지 임의로 통합하지 않는다.

## 남은 후속 사항

- `published`·`needsReview`·`hostId`·`year`·`limit` 등 `page`·`size`가 아닌 쿼리 파라미터 타입 불일치는, 컨트롤러 로컬 계약이 없는 경우 여전히 500이다. 도메인별 에러 코드를 먼저 판정해야 하므로 Issue #114 범위에서는 변경하지 않았다.
- 관리자 목록별 타입 불일치 영구 회귀 테스트는 최종 코드에 추가되지 않았다. 현재 영구 HTTP 경계 검증은 공개 Festival 목록 테스트가 대표한다.
- 공개 Artist 목록은 `page`·`size`를 문자열로 받아 직접 파싱하며 필수값으로 취급하는 기존 계약을 유지한다. 이를 다른 목록과 통일하는 것은 별도 계약 변경이다.
- `FestivalController`가 `GlobalExceptionHandler`를 주입받아 로컬 핸들러에서 직접 위임하는 역방향 의존은 그대로다. 이번 작업은 page·size의 전역 계약에 한정해 구조 리팩터링을 섞지 않았다.
