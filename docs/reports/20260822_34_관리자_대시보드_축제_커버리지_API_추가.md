### 📌 작업 개요

관리자 대시보드의 첫 화면이 요구하는 `GET /admin/festivals/coverage`를 추가했다.
전체 주최(Host)를 기준으로 연도별 축제 데이터의 구축·검수 진행 상황을 집계해,
summary와 페이지 목록을 한 응답으로 돌려준다.

기존 주최 목록은 주최별 전체 축제 수만 줬을 뿐 발행 완료·검수 대기·확인 필요를 구분하지 못했다.
**무엇이 비어 있는지**가 드러나야 운영자가 크롤러 수동 입력이나 축제 검수 흐름으로 이어갈 수 있다.

### 🎯 구현 목표

- 집계 단위를 Festival이 아니라 **Host**로 두고 대학별 진행 상황을 한눈에 보여준다
- summary(전체 주최 수 · 발행 완료 · 검수 대기 · 확인 필요 · 등록 진행률)와 목록을 한 응답으로 제공
- 기본 목록은 손이 필요한 `REVIEW_PENDING` · `NEEDS_CHECK`만, `status`를 주면 `PUBLISHED`도 조회
- 검수 대기 항목은 `festivalId`로, 확인 필요 항목은 `hostId`로 다음 화면에 이어붙일 수 있게 한다

### ✅ 구현 내용

#### 커버리지 조회 엔드포인트

- **파일**: `festival/controller/FestivalAdminController.java`
- **변경 내용**: `@RequestMapping("/admin/festivals")` 아래 `GET /coverage`.
  `year` · `status`는 선택, `page`는 기본 `0`, `size`는 기본 `20`
- **이유**: 경로에 `/api` 접두사를 붙이지 않아(DEC-0084) `SecurityConfig`의 `/admin/**` 매처 사정권에 들어간다.
  관리자 JWT 인증이 그대로 걸리고 권한 등급은 나누지 않는다(DEC-0082 · DEC-0083)

#### 상태 판정과 집계

- **파일**: `festival/service/FestivalCoverageService.java`
- **변경 내용**: 오늘(`Asia/Seoul`) 기준으로 조회 연도를 정하고, 검증 → 조회 → 상태 판정 → 요약 →
  필터 → 정렬 → 페이지 순으로 처리
- **이유**: summary는 필터 이전의 전체 행에서 계산해야 `status`를 걸어도 전체 현황이 유지된다

상태 판정은 세 줄로 끝난다.

```
미발행 축제가 하나라도 있으면        → REVIEW_PENDING
그렇지 않고 현재·예정 발행 축제가 없으면 → NEEDS_CHECK
그 외                              → PUBLISHED
```

축제가 아예 없는 주최와 과거 발행 축제만 있는 주최가 모두 `NEEDS_CHECK`로 합쳐진다.
둘을 가르는 reason은 두지 않았다 — 운영자가 할 일(직접 등록 흐름으로 이동)이 같다.

정렬은 `REVIEW_PENDING → NEEDS_CHECK → PUBLISHED` 순서를 `switch` 표현식으로 못박고,
같은 상태 안에서는 `hostName` 오름차순이다. 정렬 파라미터는 받지 않는다.

`coverageRate`는 `published * 100.0 / 전체 Host 수`를 정수로 반올림하고, Host가 0이면 0이다.

#### 주최별 커버리지 행 조회

- **파일**: `host/repository/HostRepository.java`, `host/repository/HostCoverageRow.java`
- **변경 내용**: `LEFT JOIN LATERAL` 두 개를 쓰는 네이티브 쿼리 `findCoverageRows`와 그 projection 인터페이스
- **이유**: 주최당 한 행을 보장하면서 **대표 축제 한 건**과 **현재·예정 발행 축제의 존재 여부**를
  한 번의 조회로 가져오기 위해서다

`LATERAL` 서브쿼리 둘의 역할이 다르다.

| 서브쿼리 | 조건 | 쓰임 |
| --- | --- | --- |
| `review_festival` | 해당 연도 · `published_at IS NULL`, `start_date ASC, id ASC` 중 1건 | 대표 축제 정보와 `hasUnpublishedFestival` |
| `current_festival` | 해당 연도 · `published_at IS NOT NULL` · `end_date >= 오늘`, 1건 | `hasCurrentFestival` (id만 필요) |

`ON TRUE`로 걸었기 때문에 축제가 없는 주최도 null로 채워진 행 하나를 갖는다.
그래서 조회 결과 행 수가 곧 **전체 Host 수**이고, summary의 `totalHosts`가 별도 조회 없이 나온다.

#### 응답 DTO

- **파일**: `festival/dto/FestivalCoverageResponse.java`, `FestivalCoverageSummary.java`,
  `FestivalCoverageItem.java`, `FestivalCoverageStatus.java`
- **변경 내용**: 최상위 `year` · `summary` · `hosts` 구조. `hosts`는 기존 `PageResponse<T>`를 그대로 사용
- **이유**: 목록 응답 형식을 주최 API(#22)에서 만든 것과 통일한다. 새 페이지 형식을 만들지 않는다

#### 도메인 에러 코드

- **파일**: `festival/exception/FestivalErrorCode.java`
- **변경 내용**: `FESTIVAL_COVERAGE_INVALID_STATUS`(400) · `FESTIVAL_COVERAGE_INVALID_YEAR`(400)
- **이유**: 이슈 #17의 규약대로 도메인 접두사를 붙였다.
  `page` · `size` 범위 위반은 새 코드를 만들지 않고 공통 `INVALID_PAGE` · `INVALID_PAGE_SIZE`를 재사용했다

### 🧭 결정 기록 (ADR)

#### 집계 단위를 Festival이 아니라 Host로

- **문제**: 대시보드가 세어야 하는 것이 축제인지 대학인지
- **선택**: Host. 전체 주최 수가 분모이고 상태도 주최마다 하나로 접는다
- **대안**: Festival 단위 집계 — 축제를 많이 등록한 대학이 진행률을 밀어 올려,
  **아직 아무것도 없는 대학이 지표에 묻힌다.** 이 화면의 목적과 정확히 반대다
- **트레이드오프**: 한 주최에 축제가 여러 개면 상태를 하나로 접어야 해서 우선순위 규칙이 필요하다
- ⭐ **볼트 승격 권장** — 대시보드의 모든 후속 지표가 이 단위 위에 선다

#### 미발행이 하나라도 있으면 무조건 `REVIEW_PENDING`

- **문제**: 발행 축제와 미발행 축제가 같은 주최에 함께 있을 때의 표시
- **선택**: 종료 여부와 관계없이 미발행이 우선한다
- **대안**: 현재·예정 발행 축제를 우선 — 검수 대기 중인 축제가 화면에서 사라져 영영 안 걸린다
- **트레이드오프**: 이미 발행을 마친 대학도 과거 미발행 건 하나 때문에 계속 목록에 남는다

#### `NEEDS_CHECK`를 reason으로 쪼개지 않음

- **문제**: "축제가 아예 없음"과 "과거 발행 축제만 있음"을 구분할지
- **선택**: 구분하지 않는다
- **대안**: reason 필드 추가 — 응답 필드가 늘고 프론트가 분기를 하나 더 갖는데,
  운영자가 할 일은 양쪽 다 "직접 등록 흐름으로 이동"으로 같다
- **트레이드오프**: 나중에 둘을 다르게 다루고 싶어지면 판정 로직과 응답을 함께 고쳐야 한다

#### 대표 축제를 검수 대상에서만 고름

- **문제**: 목록 항목이 보여줄 "대표 축제"를 어느 축제로 할지
- **선택**: 미발행(검수 대상) 축제 중 `start_date ASC, id ASC` 첫 건.
  `review_festival` LATERAL 하나가 대표 축제와 `hasUnpublishedFestival`을 동시에 만든다
- **대안**: 상태별로 다른 대표를 고름 — LATERAL이 하나 더 늘고, 상태마다 대표의 의미가 달라진다
- **트레이드오프**: **`PUBLISHED` 항목은 축제 관련 필드가 전부 null이 된다.** 아래 참고사항 참조

#### `Clock` 빈을 주입받아 "오늘"을 정함

- **문제**: `Asia/Seoul` 기준 오늘 날짜가 필요한데 시계를 어디서 얻을지
- **선택**: 기존 `global/config/ClockConfig`의 `clock` 빈을 주입받아 `clock.withZone(SEOUL)`로 쓴다
- **대안**: `LocalDate.now(SEOUL)` 직접 호출 — 테스트에서 연도 경계와 `end_date >= 오늘` 판정을 고정할 수 없다.
  전용 Clock 빈을 새로 만드는 것도 대안이었으나 같은 구현의 빈이 둘이 되어 이름 폴백에 의존하게 된다
- **트레이드오프**: 없음에 가깝다. 시계가 하나라 만료·경계 판정이 전부 같은 기준을 쓴다

### 📌 참고사항

**`status=PUBLISHED`로 조회하면 축제 관련 필드가 전부 null이다.**
대표 축제를 `review_festival`(미발행 축제) LATERAL에서만 뽑기 때문에,
미발행 축제가 없는 `PUBLISHED` 주최는 `festivalId` · `festivalName` · `startDate` · `endDate`가 모두 null로 나간다.

이슈 본문은 두 곳에서 서로 다른 방향을 가리킨다.

| 이슈 문장 | 함의 |
| --- | --- |
| "각 목록 항목은 주최명, 대표 축제명, 대표 축제 기간, 상태, Host Instagram 링크를 제공한다" | 모든 항목이 축제 정보를 가진다 |
| "대표 Festival은 **검수 대상 중** `startDate ASC`, 동일하면 `id ASC`로 선택한다" | 대표는 검수 대상에서만 정의된다 |
| "`NEEDS_CHECK`에 현재 대상 Festival이 없으면 … null을 허용한다" | null 허용은 `NEEDS_CHECK`에만 명시 |

구현은 두 번째 문장을 따랐고, 그 결과 명시되지 않았던 `PUBLISHED`의 축제 필드가 null이 됐다.
발행 완료 목록에서 어떤 축제가 발행됐는지를 화면에 보여야 한다면 `current_festival` LATERAL이
id만이 아니라 이름·기간까지 가져오고 상태별로 대표를 고르도록 바꿔야 한다.

**`page` · `size`에 숫자가 아닌 값이 오면 400이 아니라 500이 나간다.**
범위 위반은 `validatePagination`이 `INVALID_PAGE` · `INVALID_PAGE_SIZE`로 잡지만,
`?page=abc`처럼 타입이 어긋나면 서비스에 닿기 전에 스프링이 타입 변환 예외를 던진다.
`GlobalExceptionHandler`에 이를 받는 핸들러가 없어 catch-all로 떨어진다(이슈 #17 리포트의 참고사항 참조).
`year` · `status`도 마찬가지로 `year=abc`는 500이다.

**페이지네이션이 DB가 아니라 메모리에서 일어난다.**
`findCoverageRows`는 LIMIT·OFFSET 없이 전체 주최 행을 가져오고, 필터·정렬·자르기를 자바에서 한다.
집계와 목록이 같은 판정 결과를 써야 하므로 자연스러운 선택이고 주최 수가 대학 규모라 지금은 문제가 없다.
주최가 크게 늘면 요청마다 전체 스캔이 된다는 점만 기억해 두면 된다.

- `resolveStatus`는 요약에서 상태별로 한 번씩, 목록 매핑에서 다시 한 번 호출돼 행마다 네 번 계산된다.
  순수 함수라 결과는 같고 비용도 작다
- 이슈가 제외 범위로 못박은 것들 — 축제 검수·수정·발행·직접 등록 API, 크롤링·임포트, 프론트 화면 —
  은 이 작업에 들어 있지 않다. 이 API는 그 화면들로 가는 `festivalId` · `hostId`만 넘긴다
