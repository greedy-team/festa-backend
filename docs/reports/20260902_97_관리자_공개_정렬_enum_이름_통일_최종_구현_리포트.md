# 관리자·공개 정렬 enum 이름 통일 최종 구현 리포트

## 작업 개요

Issue #97과 PR #124를 통해 관리자·공개 API의 정렬 enum 이름을 서비스·컨트롤러와 같은 규칙으로 통일했다. 같은 개념이 관리자와 공개로 갈리면 관리자가 `Admin` 한정어를 갖고 공개가 한정어 없는 이름을 사용한다.

이 리포트는 최신 `develop`의 merge commit `1380a902db28c80920ba5c30c78dca8b0fc76000`에 반영된 최종 코드, Issue #97 요구사항, PR #124 리뷰와 GitHub Actions 결과를 기준으로 작성했다.

- 관련 Issue: #97
- 관련 PR: #124
- 최종 PR head: `891f3f1dd2498808f1bf080c2e54c0266eb5333f`
- develop merge commit: `1380a902db28c80920ba5c30c78dca8b0fc76000`

## 문제 분석

서비스와 컨트롤러는 관리자 타입에 `Admin`을 붙이고 공개 타입에 한정어 없는 이름을 사용하는 규칙을 일관되게 따랐다. 반면 정렬 enum은 관리자 타입이 맨 이름을 먼저 차지하고 공개 타입이 `List` 또는 `Public`으로 비켜나 계층마다 반대 규칙을 사용했다.

| 계층 | 관리자 | 공개 |
| --- | --- | --- |
| Service | `FestivalAdminService` · `ArtistAdminService` | `FestivalService` · `ArtistService` |
| Controller | `FestivalAdminController` · `ArtistAdminController` | `FestivalController` · `ArtistController` |
| 변경 전 enum | `FestivalSortType` · `ArtistSortType` | `FestivalListSortType` · `ArtistPublicSortType` |

이 배치는 의도된 API 구분이 아니라 관리자 기능이 먼저 구현돼 맨 이름을 선점한 작성 순서의 결과였다. 특히 공개 쪽 한정어도 `List`와 `Public`으로 갈려 같은 역할의 타입을 이름만 보고 일관되게 찾기 어려웠다.

## 최종 enum 이름

| 역할 | 변경 전 | 최종 이름 | 상수 |
| --- | --- | --- | --- |
| 관리자 축제 정렬 | `FestivalSortType` | `FestivalAdminSortType` | `IMPORTED_DESC`, `START_DATE` |
| 공개 축제 정렬 | `FestivalListSortType` | `FestivalSortType` | `LATEST`, `UPCOMING` |
| 관리자 아티스트 정렬 | `ArtistSortType` | `ArtistAdminSortType` | `CREATED_DESC`, `APPEARANCES`, `NAME` |
| 공개 아티스트 정렬 | `ArtistPublicSortType` | `ArtistSortType` | `APPEARANCES`, `NAME` |

최종 `develop`에는 삭제된 `ArtistPublicSortType`·`FestivalListSortType`의 production/test 참조가 남아 있지 않다. 기능 이름이 붙은 `FestivalCoverageStatus`·`FestivalPublishFailureReason`·`ArtistMatchReason`·`Import*`와 관리자/공개 짝이 없는 `FestivalStatus`는 변경하지 않았다.

## API·정렬·에러 계약 불변

enum 클래스 이름은 요청·응답 wire format에 포함되지 않는다. HTTP 요청에는 기존과 같이 `sort` 문자열 상수값만 들어가며 `EnumParser`가 대소문자와 앞뒤 공백을 정규화한다.

| 계약 | 최종 결과 |
| --- | --- |
| 엔드포인트·HTTP method | 변경 없음 |
| `sort` 쿼리 파라미터 이름 | 변경 없음 |
| 허용 상수값 | 변경 없음 |
| 생략·blank 기본값 | 변경 없음 |
| 잘못된 값의 HTTP 상태 | 기존 400 유지 |
| 오류 코드 | `ARTIST_INVALID_SORT_TYPE`·`FESTIVAL_INVALID_SORT_TYPE` 유지 |
| 정렬 방향과 tie-breaker | 변경 없음 |
| 응답 DTO·Swagger 설명 | 변경 없음 |

네 기존 enum 파일과 최종 enum 파일을 타입 이름만 정규화해 대조한 결과 구현 본문은 완전히 동일했다. Controller와 Service는 새 타입을 사용하지만 요청 파싱 이후의 Repository 호출, 트랜잭션 경계, 페이지네이션, KST/Clock 처리에는 변화가 없다.

수정 요청 없이 merge 가능하다고 판단됐으며 최종 merge commit에도 추가 코드 변경은 없다.

## 기존 결정과의 관계

- 관리자와 공개로 갈리는 타입은 관리자가 `Admin` 한정어를 갖고 공개가 맨 이름을 사용한다는 기존 이름 규칙을 enum·DTO 계층까지 이행했다.
- 관리자 전용 서비스가 도메인 전체의 맨 이름을 차지하지 않는다는 기존 서비스 계층 원칙과 같은 방향이다.
- 한정어는 `Coverage`·`Publish`·`Merge`처럼 다른 개념을 구분할 때 유지하며, 단지 관리자 API에서 사용된다는 이유로 기능 이름에 `Admin`을 추가하지 않는다.
- enum의 기본값과 오류 코드는 각 enum의 `from(String)`이 소유한다는 기존 파싱 계약을 유지했다.

## 제한사항 및 범위 밖

- 공개 `ArtistSortType`만 `toSort()`가 없고 `ArtistService`에서 `NAME` 여부에 따라 Repository 메서드를 선택하는 기존 구조를 유지했다. 이름 통일과 무관한 정렬 구조 리팩터링은 포함하지 않았다.
- API 문서, DB 스키마, Entity, Repository query, SecurityConfig, GlobalExceptionHandler, 배포 설정은 변경하지 않았다.
- 과거 구현 당시 타입 이름을 기록한 기존 완료 리포트는 역사 문서이므로 소급 수정하지 않았다.
