### 📌 작업 개요

관리자용 주최 등록 · 목록 · 수정 · 삭제 API를 추가했다.
주최는 크롤러가 만들지 않고 임포트가 이름으로 맞춰보기만 하므로, 누군가 먼저 등록해두어야 축제가 주최에 연결된다.
그 등록 수단이 없어 데이터베이스에 직접 넣는 것 말고는 방법이 없던 상태를 해소했다.

이 저장소의 **첫 API**이기도 하다. 이슈 #17에서 정한 에러 응답 규약이 실제로 동작하는지가 여기서 처음 확인됐다.

### ✅ 구현 내용

#### 주최 API 4종

- **파일**: `host/controller/HostAdminController.java`
- **변경 내용**: 등록(`POST`) · 목록(`GET`) · 수정(`PATCH /{id}`) · 삭제(`DELETE /{id}`)
- **이유**: 등록은 201 + 본문, 삭제는 204 무본문으로 두어 상태 코드가 결과를 말하게 했다

#### 서비스 계층

- **파일**: `host/service/HostService.java`
- **변경 내용**: 네 유스케이스와 검증(`validateName` · `validateRegion` · `blankToNull`)
- **이유**: 조회는 `@Transactional(readOnly = true)`, 나머지는 쓰기 트랜잭션으로 분리

#### 저장소와 집계

- **파일**: `host/repository/HostRepository.java`, `host/repository/HostWithFestivalCount.java`
- **변경 내용**: `existsByName` · `existsByNameAndIdNot` · `countFestivalsByHostId`와,
  주최별 축제 수를 함께 가져오는 프로젝션 쿼리 `findAllWithFestivalCount`
- **이유**: 목록에서 주최마다 축제 수를 따로 조회하면 N+1이 된다. `LEFT JOIN` + `GROUP BY`로 한 번에 가져온다.
  `countQuery`를 별도로 준 것은 `GROUP BY`가 있는 쿼리의 전체 개수를 스프링이 잘못 세는 것을 막기 위해서다

#### 공통 페이지 응답

- **파일**: `global/dto/PageResponse.java`
- **변경 내용**: `items` · `page` · `size` · `totalElements` · `totalPages` · `hasNext` · `hasPrevious` record와
  `from(Page)` 팩터리
- **이유**: 목록 API가 처음이라 여기서 만들었다. 아티스트 · 축제 목록도 같은 형식을 쓴다.
  스프링 `Page`를 그대로 직렬화하면 내부 구조가 계약이 되어 버린다

#### 주최 도메인 에러 코드

- **파일**: `host/exception/HostErrorCode.java`
- **변경 내용**: `HOST_INVALID_NAME`(400) · `HOST_INVALID_REGION`(400) · `HOST_DUPLICATE_NAME`(409) ·
  `HOST_HAS_FESTIVALS`(409) · `HOST_NOT_FOUND`(404)
- **이유**: 이슈 #17이 정한 규약대로 `ErrorCode`를 구현하고 도메인 접두사를 붙였다.
  주최 유형 관련 코드는 두지 않았다 — 유형 항목 자체를 두지 않기로 했다

#### 엔티티 보강과 마이그레이션

- **파일**: `host/entity/Host.java`, `src/main/resources/db/migration/V20260815_1428__host_logo_url.sql`
- **변경 내용**: `logoUrl` 필드와 컬럼 추가, 항목별 `change*` 메서드 7개 추가
- **이유**: 로고와 배너는 쓰임이 다르다 — 로고는 목록에서, 배너는 상세에서 쓴다

#### 최소 보안 설정

- **파일**: `global/config/SecurityConfig.java`
- **변경 내용**: csrf · formLogin · httpBasic 비활성화, `anyRequest().permitAll()`
- **이유**: 아래 ADR 참고

### 🧭 결정 기록 (ADR)

#### 모든 경로를 일단 열어둠

- **문제**: 보안 설정이 없는 상태에서 컨트롤러를 만들면, 스프링 시큐리티 기본값이 모든 경로를
  기동할 때마다 새로 만들어지는 임시 비밀번호로 잠근다. 그대로면 개발이 불가능하다
- **선택**: `permitAll()`로 열어두고 진행. 관리자 인증은 별도 이슈로 분리
- **대안**: 인증을 이 작업에서 함께 구현 — 인증 방식이 정해지기 전이라 추측으로 만들게 된다
- **트레이드오프**: **배포 전에 반드시 교체해야 한다.** 관리자 API가 인증 없이 열려 있는 상태다.
  이 부채는 이슈 #27(관리자 로그인 · JWT 인증)에서 갚았다
- ⭐ **볼트 승격 권장** — 의도적으로 남긴 보안 부채이고 배포 게이트와 연결된다

#### 길이 제한을 DB가 아니라 요청 검증에서

- **문제**: 이름 100자 · 지역 50자 제한을 어디서 걸지
- **선택**: 서비스의 검증 메서드에서. DB 컬럼은 `varchar`로 길이 제한을 두지 않았다
- **대안**: DB에 `varchar(100)` — 초과 값이 DB까지 도달해 제약 위반 예외가 나고,
  그러면 **잘못된 요청이 아니라 서버 오류**가 된다
- **트레이드오프**: DB가 최후의 방어선 역할을 하지 않는다. 검증을 빠뜨린 경로가 생기면 그대로 저장된다

#### 부분 수정에서 미전송과 빈 값을 구분

- **문제**: `PATCH`에서 항목을 안 보낸 것과 빈 값으로 보낸 것을 어떻게 가를지
- **선택**: `null`이면 기존 값 유지, 빈 문자열이면 `null`로 비운다(`blankToNull`)
- **대안**: 빈 문자열도 무시 — 값을 지울 방법이 없어진다
- **트레이드오프**: 이름과 지역은 필수라 비울 수 없다. 이 둘은 `null`이 아닐 때 검증을 거치므로
  빈 문자열이 오면 `HOST_INVALID_NAME` · `HOST_INVALID_REGION`으로 거절된다

#### 축제가 남은 주최는 삭제 전에 걸러냄

- **문제**: 축제가 주최를 참조하므로 DB가 삭제를 거부한다
- **선택**: 삭제 전에 축제 수를 세어 `HOST_HAS_FESTIVALS`(409)로 응답
- **대안**: DB 제약 위반을 잡아 변환 — 걸러내지 않으면 잘못된 요청이 서버 오류로 나간다
- **트레이드오프**: 조회가 한 번 더 든다

### 📌 참고사항

- **경로가 나중에 정정됐다.** 이 작업은 이슈 본문이 적은 대로 `/api/admin/hosts`에 매핑했으나,
  노션 명세와 프론트는 접두사를 쓰지 않는다. 이슈 #26에서 `/admin/hosts`로 되돌렸다.
  접두사를 붙이지 않는다는 판단에 결정 노트가 없어 인용할 id가 없었던 것이 원인이다
- **`logoUrl`은 이슈 본문에 없는 항목이다.** 목록과 상세에서 쓰임이 갈린다는 판단으로 구현 단계에서 추가했고,
  마이그레이션도 함께 넣었다
- 값 검증을 Bean Validation 애노테이션이 아니라 서비스의 수동 검사로 구현했다.
  에러 코드 하나에 사용자 문구 하나를 대응시키려면 검증 실패를 코드별로 갈라야 하는데,
  표준 검증 예외를 코드로 변환하는 핸들러가 아직 없기 때문이다(이슈 #17 보고서의 참고사항 참조)
