# 기록되지 않던 실패 지점 로그 최종 구현 리포트

## 작업 개요

Issue #117과 PR #127은 실패 원인과 관리 작업 결과가 서버에 충분히 남지 않던 문제를 정리했다. CSV 파싱 실패의 원인, 예외가 발생한 요청 경로, 인증 실패, 로그인 실패 사유, 되돌릴 수 없는 관리 작업, 일괄 발행 결과를 각 사건의 책임 지점에서 한 번만 기록하도록 만들었다.

최종 구현은 PR head `3b22162660b389b95fe82728ee2a65dd6fc93fcf`가 develop merge commit `f856ce63b56a0e0baa70b2c91ff19fec401c147a`로 병합된 코드를 기준으로 확인했다.

## 문제 분석

기존 코드는 실패 원인을 잡고도 버리거나, 예외 기록에 요청 정보를 쓰지 않거나, Spring Security 진입점에서 끝나는 인증 실패를 남기지 않았다. 서비스의 되돌릴 수 없는 작업은 대상과 수행자를 추적할 수 없었고, 일괄 발행의 부분 실패 요약은 응답을 직접 확인해야만 알 수 있었다.

첫 구현은 관리 작업의 성공 로그를 `@Transactional` 서비스 메서드 안에서 바로 기록했다. 이 방식은 SQL 실행이 끝났더라도 실제 commit 전에 로그가 남는다. commit 단계에서 실패해 rollback되면 데이터는 반영되지 않았는데 로그에는 성공한 것으로 남아 감사·장애 조사 근거가 사실과 어긋난다.

리뷰 과정에서 두 문제가 추가로 확정됐다.

1. 작업 대상뿐 아니라 인증된 관리자 식별자도 모든 관련 로그에 일관되게 붙어야 한다.
2. 관리 작업의 성공 로그는 메서드가 정상 반환한 시점이 아니라 실제 transaction commit이 끝난 뒤에만 기록해야 한다.

## 최종 계약

- 인증된 관리자의 username은 `JwtAuthenticationFilter`가 MDC의 `admin` 키에 넣는다.
- 요청이 끝나거나 예외로 빠져나가도 `finally`에서 `admin`을 제거한다. 톰캣 스레드 재사용 시 다음 요청으로 식별자가 새지 않는다.
- 로그 문구마다 관리자 이름을 직접 조립하지 않는다. `logging.pattern.correlation`이 MDC 값을 모든 로그에 공통으로 붙인다.
- 관리 작업의 성공 로그는 `AfterCommitLogger.info(...)`로 등록하고 transaction의 `afterCommit()`에서만 기록한다.
- rollback된 작업에는 성공 로그를 남기지 않는다.
- 비동기 listener로 넘기지 않고 commit한 동일 스레드의 transaction synchronization callback에서 기록한다. 따라서 요청 번호와 `admin` MDC가 afterCommit 로그에도 유지된다.
- transaction synchronization이 없는 호출은 기다릴 commit이 없으므로 즉시 기록한다.
- 성공 로그 7곳에 같은 기준을 적용한다.

| 관리 작업 | 로그 내용 |
| --- | --- |
| 주최 삭제 | `hostId` |
| 아티스트 삭제 | `artistId` |
| 아티스트 병합 | target/source, 이동 출연 수, 제거 중복 수 |
| 축제 삭제 | `festivalId` |
| 라인업 삭제 | `festivalId`, `lineupId` |
| 축제 발행 취소 | `festivalId` |
| 축제 일괄 발행 | 요청·발행·실패 건수와 실패 사유 |

## 구현 내용

### 실패 원인과 응답 메시지 분리

`FestaException`은 응답용 `ErrorCode`와 로그 전용 `logMessage`, 원인 예외를 분리한다. `GlobalExceptionHandler`는 HTTP 메서드와 URI, 도메인 맥락, 원인 예외를 기록하지만 응답의 `message`는 항상 `ErrorCode`의 고정 문구를 사용한다. 로그를 보강해도 API 응답으로 내부 맥락이 새지 않는다.

`ImportCsvParser`는 CSV 본문 파싱, 파일 읽기, UTF-8 디코딩 실패의 원인을 `FestaException` cause로 보존한다. 업로드 크기 초과와 multipart 누락, 쿼리 파라미터 타입 오류, 축제 컨트롤러가 직접 응답하는 타입 오류에도 요청 맥락을 남긴다.

### 인증과 관리자 식별자

토큰 만료·위조는 전역 예외 처리까지 도달하지 않으므로 `JwtAuthenticationEntryPoint`가 한 번만 기록한다. 로그인 실패는 `AdminAuthService`가 계정 없음·비밀번호 불일치·입력 누락을 로그 맥락으로 구분하되 응답은 동일한 인증 실패 계약을 유지한다. 비밀번호와 토큰 값은 기록하지 않는다.

유효한 관리자 토큰은 `JwtAuthenticationFilter`에서 username을 MDC `admin`에 넣는다. 서비스 로그는 관리자 필드를 직접 알 필요가 없고, 필터 체인이 끝나면 `finally`에서 MDC를 정리한다.

### commit 이후 성공 로그

`AfterCommitLogger`는 transaction synchronization이 활성화된 경우 `TransactionSynchronizationManager.registerSynchronization(...)`으로 callback을 등록한다. 성공 로그는 `afterCommit()`에서 기록되므로 commit 실패와 rollback에는 실행되지 않는다.

`@TransactionalEventListener`와 비동기 listener 대신 이 구조를 선택했다. 비동기 실행은 thread-local인 MDC를 자동으로 이어받지 못해 관리자 식별자가 사라질 수 있다. 현재 callback은 commit한 요청 스레드에서 연속 실행되므로 `admin`과 요청 번호가 그대로 유지된다.

## 리뷰 논의 및 반영 내용

### 관리자 식별자를 함께 남겨야 한다

리뷰는 아티스트 삭제 로그에 작업한 관리자 식별자가 없다고 지적했다. `27e6dad`에서 개별 로그 문구를 고치는 대신 MDC `admin`과 공통 로그 패턴으로 반영했다. 새 로그가 추가돼도 관리자 필드가 빠지지 않고 WARN 이상 실패 로그에도 같은 식별자가 붙는다.

### transaction 안의 성공 로그는 rollback과 모순될 수 있다

리뷰는 일괄 발행 성공 로그가 commit 전에 기록돼 rollback된 작업을 성공으로 남길 수 있다고 지적했다. 조사 결과 동일 문제가 처음 언급한 5곳이 아니라 주최 삭제와 라인업 삭제를 포함한 7곳 전체에 있었다.

`b09d736`에서 7곳 모두 `AfterCommitLogger`로 전환했다. 기존 `@DataJpaTest`는 테스트 자체가 rollback되므로 afterCommit 로그를 검증할 수 없어, 실제 PostgreSQL transaction을 commit하거나 명시적으로 rollback하는 `AfterCommitLogTest`로 교체했다.

두 리뷰 모두 최종 코드와 테스트에 반영됐으며 남은 blocking finding은 없다.

## 테스트 및 검증

`AfterCommitLogTest`는 Testcontainers PostgreSQL과 실제 `PlatformTransactionManager`를 사용한다.

- commit된 작업에는 성공 로그가 남는다.
- transaction 밖의 호출은 즉시 기록된다.
- afterCommit 로그에도 MDC `admin`이 유지된다.
- 주최 삭제, 아티스트 삭제, 아티스트 병합, 축제 삭제, 라인업 삭제, 발행 취소, 일괄 발행의 7곳 각각에서 rollback 시 데이터가 복원되고 성공 로그가 남지 않는다.
- 발행 취소와 일괄 발행이 commit되면 대상·건수·실패 사유가 기록된다.

`JwtAuthenticationFilterTest`는 유효한 토큰에서 MDC가 체인 안에 존재하고, 토큰 없음·오류에서는 설정되지 않으며, 체인 종료 후 제거되는 것을 검증한다. `LogCaptor`는 실제 Logback event의 MDC property map도 읽어 afterCommit 로그의 관리자 식별자를 확인한다.

## 결정 기록 (ADR)

### 작업 성공 로그는 transaction commit 이후에 기록한다

- **문제**: `@Transactional` 메서드 내부의 `log.info`는 commit 전에 실행돼 rollback된 작업을 성공으로 기록할 수 있다.
- **선택**: transaction synchronization의 `afterCommit()`에서 성공 로그를 기록하는 `AfterCommitLogger`를 사용한다.
- **대안**: 서비스 메서드 반환 직전 기록은 commit 보장이 없어 제외했다. 비동기 event listener는 MDC가 다른 스레드로 자동 전파되지 않아 제외했다.
- **결과**: rollback에는 성공 로그가 없고, commit한 동일 스레드에서 실행돼 요청 MDC가 유지된다.

### 관리자 식별자는 로그 문구가 아니라 MDC로 전파한다

- **문제**: 각 서비스가 username을 인자로 받아 로그 문자열에 넣으면 호출 계약이 오염되고 신규 로그에서 누락되기 쉽다.
- **선택**: 인증 필터가 MDC `admin`을 설정하고 공통 로그 패턴이 출력한다.
- **대안**: 서비스별 수동 필드는 중복과 누락 위험 때문에 제외했다.
- **결과**: 요청 안의 성공·실패 로그에 같은 관리자 식별자가 적용되고, 요청 종료 시 cleanup으로 스레드 재사용 누수를 막는다.

## 남은 후속 사항

- 관리 작업의 `INFO` 로그는 stdout에만 남고 다음 배포에서 사라질 수 있다. 장기 감사가 필요하면 로그 레벨을 왜곡하지 말고 별도 감사 테이블을 사용해야 한다.
- `ImportPreviewService`의 `uploadedByAdmin(null)`은 이 PR 범위 밖이다. 임포트 감사 행에 업로더를 연결하려면 별도 작업이 필요하다.
- 로그인 아이디의 마스킹 여부는 관리자 계정 운영 정책이 바뀔 때 다시 판단한다.
