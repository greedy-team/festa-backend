### 📌 작업 개요

`festa-crawler`가 만든 `festivals.csv` · `lineup.csv` · `artists.csv`를 관리자가 업로드하면
파싱·검증하고 기존 DB와 대조해 **실제 반영 전 preview**를 돌려주는 API를 추가했다.

3단계로 나눈 임포트 기능 중 첫 번째다. 이 단계는 `Artist` · `Festival` · `Lineup`을
생성·수정·삭제하지 않는다. 판정 결과를 `ImportBatch.preview`에 JSON 한 건으로 저장해,
후속 commit이 원본 CSV를 다시 받지 않고도 반영할 수 있게 하는 것까지가 범위다.

### 🎯 구현 목표

- bundle(3종 한 번에)과 single(1종) 업로드가 **같은 parser · validator · matcher**를 쓰게 한다
- 형식·값 검증과 Host / Artist / ArtistAlias / Festival 매칭으로
  `CREATE` · `UPDATE` · `SKIP` · `INVALID` 예상 action과 blocker / warning을 계산한다
- API 응답 DTO와 저장용 preview 모델을 분리하고, 저장 모델에 `schemaVersion`을 둔다
- `ImportBatch`를 저장하고 만료 시각을 `uploadedAt + 30분`으로 계산한다

### ✅ 구현 내용

#### 업로드 엔드포인트 2종

- **파일**: `importer/controller/ImportAdminController.java`
- **변경 내용**: `POST /admin/imports/bundle`과 `POST /admin/imports/{type}`.
  둘 다 `multipart/form-data`만 받고 성공 시 `201 Created`로 preview를 반환한다
- **이유**: 경로에 `/api`를 붙이지 않아(DEC-0084) `/admin/**` 인증 매처에 그대로 걸린다(DEC-0082 · DEC-0083)

form field 계약은 다음과 같다.

| 엔드포인트 | part 이름 | 비고 |
| --- | --- | --- |
| `/bundle` | `festivals` · `lineups` · `artists` · `onConflict` | `artists`는 선택 |
| `/{type}` | `file` · `onConflict` | `type`은 `festivals` · `lineups` · `artists` |

`onConflict`는 생략하면 `UPDATE`, 허용값은 `UPDATE` · `SKIP`이다. 대소문자와 앞뒤 공백을 흡수하고
그 밖의 값은 `IMPORT_INVALID_CONFLICT_POLICY`로 거절한다.
path variable은 외부 계약대로 소문자를 쓰고 `ImportSection.fromPath`가 내부 타입으로 옮긴다.

#### CSV 파서

- **파일**: `importer/parser/ImportCsvParser.java`, `build.gradle.kts`
- **변경 내용**: Apache Commons CSV `1.14.1`을 도입하고 RFC4180 형식으로 파싱.
  크기 → 빈 파일 → UTF-8 디코딩 → BOM 제거 → 헤더 검증 → 행 변환 순으로 처리한다
- **이유**: quoted comma · escaped quote · 값 안의 줄바꿈을 직접 다루지 않기 위해서다.
  단순 쉼표 분할 방식은 이 셋 중 어느 것도 처리하지 못한다

디코딩은 관대하게 하지 않았다. `onMalformedInput(REPORT)` · `onUnmappableCharacter(REPORT)`를 걸어
UTF-8이 아닌 바이트가 하나라도 있으면 대체 문자로 덮지 않고 `IMPORT_INVALID_CSV_ENCODING`으로 세운다.
BOM은 디코딩 **후** 첫 문자로 판정해 떼어낸다 — BOM만으로 인코딩 오류를 내지 않는다.

행 번호는 헤더를 제외하고 1부터 센다(DEC-0077). 열 개수가 헤더와 어긋난 행은 `IMPORT_INVALID_CSV`다.

#### 섹션 정의와 검증

- **파일**: `importer/model/ImportSection.java`
- **변경 내용**: 섹션마다 헤더 목록과 `ImportBatchType`을 함께 들고 있는 enum
- **이유**: 헤더 계약과 batch 타입이 같은 자리에 있어야 둘이 따로 놀지 않는다

값 검증은 필수값 · 날짜 · ISO-8601 datetime · URL · 열거값 · 행 간 참조를 다룬다.

- `ticket_open_at`은 offset이 있으면 그대로 `Instant`로, 없으면 `Asia/Seoul`로 해석한다.
  date-only는 거절하고 **원문 문자열은 `ticketOpenAtRaw`로 보존**한다
- `flag` 7종과 `discovery` 4종은 DB CHECK 없이 애플리케이션에서 검증한다(DEC-0057)
- `image_urls`는 파이프로 나눠 원본 배열을 보존하고, 대표 이미지는 `poster_url` 우선,
  비어 있으면 첫 번째 `image_urls`를 쓴다. 나머지 이미지는 저장되지 않으므로
  `ADDITIONAL_IMAGE_URLS_NOT_PERSISTED` warning을 붙인다

#### DB 매칭

- **파일**: `importer/service/ImportPreviewService.java`의 `loadLookup`,
  `host/repository/HostRepository.java`, `artist/repository/ArtistRepository.java`,
  `artist/repository/ArtistAliasRepository.java`, `festival/repository/FestivalRepository.java`
- **변경 내용**: 업로드 전체에서 필요한 이름·키를 먼저 모아 `IN` 조회 네 번으로 끌어온 뒤
  `Lookup` 레코드에 담아 행 판정에 넘긴다
- **이유**: 행마다 조회하면 수천 행에서 그만큼의 쿼리가 나간다. 조회를 앞으로 모아 고정 횟수로 만든다

매칭 규칙은 계약 그대로다. Host는 trim 후 `name` exact match만 쓰고 자동 생성하지 않는다 —
없으면 `HOST_NOT_FOUND`, 여러 개면 `HOST_AMBIGUOUS` blocker다.
Artist는 `Artist.name`을 먼저 보고 없으면 `ArtistAlias.name`으로 넘어가며,
서로 다른 Artist를 가리키면 임의로 고르지 않고 `UNRESOLVED` + blocker다.
같은 업로드 안에서 대표명과 별칭이 교차하는 경우까지 `conflictingArtistLines`로 잡는다.

#### action 판정

- **파일**: `importer/service/ImportPreviewService.java`
- **변경 내용**: 섹션별 `festivalRow` · `artistRow` · `lineupRow`가 각각 검증·매칭 후 action을 정한다
- **이유**: 세 섹션의 식별자와 blocker 종류가 달라 판정을 한 함수로 합칠 수 없다

Festival 판정 순서는 이렇다.

```
blocker/error가 있으면        → INVALID
flag != OK 이면               → SKIP  (skipReason = CRAWLER_FLAG_<flag>)
DB에 같은 import_key가 없으면  → CREATE
onConflict == SKIP 이면       → SKIP  (skipReason = ON_CONFLICT_SKIP)
그 외                         → UPDATE
```

`UPDATE`에서 빈 값이 기존 값을 지우지 않도록 `keepExisting`을 모든 선택 필드에 통과시킨다.
Artist 별칭은 기존 값과 CSV 값의 합집합이다.

#### preview 저장과 응답

- **파일**: `importer/model/StoredImportPreview.java`, `StoredPreviewRow.java`,
  `importer/service/PreviewJsonCodec.java`, `importer/repository/ImportBatchRepository.java`
- **변경 내용**: 저장 모델 최상위에 `schemaVersion: 1`을 두고 Jackson으로 직렬화해
  `ImportBatch.preview` text 한 건에 넣는다(DEC-0055 · DEC-0076)
- **이유**: 후속 commit이 원본 CSV 없이 반영하려면 section · line · importKey · action ·
  정규화 값 · **원본 payload** · 매칭 결과 · blocker가 모두 남아 있어야 한다

- **파일**: `importer/dto/ImportPreviewResponse.java`, `ImportPreviewRowResponse.java`,
  `ImportPreviewSummary.java`, `ImportBlockerResponse.java`
- **변경 내용**: 응답은 `importId` · `type` · `onConflict` · `uploadedAt` · `expiresAt` ·
  `summary` · `blockers` · `rows`. summary는 `toCreate` · `toUpdate` · `toSkip` · `invalid`
- **이유**: 저장 모델을 그대로 내보내면 내부 구조가 외부 계약이 된다. 둘을 분리했다

`blockers`는 행 목록을 그대로 주지 않고 **code 단위로 접는다.** code마다 건수와
사람이 알아볼 값 목록을 함께 준다 — `HOST_` 계열이면 주최명, `ARTIST_` 계열이면 아티스트명,
그 밖에는 import key다. 1000행에서 주최 하나가 안 맞으면 blocker 1000개가 아니라
`HOST_NOT_FOUND` 하나에 이름 하나가 뜬다.

#### 만료와 업로드 제한

- **파일**: `importer/entity/ImportBatch.java`(기존), `src/main/resources/application.yml`
- **변경 내용**: `expiresAt`은 엔티티 생성자가 `uploadedAt.plus(30, MINUTES)`로 계산한다.
  multipart는 파일당 `5MB`, 요청 전체 `20MB`
- **이유**: 만료 계산을 엔티티가 가지면 서비스가 어디서 부르든 규칙이 하나다.
  파서에도 5MB 검사를 한 번 더 두어 서블릿 계층을 우회한 호출에서도 같은 한도가 선다

#### 공통 예외 처리 보강

- **파일**: `global/exception/GlobalExceptionHandler.java`, `global/exception/CommonErrorCode.java`
- **변경 내용**: `MaxUploadSizeExceededException` → `PAYLOAD_TOO_LARGE`(신설),
  `MissingServletRequestPartException` → `INVALID_REQUEST_BODY` 핸들러 추가
- **이유**: 용량 초과는 스프링이 컨트롤러에 닿기 전에 던진다. 핸들러가 없으면 공통 형식이 아니라
  catch-all 500으로 나간다

### 🧭 결정 기록 (ADR)

#### 헤더를 순서까지 정확히 일치시킴

- **문제**: 헤더 검증을 집합 비교로 할지 순서까지 볼지
- **선택**: `actual.equals(section.headers())` — 순서가 다르거나 모르는 열이 붙어도 거절한다
- **대안**: 집합 비교 후 이름으로 접근 — 열 순서가 바뀌어도 통과하니 관대해 보이지만,
  crawler가 열을 하나 추가했는데 백엔드가 모르고 지나가는 상황을 못 잡는다
- **트레이드오프**: crawler가 열을 하나만 늘려도 업로드가 전부 막힌다.
  crawler 산출물과 업로드 계약을 한 벌로 유지하기로 한 결정(DEC-0049)이 이 강한 검증을 지탱한다

#### `flag != OK` 행은 값 검증을 건너뛰고 SKIP으로 판정

- **문제**: crawler가 수집에 실패한 행은 필드가 비어 있다. 이 행에 필수값·날짜 검증을 걸면
  전부 INVALID가 되어 blocker 목록이 실패 행으로 뒤덮인다
- **선택**: `flag == OK`일 때만 이름·Host 매칭·날짜·discovery를 검증한다.
  그 외에는 검증을 건너뛰고 `SKIP` + `skipReason = CRAWLER_FLAG_<flag>`로 내린다
- **대안**: 실패 행도 동일하게 검증 — 관리자가 손댈 수 없는 오류가 목록을 채운다
- **트레이드오프**: **SKIP 행의 원본 값은 한 번도 검증되지 않은 채 payload에 남는다.**
  SKIP도 감사 대상이라 저장되므로, 후속 commit이 payload를 다시 파싱하면 검증을 통과한 적 없는
  문자열을 만난다. 아래 참고사항 참조

#### 응답 DTO와 저장 모델을 분리하고 저장 모델에만 버전을 붙임

- **문제**: preview를 DB에 넣고 나중에 읽어야 하는데, 그 사이 코드가 바뀐다
- **선택**: 저장 모델 `StoredImportPreview`에 `schemaVersion: 1`을 두고,
  역직렬화에서 버전이 다르면 명시적으로 거절한다. 응답 DTO는 따로 둔다
- **대안**: 응답 DTO를 그대로 저장 — 응답 필드를 바꾸는 순간 저장된 preview를 못 읽는다.
  버전 없이 저장 — 못 읽는 이유가 파싱 오류로만 드러나 원인을 알 수 없다
- **트레이드오프**: 같은 정보를 두 모델로 유지해야 한다
- ⭐ **볼트 승격 권장** — 후속 commit · history 이슈가 모두 이 저장 계약 위에 선다

#### blocker를 행이 아니라 code 단위로 접어서 응답

- **문제**: 주최 하나가 등록되지 않으면 그 주최의 모든 축제 행이 blocker를 단다
- **선택**: code별로 건수와 값 목록(중복 제거)을 집계해 내려준다
- **대안**: 행마다 blocker를 그대로 나열 — 화면이 같은 메시지로 도배되고,
  관리자가 실제로 해야 할 일("이 주최를 먼저 등록하라")이 묻힌다
- **트레이드오프**: 어느 행이 걸렸는지는 `blockers`가 아니라 `rows`에서 찾아야 한다

#### 신규 Artist는 CSV 값과 무관하게 `needsReview = true`

- **문제**: `artists.csv`에 `needs_review` 열이 있는데 신규 생성 시 이 값을 따를지
- **선택**: 매칭 상태가 `NEW`면 CSV 값을 무시하고 무조건 `true`. 기존 Artist 갱신에서는 CSV 값을 쓴다
- **대안**: CSV 값을 그대로 신뢰 — crawler가 `false`를 넣으면 사람이 한 번도 안 본 아티스트가
  검토 대기열을 건너뛴다
- **트레이드오프**: CSV의 `needs_review` 열이 신규 행에서는 검증만 되고 쓰이지 않는다.
  열을 읽는 사람은 그 값이 반영된다고 기대하기 쉽다

### 📌 참고사항

**`uploadedByAdmin`이 항상 `null`로 저장된다.**
이슈의 완료 조건은 "`ImportBatch`가 요청 유형, 파일명, conflict policy, preview, **업로더**,
uploadedAt, expiresAt과 함께 저장된다"인데, 서비스가 `.uploadedByAdmin(null)`을 하드코딩한다.
`/admin/**`는 JWT 인증을 요구하므로 관리자 신원이 SecurityContext에 이미 있다.
후속 history 이슈(#41)가 "누가 올렸나"를 보여주려면 이 자리를 채워야 하고,
그때 과거 batch는 전부 null로 남는다.

**`uploadedAt`을 컨트롤러가 `Instant.now()`로 직접 만든다.**
"`uploadedAt`은 auditing이 아니라 Service가 전달한다"는 계약은 서비스가 파라미터로 받으므로 지켜졌다.
다만 값의 출처가 주입 불가능한 `Instant.now()`라 **만료 30분 경계를 테스트에서 고정할 수 없다.**
이미 `global/config/ClockConfig`의 `clock` 빈이 있으므로(#27), 이를 주입받으면
만료를 정하는 시계와 나중에 만료를 판정하는 시계가 같은 기준이 된다.

**`flag != OK` 행의 원본 값은 검증을 통과한 적이 없다.**
`FETCH_FAILED` 같은 행은 `start_date` · `end_date`를 한 번도 파싱하지 않고 SKIP이 된다.
`normalized`의 날짜는 null이지만 `payload`에는 CSV 원문이 그대로 들어 있고, SKIP도 감사 대상이라
저장된다. 후속 commit이 `payload`를 파싱하면 검증되지 않은 문자열을 만나고,
날짜 형식이 어긋나면 `DateTimeParseException`이 잡히지 않고 올라가 전체 rollback이 될 수 있다.
preview 단계에서 flag와 무관하게 **날짜 형식만은 검증**하거나, commit 쪽 파싱이 실패를 흡수해야 한다.

**`PreviewJsonCodec`이 `FestaException` 밖의 예외를 던진다.**
직렬화 실패는 `IllegalStateException`, 역직렬화 실패와 미지원 `schemaVersion`은
`IllegalArgumentException`이다. `GlobalExceptionHandler`가 `FestaException`은 `warn` + 코드 상태로,
나머지는 `error` + 500으로 가르기 때문에 **미지원 schemaVersion이 500 + error 로그로 나간다.**
버전이 안 맞는 preview는 우리 버그가 아니라 오래된 데이터이므로 도메인 에러 코드가 어울린다.

`ImportBatch` 저장도 마찬가지라 `preview` text 컬럼과 `NOT NULL` `expiresAt`,
`fileNames` 컬렉션 매핑이 실물 DB를 통과한 적이 없다.
같은 날 머지된 #34가 `PostgresTestSupport`를 상속한 `HostRepositoryCoverageQueryTest`로
네이티브 쿼리를 실제 PostgreSQL에 대고 검증했으므로, 필요한 기반은 이미 저장소에 있다.
