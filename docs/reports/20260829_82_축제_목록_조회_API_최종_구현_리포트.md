# 축제 목록 조회 API 최종 구현 리포트

## 작업 개요

Issue #82와 PR #93을 통해 공개 축제 목록 조회 API를 구현했다. 헤더 메뉴의 전체 목록, 아티스트 출연 이력의 더 보기, 주최별 축제 목록이 `GET /api/festivals` 하나를 필터와 정렬 조합으로 재사용한다.

이 리포트는 PR 초안이 아니라 최신 `develop`의 merge commit `53d3dd84fd4ff31d32d16d2a7543a40f59e95631`에 반영된 코드, 최종 review thread와 GitHub Actions 결과를 기준으로 작성했다.

- 관련 Issue: #82
- 관련 PR: #93
- 최종 PR head: `80549ff5439f5eb1d5fc4786e08c01c203f3843f`
- develop merge commit: `53d3dd84fd4ff31d32d16d2a7543a40f59e95631`

## 구현 범위

- 인증이 필요 없는 `GET /api/festivals` 추가
- `hostId`, `year`, `artistId`, `status`, `q` 필터 구현
- `LATEST`와 `UPCOMING` 정렬, `page`와 `size` 페이지네이션 구현
- 발행된 축제와 주최가 연결된 축제만 공개 목록에 노출
- 프로젝트 공통 `PageResponse`와 축제 카드용 `FestivalListItemResponse` 사용
- 목록 파라미터별 400 오류 계약과 `FESTIVAL_INVALID_FILTER`, `FESTIVAL_INVALID_STATUS_TYPE` 추가
- KST 오늘 기준 진행 상태 판정과 LIKE 와일드카드 이스케이프 적용
- Controller 계약 테스트 7개 추가, 실물 Postgres 기반 서비스 테스트 22개 추가

## API 계약

### 요청

`GET /api/festivals`

| 파라미터 | 계약 |
| --- | --- |
| `hostId` | 해당 주최의 축제만 조회 |
| `year` | `startDate`가 해당 연도에 속하는 축제만 조회 |
| `artistId` | 해당 아티스트가 라인업에 포함된 축제만 조회 |
| `status` | `UPCOMING`, `ONGOING`, `ENDED`; KST 오늘 기준 필터 |
| `q` | 축제 이름 부분 일치, 대소문자 무시, `%`·`_`는 리터럴 검색 |
| `sort` | `LATEST` 기본값 또는 `UPCOMING` |
| `page` | 0부터 시작, 기본값 0 |
| `size` | 1~50, 기본값 20 |

필터는 조합할 수 있으며, 이 PR에서는 실제 화면이 함께 보내지 않는 `artistId`와 `hostId`의 동시 지정 거부 계약을 만들지 않았다.

### 응답

응답은 공통 `PageResponse<FestivalListItemResponse>`를 사용한다.

- 축제: `festivalId`, `name`, `startDate`, `endDate`, `imageUrl`
- 주최 요약: `id`, `name`, `logoUrl`
- 페이지 정보: `items`, `page`, `size`, `totalElements`, `totalPages`, `last`

목록 카드에서 사용 근거가 확인되지 않은 `venueName`은 싣지 않았다. `FestivalRecentResponse`와 현재 필드 구성이 같아도 화면별 계약이 독립적으로 바뀔 수 있으므로 목록 전용 DTO를 유지했다.

## 필터와 정렬

공개 목록은 `published_at IS NOT NULL`이고 주최가 연결된 축제만 반환한다. `artistId` 필터는 라인업 `EXISTS` 서브쿼리를 사용해 같은 아티스트가 여러 일차에 출연해도 축제가 중복되지 않는다.

`year`는 `startDate >= yearStart AND startDate < nextYearStart`의 반개구간으로 처리해 연도 경계를 넘지 않는다. `year`가 숫자로 변환되더라도 `LocalDate` 범위를 벗어나면 500이 아니라 `FESTIVAL_INVALID_FILTER` 400을 반환한다.

정렬 계약은 다음과 같다.

- `LATEST`: `published_at` 내림차순, 동점은 `id` 오름차순
- `UPCOMING`: `start_date` 오름차순, 동점은 `id` 오름차순

`sort=UPCOMING`은 날짜순으로 정렬만 하고 과거 축제를 제거하지 않는다. 과거 축제만 존재하는 주최별 이력 화면도 목록을 유지해야 하기 때문이다. 날짜로 거르는 것은 `status=UPCOMING`과 홈 전용 `/api/festivals/upcoming`의 역할이다.

## 진행 상태와 검색어 처리

진행 상태는 `LocalDate.now(clock.withZone(Asia/Seoul))`로 계산한 KST 오늘을 기준으로 판정한다.

- `UPCOMING`: `startDate > today`
- `ONGOING`: `startDate <= today <= endDate`
- `ENDED`: `endDate < today`

시작일과 종료일 양끝을 포함하므로 오늘 시작하거나 오늘 종료하는 축제는 `ONGOING`이다. `sort`와 `status`에 같은 `UPCOMING` 어휘가 있지만, 전자는 순서만 정하고 후자는 결과를 필터링한다. 이 차이는 Swagger 설명과 테스트에 함께 고정했다.

검색어 `q`는 앞뒤 공백을 제거하고 빈 문자열이면 미지정과 같이 처리한다. PostgreSQL LIKE의 `%`, `_`, `\`를 이스케이프하고 query의 `ESCAPE '\\'` 절과 함께 사용해 `?q=%`나 `?q=_`가 전체 결과를 반환하지 않게 했다.

## 파라미터 오류 계약

기존 `FestivalController`의 로컬 타입 불일치 핸들러는 파라미터 이름을 보지 않고 모두 `FESTIVAL_INVALID_LIMIT`으로 변환했다. 목록 파라미터가 추가된 뒤에는 이름별로 다음 오류를 반환하도록 수정했다.

| 요청 | 오류 코드 |
| --- | --- |
| `limit` 타입 불일치 | `FESTIVAL_INVALID_LIMIT` |
| `page` 타입 불일치 또는 음수 | `INVALID_PAGE` |
| `size` 타입 불일치 또는 1~50 밖 | `INVALID_PAGE_SIZE` |
| `hostId`, `year`, `artistId` 타입·범위 오류 | `FESTIVAL_INVALID_FILTER` |
| `status` 허용값 밖 | `FESTIVAL_INVALID_STATUS_TYPE` |

로컬 핸들러가 모르는 파라미터는 전역 `GlobalExceptionHandler`에 위임한다. 따라서 후속 #83이 추가할 `/api/festivals/{id}`의 경로 변수 타입 오류도 기존 공개 API와 같은 `INVALID_PATH_VARIABLE` 계약을 재사용한다.

## 리뷰 반영 내용

### `status`와 `q` 필터 누락 보완

- 지적: Issue #82 범위의 `status`와 `q`가 Controller에 선언되지 않아 클라이언트가 보내도 Spring MVC가 조용히 무시하고 전체 목록을 200으로 반환할 수 있었다.
- 반영: commit `d40acc38f84cfc7c4aef4e948228f6506fa1c13c`에서 두 파라미터, `FestivalStatus`, KST 상태 predicate와 축제 이름 검색을 구현했다.
- 검증: 상태별 경계, `sort`와 `status`의 역할 차이, 대소문자 무시, `%`·`_` 리터럴 검색, 공백 검색어를 서비스 테스트로 추가했다.

### 과대 `year`의 500 방지

- 지적: `year`가 정수로는 파싱되지만 `LocalDate` 범위를 벗어나면 `LocalDate.of()`의 `DateTimeException`이 500으로 전파될 수 있었다.
- 반영: 같은 commit `d40acc38f84cfc7c4aef4e948228f6506fa1c13c`에서 날짜 범위 오류를 `FESTIVAL_INVALID_FILTER` 400으로 변환했다.
- 검증: `year=2000000000` 경계 테스트를 추가했다.

### Controller 400 계약 보강

최종 commit `80549ff5439f5eb1d5fc4786e08c01c203f3843f`에서 서비스 테스트가 지나가지 않는 실제 HTTP 바인딩 경로를 보강했다.

- `?year=abc`, `?page=abc`, `?size=abc`의 이름별 오류 코드
- `?status=abc`의 `FESTIVAL_INVALID_STATUS_TYPE`
- 빈 `status`는 미지정과 같이 200
- `q` 원문이 Controller에서 변형되지 않고 서비스로 전달됨
- 응답 JSON의 축제·주최 요약 필드
- Controller가 모르는 타입 불일치는 전역 핸들러로 위임

리뷰 지적 2건은 모두 최종 코드와 테스트에 반영됐으며 의도적으로 미반영한 review finding은 없다.

## 제한사항 및 후속 작업

- 축제 상세 조회는 Issue #83으로 분리돼 있다. 같은 `FestivalController`와 `FestivalService`를 수정하므로 최신 `develop` 리베이스가 필요하다.
- 관리자·공개 enum 이름 규칙 통일은 Issue #97로 분리돼 있다. #83과 관련 작업이 머지된 뒤 순수 리네임으로 진행한다.
- `q` 길이 상한, 공통 LIKE 이스케이프 유틸 추출, 관리자 축제·아티스트 목록의 `%`·`_` 처리 판정은 Issue #98로 분리돼 있다.
- `FestivalAdminService.findAll`의 과대 `year`는 여전히 500이 될 수 있다. 관리자 엔드포인트의 별도 후속 범위다.
- `FESTIVAL_CONFLICTING_FILTER`는 실제로 `artistId`와 `hostId`를 함께 보내는 화면이 없어 구현하지 않았다.
- 인기순 정렬은 인기 지표가 없어 범위 밖으로 유지했다.
- `sort=UPCOMING`과 `status=UPCOMING`의 어휘 중복을 없애려면 프론트 동시 변경이 필요하다. 프론트가 status 필터 UI를 붙일 때 `sort=START_DATE` 전환을 함께 검토한다.
