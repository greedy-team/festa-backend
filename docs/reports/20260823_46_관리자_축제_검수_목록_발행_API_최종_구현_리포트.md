# 관리자 축제 검수 목록·발행 API 최종 구현 리포트

## 작업 개요

Issue #46과 PR #55를 통해 관리자가 미발행 축제를 포함한 검수 목록을 조회하고 개별 축제를 발행하거나
발행 해제할 수 있는 API를 구현했다. 이 리포트는 PR 초안이 아니라 `develop`에 반영된 merge commit
`7bbbc31babe6ca821dea423781e6727c4025c3cf`의 실제 코드를 기준으로 작성했다.

- 관련 Issue: `#46` — 관리자 축제 검수 목록·발행 API 추가
- 관련 PR: `#55` — 관리자 축제 검수 목록·발행 API 추가
- 최종 PR head: `e8ce6a4e5671aa4309c2e6097074afdaf8673874`
- merge 직전 develop: `279dd86d0f070fba3cef9cd88009148370824cd3`
- develop merge commit: `7bbbc31babe6ca821dea423781e6727c4025c3cf`

## 구현 범위

- `GET /admin/festivals` 관리자 검수 목록 추가
- `POST /admin/festivals/{id}/publish` 개별 발행 추가
- `DELETE /admin/festivals/{id}/publish` 개별 발행 해제 추가
- 라인업, 주최, 좌표를 확인하는 발행 blocker 3종 추가
- 목록과 발행에서 동일한 blocker 판정 로직 사용
- `publishedAt` 기반 발행 상태와 순차적 멱등 처리
- 목록 filter, sorting, pagination과 전용 오류 코드 추가
- 기존 Festival coverage API와 공통 `ClockConfig` 보존

## 주요 구현 내용

### 관리자 검수 목록

`FestivalRepository.findReviewRows`가 Festival, Host, Lineup을 조회하고 Lineup 수를 집계한다. Lineup은
`LEFT JOIN`으로 연결해 Lineup이 없는 Festival도 조회 대상이 되는 형태로 작성했다. Service는 조회 결과의
Host 연결 여부, 좌표, `lineupCount`를 `FestivalPublishBlocker.evaluate`에 전달해 목록의 `blockers`를
계산한다.

응답은 Entity를 직접 노출하지 않고 `FestivalReviewItem`과 공통 `PageResponse`를 사용한다. 검수 행에는
Festival 식별자와 import 정보, 이름, Host, 기간, `publishedAt`, 수집 경로, 원본 URL, Lineup 수,
import 시각, blocker 목록이 포함된다.

### 개별 발행과 발행 해제

- 발행은 Festival을 조회하고 이미 `publishedAt`이 있으면 기존 시각을 유지한 채 성공한다.
- 미발행 Festival은 Lineup 수와 Host·좌표 상태를 검증한 뒤 공통 `Clock`의 현재 시각으로 발행한다.
- 발행 해제는 `publishedAt`을 null로 변경하고 변경된 상태를 응답한다.
- 이미 미발행인 Festival의 발행 해제도 성공하므로 순차 요청에 대해 멱등이다.
- 없는 Festival은 발행과 발행 해제 모두 `FESTIVAL_NOT_FOUND`로 실패한다.
- 조회는 read-only transaction, 발행과 발행 해제는 write transaction에서 실행한다.

### 기존 develop 기능 보존

PR에서 최신 develop을 반영하며 `FestivalAdminController`와 `FestivalErrorCode`의 충돌을 정리했다.
최종 Controller에는 검수 목록·발행 API와 기존 `/admin/festivals/coverage`가 함께 남아 있다. coverage용
오류 코드와 발행용 오류 코드도 모두 보존했으며, Festival service는 develop의 공통 `ClockConfig`를
사용해 중복 `Clock` Bean을 만들지 않는다.

## API 계약

세 API는 기존 Security 설정에 따라 인증된 관리자 요청을 요구한다.

### GET /admin/festivals

미발행 Festival을 포함한 관리자 검수 목록을 조회한다.

요청 query parameter:

| 필드 | 타입 | 기본값 | 설명 |
| --- | --- | --- | --- |
| `published` | Boolean | 전체 | `true`는 발행, `false`는 미발행 |
| `hostId` | Long | 전체 | 연결된 Host ID |
| `year` | Integer | 전체 | `startDate`가 해당 연도에 속한 Festival |
| `q` | String | 전체 | Festival 이름 대소문자 무시 부분 검색 |
| `discovery` | String | 전체 | 수집 경로 정확히 일치 |
| `sort` | String | `IMPORTED_DESC` | `IMPORTED_DESC` 또는 `START_DATE` |
| `page` | int | `0` | 0부터 시작하는 페이지 번호 |
| `size` | int | `20` | 1~50 |

응답은 `PageResponse<FestivalReviewItem>`이다.

| 필드 | 설명 |
| --- | --- |
| `items` | 현재 페이지의 Festival 검수 행 |
| `page`, `size` | 현재 페이지와 페이지 크기 |
| `totalElements`, `totalPages` | 전체 행 수와 페이지 수 |
| `hasNext`, `hasPrevious` | 다음·이전 페이지 존재 여부 |

검수 행은 `festivalId`, `importKey`, `name`, `hostId`, `hostName`, `startDate`, `endDate`,
`publishedAt`, `discovery`, `sourceUrl`, `lineupCount`, `importedAt`, `blockers`를 제공한다.

### POST /admin/festivals/{id}/publish

발행 조건을 만족하는 Festival을 발행한다. 성공 응답은 `FestivalPublishResponse`이며 `festivalId`,
`name`, `publishedAt`을 제공한다. 이미 발행된 Festival은 blocker를 다시 평가하지 않고 기존
`publishedAt`을 유지한다.

발행을 막는 첫 조건은 HTTP 400과 다음 전용 코드 중 하나로 반환한다.

| blocker | 오류 코드 |
| --- | --- |
| `LINEUP_EMPTY` | `FESTIVAL_PUBLISH_LINEUP_EMPTY` |
| `HOST_NOT_LINKED` | `FESTIVAL_PUBLISH_HOST_NOT_LINKED` |
| `COORDINATES_MISSING` | `FESTIVAL_PUBLISH_COORDINATES_MISSING` |

여러 조건을 동시에 위반하면 Lineup → Host → 좌표 순서에서 첫 오류를 반환한다. 전체 조건은 목록 행의
`blockers`에서 확인할 수 있다.

### DELETE /admin/festivals/{id}/publish

Festival의 발행을 해제한다. 삭제 API가 아니라 상태 변경 API이므로 204 대신 발행과 동일한
`FestivalPublishResponse`를 반환한다. 성공 응답의 `publishedAt`은 null이다. 별도 `unpublishedAt`이나
최초 발행 이력은 저장하지 않는다.

## 발행 가능 여부와 blocker 판정

발행 가능 여부는 `FestivalPublishBlocker.evaluate` 한 곳에서 판정한다.

| 조건 | blocker | 판정 |
| --- | --- | --- |
| Lineup 0건 | `LINEUP_EMPTY` | `lineupCount == 0` |
| Host 미연결 | `HOST_NOT_LINKED` | Host가 null |
| 좌표 누락 | `COORDINATES_MISSING` | latitude 또는 longitude 중 하나라도 null |

목록은 위반한 모든 blocker를 반환하고, 발행은 같은 목록에서 첫 blocker를 오류 코드로 변환한다. 이 구조로
목록이 보여주는 발행 불가 사유와 실제 발행 요청을 막는 조건이 갈리지 않도록 했다.

## publishedAt 기반 발행 상태 계약

최종 계약은 `publishedAt` 단독 표현이다.

- `publishedAt != null`: 발행
- `publishedAt == null`: 미발행
- 별도 `published` boolean은 제공하지 않는다.
- Festival 검수 행에 Host 단위 coverage 상태인 `FestivalCoverageStatus`를 재사용하지 않는다.
- 검수 화면의 상태는 `publishedAt`과 `blockers` 조합으로 표현한다.
- `FestivalCoverageStatus`는 `/admin/festivals/coverage` 응답에만 사용한다.

PR 중간에 `published` boolean을 추가한 커밋이 있었지만 최종 결정에 따라 되돌렸고, Issue 문서에는 초기
제안을 보존한 채 최종 구현 결정 섹션을 추가했다.

## pagination, sorting, filter 계약

- 기본 pagination은 `page=0`, `size=20`이다.
- `page < 0`은 `INVALID_PAGE`, `size < 1` 또는 `size > 50`은 `INVALID_PAGE_SIZE`다.
- 잘못된 sort 값은 `FESTIVAL_INVALID_SORT_TYPE`이다.
- `IMPORTED_DESC`는 `importedAt DESC NULLS LAST`, `START_DATE`는 `startDate ASC`다.
- 두 정렬 모두 동일한 값에서 `id ASC`를 추가해 페이지 순서를 안정화한다.
- `published`, `hostId`, `year`, `q`, `discovery` filter를 선택적으로 조합할 수 있다.
- `published`는 별도 boolean 컬럼이 아니라 `publishedAt`의 null 여부로 판정한다.
- content query와 count query에 동일한 filter 조건을 적용한다.

## 리뷰 반영 내용

- 최신 develop과 충돌하던 `FestivalAdminController`와 `FestivalErrorCode`를 정리해 coverage와 검수·발행
  기능을 모두 보존했다.
- develop의 공통 `ClockConfig`를 사용해 중복 Bean과 Spring context 기동 문제를 피했다.
- `HealthEndpointSecurityTest`와 `SwaggerDisabledByDefaultTest`에 `FestivalRepository` mock을 연결해
  최신 context 구성을 반영했다.
- 응답의 `published` 중복 필드를 제거하고 `publishedAt` 단독 계약을 최종 선택했다.
- Host 단위 `FestivalCoverageStatus`를 검수 행에 재사용하지 않고 `publishedAt + blockers`로 계약을
  분리했다.
- publish/unpublish 동시성 제어는 관리자 전용 기능의 낮은 경합 가능성을 고려해 별도 Issue로 분리했다.
- Festival 목록 Repository의 실제 PostgreSQL 검증은 PR 범위 확대를 고려해 별도 Issue로 분리했다.
- 신규 검수·발행 Controller 계약 테스트는 추가하지 않았으며 non-blocking 후속 보강 대상으로 남겼다.

## 제한사항 및 후속 작업

### Festival publish/unpublish 동시성

현재 발행과 발행 해제는 일반 `findById`를 사용하며 비관적 잠금이나 `@Version`을 사용하지 않는다. 동일
Festival에 동시 요청이 들어오면 두 transaction이 같은 이전 상태를 읽어 `publishedAt` 멱등성이 깨지거나
응답과 최종 DB 상태가 달라질 수 있다. 관리자 전용 기능이라 실제 경합 가능성은 낮지만, 다음 내용을 별도
Issue로 후속 관리할 예정이다. 현재 직접 대응하는 Issue 번호는 없다.

- Festival 상태 변경용 잠금 또는 optimistic locking 정책
- 동시 publish의 기존 `publishedAt` 유지
- publish/unpublish 경합 시 최종 상태와 응답 정합성
- 실제 PostgreSQL 동시 요청 테스트

### Festival 관리자 목록 PostgreSQL 통합 테스트

`findReviewRows`는 `LEFT JOIN`, `GROUP BY`, `COUNT`, 별도 `countQuery`, pagination을 함께 사용하지만
이번 PR에는 해당 query를 실제 PostgreSQL에서 실행하는 테스트가 없다. 다음 항목을 별도 Issue로 후속
관리할 예정이다. 현재 직접 대응하는 Issue 번호는 없다.

- Lineup 0건 Festival도 조회되는지
- `lineupCount` 정확성
- Host null과 좌표 null 조합의 blocker
- published, year, host, discovery, 검색어 filter
- `totalElements`와 `totalPages`
- 여러 페이지의 pagination
- 동일 sort key에서 ID tie-break가 유지되는지

### Controller 계약 테스트

검수 목록의 `PageResponse`, publish/unpublish 성공, 잘못된 sort/page/size, blocker의 HTTP status와
`errorCode`를 직접 검증하는 Controller 테스트는 없다. 핵심 Service 단위 테스트와 전체 Spring context
검증은 통과했지만 HTTP 계약 회귀 방지를 위해 후속 테스트 보강이 권장된다.
