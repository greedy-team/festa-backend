# 주최 상세 조회 API 최종 구현 리포트

## 작업 개요

Issue #79와 PR #80을 통해 공개 주최 상세 조회 API를 구현했다. 주최 기본 정보와 발행된 축제를 기준으로 한 연도, 예정 축제, 지난 축제 이력, 자주 출연한 아티스트를 한 응답으로 제공한다.

이 리포트는 PR 초안이 아니라 최신 `develop`의 merge commit `b919873bce8a1c8f744d5f68651c0d57935ce1dc`에 반영된 코드, 최종 review thread와 GitHub Actions 결과를 기준으로 작성했다.

- 관련 Issue: #79
- 관련 PR: #80
- 최종 PR head: `ea7b9d6ecc5aa7769f66165f3ab1520c0764acb5`
- develop merge commit: `b919873bce8a1c8f744d5f68651c0d57935ce1dc`

## 구현 범위

- 인증이 필요 없는 `GET /api/hosts/{id}` 추가
- 주최 기본 정보와 `homepageUrl`을 포함하는 상세 응답 DTO 추가
- 발행된 축제만 대상으로 `availableYears`, `upcomingFestivals`, `festivalHistory` 구성
- 종료된 발행 축제 라인업을 기준으로 자주 출연한 아티스트 상위 3명 집계
- KST 기준의 `today`와 양수형 남은 일수 `dday` 계산
- 기존 관리자 전용 `HostService`를 `HostAdminService`로 분리하고 공개 조회 서비스에 `HostService` 이름 사용
- 숫자가 아닌 경로 변수의 `INVALID_PATH_VARIABLE` 400 공통 계약 구현
- 공개 Controller 계약 테스트 2개와 실물 Postgres 기반 서비스 테스트 4개 추가

## API 계약

### 요청

`GET /api/hosts/{id}`

- 공개 API이며 JWT 인증을 요구하지 않는다.
- 존재하지 않는 주최 ID는 `HOST_NOT_FOUND` 404를 반환한다.
- 숫자로 변환할 수 없는 ID는 `INVALID_PATH_VARIABLE` 400을 반환한다.

### 응답

응답은 다음 항목으로 구성된다.

- 주최 기본 정보: `id`, `name`, nullable `shortName`, `region`, `logoUrl`, `bannerUrl`, `homepageUrl`
- `availableYears`: 발행된 모든 축제의 시작 연도 중복 제거, 내림차순
- `upcomingFestivals`: `endDate >= today`인 발행 축제, `startDate`와 `festivalId` 오름차순
- `festivalHistory.items`: `endDate < today`인 발행 축제 중 최신 2건
- `festivalHistory.total`: 2건으로 자르기 전 종료 축제 전체 개수
- `frequentArtists`: 종료된 발행 축제 라인업의 출연 횟수 상위 3명

명세 초안과 달리 `type`과 `rank`는 응답에 두지 않는다. `type`은 엔티티와 확정 ERD에 값의 근거가 없고, `rank`는 배열 순서에서 파생되는 값이기 때문이다. 아티스트 이미지 필드명은 프로젝트의 현재 계약에 맞춰 `imageUrl`을 사용한다.

## 공개 범위와 발행 경계

네 파생 섹션은 모두 `published_at IS NOT NULL`인 축제만 사용한다. 미발행 축제는 예정 목록, 이력, 이력 전체 개수, 연도와 자주 출연한 아티스트 집계 어디에도 노출되지 않는다.

예정과 이력은 종료일을 기준으로 서로 겹치지 않게 나눈다.

- 오늘 종료되는 축제: 예정 축제
- 어제까지 종료된 축제: 이력
- 자주 출연한 아티스트: 종료된 발행 축제만 집계
- `artist_id IS NULL`인 시크릿 게스트 라인업: 집계 제외

자주 출연한 아티스트는 출연 횟수 내림차순, 동점은 `artistId` 오름차순으로 정렬한다. 배열 순서가 곧 순위 계약이며 `rank` 필드는 별도로 만들지 않는다.

## KST 기준 날짜와 dday

서비스는 한 요청을 처리할 때 `LocalDate.now(clock.withZone(Asia/Seoul))`로 `today`를 한 번 계산하고 모든 분류와 집계에 같은 값을 사용한다. DB의 `CURRENT_DATE`에 의존하지 않으므로 서버와 DB 타임존이 달라도 KST 00:00~09:00 구간에서 예정/이력 경계와 `dday`가 하루 어긋나지 않는다.

`dday`는 `startDate - today`로 계산한다.

- 시작 전: 양수
- 당일: 0
- 진행 중: 음수

이는 프론트엔드의 현재 `formatDday` 계약과 일치한다. 기존 `ArtistRepository`의 다른 공개 조회용 `CURRENT_DATE` 3곳은 이번 PR 범위 밖이라 변경하지 않았고, 신규 주최 집계 query에는 명시적인 `today` 파라미터를 사용했다.

## 관리자 서비스 분리

기존 `HostService`는 이름과 달리 `HostAdminController`에서만 사용되는 관리자 등록·목록·수정 서비스였다. PR #80에서 이를 `HostAdminService`로 옮기고 기존 관리자 동작과 테스트를 보존했다. 새 `HostService`는 공개 상세 조회만 담당한다.

이로써 Issue #57에서 정한 `<도메인>AdminService` 명명 규칙이 주최 도메인에 실제 반영됐으며, 공개 API와 관리자 API가 같은 서비스 이름을 두고 충돌하지 않는다. `ArtistService` 분리는 아티스트 공개 API 작업 범위로 남겼다.

## 리뷰 반영 내용

### 숫자가 아닌 경로 변수의 400 계약

- 지적: Issue #79는 숫자가 아닌 `{id}`에 `INVALID_PATH_VARIABLE` 400을 요구했지만, 최초 구현에서는 Spring의 `MethodArgumentTypeMismatchException`이 공통 예외 처리로 들어가 500이 반환됐다.
- 반영: commit `ea7b9d6ecc5aa7769f66165f3ab1520c0764acb5`에서 `GlobalExceptionHandler`가 `@PathVariable` 타입 변환 실패를 식별해 `CommonErrorCode.INVALID_PATH_VARIABLE`로 변환하도록 추가했다.
- 응답 계약: `errorCode=INVALID_PATH_VARIABLE`, `message=경로 변수의 형식이 올바르지 않습니다`, `status=400`, `path=/api/hosts/abc`.
- 범위: 같은 예외를 사용하는 query parameter 타입 불일치는 기존 동작을 유지한다. 이번 계약은 경로 변수에만 적용한다.

### Controller 계약 테스트

`HostControllerTest`에 다음 Web MVC 테스트 2개를 추가했다.

- `/api/hosts/abc`가 400과 정확한 `ErrorResponse`를 반환한다.
- 타입 변환 실패가 Controller argument 바인딩 단계에서 처리되어 `HostService`에는 호출이 전달되지 않는다.

리뷰 전 head `2d82b300`과 비교하면 이 반영으로 테스트 36개와 suite/file 6개가 늘었다. 최종 head의 전체 280개 테스트가 모두 통과해 공통 예외 처리 변경의 회귀도 함께 검증됐다.

의도적으로 미반영한 review finding은 없다.

## 제한사항 및 후속 작업

- 공개 주최 목록과 주최별 전체 축제 목록은 구현하지 않았다. 후자는 공개 축제 목록 API의 `hostId` 필터 범위다.
- 프론트엔드 목과 타입에 남은 `type`, `rank`, `shortName` non-null 계약은 별도 프론트 작업에서 정리해야 한다.
- 노션 API 명세의 `dday` 부호, `photoUrl`, `homepageUrl`, `rank` 차이는 이번 백엔드 PR에서 수정하지 않았다.
- `ArtistRepository`의 기존 `CURRENT_DATE` 기반 집계 3곳은 별도 작업에서 KST 기준으로 통일해야 한다.
- 상세 응답은 한 주최의 발행 축제를 메모리에서 분류한다. 데이터 규모가 커져 성능 문제가 확인되면 집계 query 분리를 검토한다.
