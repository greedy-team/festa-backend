# Issue/PR 템플릿 본문 구조 통일 최종 구현 리포트

## 작업 개요

Issue #73과 PR #74를 통해 `festa-backend`의 Pull Request 템플릿과 Issue 템플릿 5종을 현재 FESTA 작성 규칙에 맞게 정리했다. 템플릿마다 달랐던 제목과 작성 항목을 공통 구조로 맞추면서도, 버그·기능·리팩토링·설정·문서 유형별로 실제 작성 시 필요한 정보는 유지했다.

이 리포트는 PR 초안이 아니라 최신 `develop`의 merge commit `03aa2acd86a47a88e35afce67750e296f7773028`에 반영된 파일과 최종 review thread를 기준으로 작성했다.

- 관련 Issue: #73
- 관련 PR: #74
- 최종 PR head: `575cc65e2bd41c6c1330660b3baa867201be406b`
- develop merge commit: `03aa2acd86a47a88e35afce67750e296f7773028`

## 구현 범위

- `.github/PULL_REQUEST_TEMPLATE.md`의 본문 구조 통일
- `.github/ISSUE_TEMPLATE/` 아래 버그·기능·리팩토링·설정·문서 템플릿 5종 정리
- 각 Issue 템플릿의 YAML frontmatter, 기본 제목, assignee와 `type:` 라벨 유지
- 기존 브랜치명 기반 Issue 자동 종료 방식 유지
- 리뷰에서 확인된 유형별 필수 정보 복원 및 안내 문구 보완

애플리케이션 코드와 런타임 설정은 변경하지 않았다.

## Pull Request 템플릿 최종 구조

최종 PR 템플릿은 작업 성격별로 첫 제목을 선택하게 하지 않고 다음 네 섹션으로 고정했다.

1. `✨ 변경 사항`
2. `✅ 테스트`
3. `📌 리뷰어가 알아야 할 것`
4. `🔗 관련된 이슈`

신규 구현과 기존 기능 수정 모두 `변경 사항`에 작성한다. 최초 계획의 `✨ 변경 사항` / `✨ 구현 사항` 선택 방식은 작성자가 불필요한 제목을 직접 지워야 하고 실제 사용에서 누락되기 쉽다는 리뷰를 반영해 단일 제목으로 정리했다.

관련 Issue에는 `Closes #N`이 아니라 `#N`만 작성한다. 작업 PR은 `develop`으로 병합되어 GitHub closing keyword가 동작하지 않고, Issue 종료는 브랜치명에서 번호를 추출하는 `PROJECT-COMMON-CLOSE-ISSUE-ON-MERGE`가 담당한다는 근거를 템플릿 주석에 남겼다. 실제로 PR #74 병합 뒤 해당 workflow가 Issue #73을 자동으로 종료했다.

## Issue 템플릿 최종 구조

기능·리팩토링·설정·문서 템플릿은 다음 네 섹션을 공통 골격으로 사용한다.

1. `🔍 현재 문제점`
2. `💡 해결 방안 / 제안 기능`
3. `🔧 작업 내용`
4. `👤 담당자`

유형별 의미가 달라야 하는 항목은 공통 제목 아래 안내 문구로 구분했다.

- 기능: 부족한 기능, 구체적인 해결 방안, 구현 작업 항목
- 리팩토링: 현재 구조의 문제, 외부 동작을 바꾸지 않는 개선 방향, 필요한 작업 항목
- 설정: 설정·빌드·CI/CD 문제, 적용할 설정과 별도로 구분한 영향 범위, 필요한 작업 항목
- 문서: 없거나 낡은 문서, 수정할 위치와 담을 내용, 문서 작업 항목

버그 템플릿은 문제를 등록하는 시점에 해결 작업을 모두 알기 어렵다는 리뷰를 반영해 공통 네 섹션을 그대로 강제하지 않았다. 최종 구조는 다음과 같다.

1. `🔍 현재 문제점` — 실제 동작과 예상 동작을 분리
2. `🔄 재현 방법` — 번호 스캐폴드 유지
3. `💡 해결 방안` — 선택적으로 작성
4. `📸 참고 자료` — 로그와 스크린샷 첨부 위치
5. `⚙️ 환경 정보` — OS·브라우저·버전 등 필요한 환경
6. `👤 담당자`

버그의 `작업 내용`은 제거했다. 수행한 수정 작업은 구현 전 Issue가 아니라 작업을 마친 PR의 `변경 사항`에 기록한다.

## Frontmatter와 자동화 호환성

Issue 템플릿 5종의 frontmatter는 변경 전후 동일하게 유지했다.

| 템플릿 | 기본 라벨 |
| --- | --- |
| `bug_report.md` | `작업전`, `type: fix` |
| `feature_request.md` | `작업전`, `type: feat` |
| `refactor_request.md` | `작업전`, `type: refactor` |
| `chore_request.md` | `작업전`, `type: chore` |
| `docs_request.md` | `작업전`, `type: docs` |

따라서 Issue Helper가 라벨에서 브랜치 타입을 결정하는 기존 동작과 브랜치명 기반 자동 종료 계약은 유지된다. 담당자 표기는 variation selector나 ZWJ가 들어간 `🙋‍♂️` 대신 단일 code point인 `👤`로 통일했다.

## 리뷰 반영 내용

### 버그 재현 정보 복원

- 지적: 최초 수정안은 재현 단계, 참고 자료, 환경 정보를 한 줄 안내로 합쳐 이후 원인 분석에 필요한 정보가 사라질 수 있었다.
- 반영: 번호가 있는 재현 단계, 로그·스크린샷 첨부 영역, 선택적 환경 정보 영역을 각각 복원했다.
- 추가 정리: 버그 템플릿만 HTML 주석으로 작성돼 있던 안내를 다른 템플릿과 같은 노출형 문장으로 바꿨다.

### 실제 동작·예상 동작과 해결 방안 분리

- 지적: 버그 등록자는 정상적으로 기대한 동작은 알지만 해결 방법은 모를 수 있으므로 두 정보를 한 항목에 묶으면 안 된다.
- 반영: `현재 문제점` 아래에 실제 동작과 예상 동작을 각각 적게 하고, 해결 방안은 별도 선택 항목으로 유지했다.

### 버그 작업 체크리스트 제거

- 지적: Issue 작성 시점에는 실제 수정 작업을 확정하기 어렵고, 수행한 작업은 PR에서 기록하는 편이 정확하다.
- 반영: 버그 템플릿의 `작업 내용` 섹션을 제거했다.

### 리팩토링 외부 동작 안내 복원

- 지적: `외부 동작 변경 없음`은 구현 작업 체크박스가 아니라 검증 결과이며, 동작이 달라질 때 기록할 자리도 필요하다.
- 반영: 체크박스를 제거하고 리팩토링은 원칙적으로 외부 동작을 변경하지 않는다는 안내와 예외 내용을 적는 줄을 복원했다.

### 설정 작업의 영향 범위 분리

- 지적: 설정·빌드 Issue에서는 영향 범위가 핵심인데 해결 방안 안내 문장에 섞이면 누락되기 쉽다.
- 반영: `해결 방안 / 제안 기능` 안에서 적용할 설정과 영향 범위를 별도 불릿으로 나눴다.

### PR 첫 섹션과 Issue 종료 근거 단순화

- 지적: `변경 사항`과 `구현 사항` 중 하나를 직접 선택해 지우는 방식은 사용 마찰이 크다.
- 반영: `변경 사항` 하나로 고정했다.
- 지적: `Closes`를 쓰지 않는 이유가 없으면 나중에 규칙이 되돌아갈 수 있다.
- 반영: develop PR과 브랜치명 기반 자동 종료의 관계를 주석으로 명시했다.

모든 코드 리뷰 지적은 최종 파일에 반영됐다. review thread 일부는 Resolve되지 않은 채 outdated 상태지만, 각 지적에는 반영 답변이 있고 최종 diff에서 변경 내용을 확인했다.

## 제한사항 및 후속 작업

- 이번 PR은 `festa-backend`의 `.github/ISSUE_TEMPLATE/`와 PR 템플릿만 변경했다. Issue #73이 언급한 `festa-frontend`와 `festa-crawler`의 동일 구조 적용 여부는 이 PR에서 검증하거나 변경하지 않았다.
- `PROJECT-COMMON-QA-ISSUE-CREATION-BOT.yaml`의 `qaBody`는 기존 본문 구조를 유지한다. 이 workflow는 backend·frontend·crawler에 바이트 동일하게 배포된 공용 번들이므로 한 저장소에서만 고치지 않고 별도 Issue로 세 저장소를 함께 변경해야 한다.
- 템플릿 내용의 자동 스냅샷 테스트는 없다. 이번 변경은 정적 대조와 리뷰로 검증했다.
- 기존에 생성된 Issue와 PR 본문은 소급 변경되지 않는다.
