### 📌 작업 개요

이슈 #29 머지 후 `develop` 자동 배포가 실패하고 직전 이미지로 롤백되던 문제를 수정했다.
관리자 인증이 요구하는 환경변수 `ADMIN_JWT_SECRET`이 서버 컨테이너까지 전달되지 않아
애플리케이션이 기동하지 못한 것이 원인이었다. CD 워크플로우와 Compose 정의에 전달 경로를
추가하고, 같은 누락이 반복되지 않도록 러너 단계 가드와 `AGENTS.md` 규칙을 함께 넣었다.

### 🔍 문제 분석

**증상.** 배포 워크플로우의 "컨테이너 재기동" 스텝에서 `container festa-app-1 is unhealthy`
후 롤백이 동작했다. 서버는 직전 커밋으로 복구돼 정상 응답했지만, 워크플로우는 exit 1로
종료했고 관리자 인증 기능은 배포되지 않은 상태로 남았다.

**원인.** 이슈 #27 구현이 `application.yml`에 세 개의 설정을 추가했는데, 그중 하나만
기본값이 없다.

```yaml
app:
  admin:
    initial-username: ${ADMIN_INITIAL_USERNAME:}   # 기본값 있음 - 없어도 기동
    initial-password: ${ADMIN_INITIAL_PASSWORD:}   # 기본값 있음 - 없어도 기동
  jwt:
    admin-secret: ${ADMIN_JWT_SECRET}              # 기본값 없음 - 없으면 기동 실패
```

`ADMIN_JWT_SECRET`에 값이 주입되지 않으면 Spring이 플레이스홀더를 해석하지 못해 애플리케이션
컨텍스트 생성 단계에서 기동이 중단된다. `/actuator/health`가 응답하지 않으므로 Compose의
`--wait-timeout 180` 동안 계속 unhealthy로 판정된다.

**전달 경로 점검 결과 세 곳 모두 비어 있었다.**

| 전달 지점 | 수정 전 |
| --- | --- |
| GitHub Environment Secret | 미등록 |
| CD 워크플로우 `env:` · `write_env` | DB 3종 · OAuth 2종 · `JWT_SECRET` · `AES_KEY`만 |
| `deploy/compose.yaml` app 환경변수 | `JWT_SECRET`만 |

이슈 #27 구현은 `.github/`와 `deploy/` 아래 파일을 변경하지 않았다. 따라서 Secret만
등록해도 컨테이너까지 도달하지 않는다.

**CI가 통과한 이유.** 테스트는 이 값을 인라인으로 주입한다
(`SecurityConfigTest`, `HealthEndpointSecurityTest`의 `app.jwt.admin-secret=...`).
환경변수 누락은 실제 배포 전까지 드러날 경로가 없었다.

### ✅ 구현 내용

#### 환경변수 전달 경로 추가

- **파일**: `.github/workflows/PROJECT-SPRING-CD.yaml`
- **변경 내용**: "SSH와 실행 환경 준비" 스텝의 `env:` 블록과 `write_env` 목록에
  `ADMIN_JWT_SECRET` · `ADMIN_INITIAL_USERNAME` · `ADMIN_INITIAL_PASSWORD` 추가
- **이유**: `write_env`가 기록하는 키만 `app.env`에 들어가고, 그 파일이 Compose의
  `--env-file`로 쓰인다. 목록에 없으면 Secret이 있어도 서버에 도달하지 않는다

- **파일**: `deploy/compose.yaml`
- **변경 내용**: app 서비스 `environment:`에 같은 세 개 추가
- **이유**: Compose가 호스트 환경변수를 컨테이너로 넘기는 유일한 지점이다

#### 기동 전 가드 추가

- **파일**: `.github/workflows/PROJECT-SPRING-CD.yaml`
- **변경 내용**: `DB_URL` · `OCI_HOST_KEY` 가드 뒤에 세 개 검사 추가
  - `ADMIN_JWT_SECRET` 누락
  - `ADMIN_INITIAL_USERNAME`만 설정된 경우
  - `ADMIN_INITIAL_PASSWORD`만 설정된 경우
- **이유**: 셋 다 확정적으로 기동 실패를 부르는 조건이다. 러너에서 즉시 중단하면 원인이
  담긴 메시지가 바로 나오고, 이미지 전송과 헬스체크 180초 대기, 롤백까지 가는 경로를
  건너뛴다

#### 배포 문서 정정

- **파일**: `AGENTS.md`
- **변경 내용**: "배포는 아직 구성 전입니다"와 CI/CD 표의 "배포 · 미설정",
  "배포를 붙일 자리는 `main` push입니다" 세 군데를 현재 구성으로 교체.
  `앱에 환경변수를 추가할 때` 절 신설
- **이유**: 이 문서는 저장소의 에이전트 지침 원본이며, 어떤 도구로 열든 세션 시작 시 읽힌다.
  배포가 없다고 안내하는 문서만 읽으면 CD와 Compose를 함께 고쳐야 한다는 사실을 알 수 없다.
  이번 누락의 배경이다

### 🧭 결정 기록 (ADR)

#### 필수 여부를 값의 성격에 따라 다르게 둔다

- **문제**: Compose에서 새 환경변수 세 개를 어떻게 선언할지. `${VAR:?}`는 없으면 즉시
  실패하고, `${VAR:-}`는 빈 값을 허용한다
- **선택**: `ADMIN_JWT_SECRET`만 `:?`(필수), 초기 계정 두 개는 `:-`(빈 값 허용)
- **대안**:
  - **셋 다 필수** — 초기 계정 시딩을 원하지 않는 환경에서 배포가 불가능해진다.
    애플리케이션은 두 값이 모두 비면 시딩만 건너뛰도록 이미 설계돼 있는데 그 여지를 없앤다
  - **셋 다 선택** — `ADMIN_JWT_SECRET`이 비면 결국 기동 실패한다. Compose에서 2초 만에
    명확히 끊을 수 있는 것을 180초 unhealthy로 미루는 셈이다
- **트레이드오프**: 초기 계정 변수는 Secret 이름을 잘못 적어도 조용히 시딩만 건너뛴다.
  이 구멍은 워크플로우 가드가 아니라 배포 로그(`초기 관리자 계정을 생성했습니다`)로 확인해야 한다

#### 앱의 환경변수 요구사항을 CD 워크플로우에서도 검사한다

- **문제**: 환경변수 누락을 어디서 잡을 것인가. 애플리케이션과 Compose가 이미 각자 검사한다
- **선택**: CD 워크플로우에 사전 가드를 두어 러너 단계에서 중단
- **대안**:
  - **앱과 Compose 검사에만 의존** — 워크플로우가 앱 설정을 몰라도 되어 결합이 없다.
    다만 실패가 배포 후반부에 발생해 이미지 빌드·전송·헬스체크 대기·롤백을 모두 치른 뒤
    드러난다. 이번 사고가 정확히 그 경로였다
  - **CI에서 정적 검사** — `application.yml`의 기본값 없는 `${VAR}`를 뽑아 `write_env`
    목록과 대조하면 PR 단계에서 잡힌다. 누락을 배포 이전에 막는다는 점에서 더 낫지만,
    워크플로우 파일 구조를 파싱하는 방식이라 파일이 바뀌면 검사도 함께 깨진다
- **트레이드오프**: 워크플로우가 애플리케이션의 설정 요구사항을 알게 된다. 환경변수가
  늘어날 때마다 가드도 함께 관리해야 한다
- ⭐ **볼트 승격 권장** — `/capture`로 `knowledge/decisions/`에 등록

#### 재발 방지를 정적 검사가 아니라 문서 규칙으로 둔다

- **문제**: "환경변수 추가 시 세 곳을 함께 고친다"를 어떻게 강제할 것인가
- **선택**: `AGENTS.md`에 절차로 명시. 자동 검사는 이번 범위에 넣지 않는다
- **대안**:
  - **CI 검사 추가** — 확실하게 막지만 워크플로우 파일 구조에 의존한다. 이번 이슈는
    배포 복구가 목적이고, 검사 도입은 별도 판단이 필요하다
  - **아무것도 하지 않음** — 같은 누락이 다음 환경변수에서 반복된다
- **트레이드오프**: 문서 규칙은 읽지 않으면 효력이 없다. 다만 이번 사례는 문서가 사실과
  달라 오히려 잘못된 전제를 준 경우여서, 문서 정정 자체가 원인 제거에 해당한다
- ⭐ **볼트 승격 권장** — `/capture`로 `knowledge/lessons/`에 등록

### 🔧 주요 변경사항 상세

#### write_env를 통한 값 전달

`write_env`는 값을 작은따옴표로 감싸 `app.env`에 기록하고, 값 안의 작은따옴표는 이스케이프한다.
`ADMIN_JWT_SECRET`은 Base64 문자열이라 `+` `/` `=`를 포함하고, 초기 비밀번호에는 임의의
특수문자가 들어갈 수 있다. 이 값들이 변형 없이 컨테이너까지 도달하는지 확인이 필요했다.

**특이사항**:
- `JwtTokenProvider`가 `Decoders.BASE64.decode()` 후 HS256 키로 사용한다. 값은 Base64로
  인코딩된 32바이트 이상이어야 하며, 미만이면 `WeakKeyException`으로 기동에 실패한다
- 기존 `JWT_SECRET`(`app.jwt.secret`)은 현재 읽는 코드가 없다. `admin-secret`과는 별개 키이므로
  값을 재사용하지 않는다

#### 초기 계정 시딩 조건

`AdminAccountSeeder`는 사용자명과 비밀번호가 모두 있으면 계정을 생성하고, 모두 없으면
시딩을 건너뛰며, 하나만 있으면 `IllegalStateException`을 던진다. 워크플로우 가드는 이
세 번째 경우를 러너에서 먼저 걸러 동일한 판정을 앞당긴다.

- **`bash -n` 문법 검사** — 워크플로우의 `run` 블록 7개, heredoc 내부 원격 스크립트 3개 통과

  | `ADMIN_JWT_SECRET` | `ADMIN_INITIAL_USERNAME` | `ADMIN_INITIAL_PASSWORD` | 결과 |
  | --- | --- | --- | --- |
  | 있음 | 있음 | 있음 | 통과 |
  | 없음 | 있음 | 있음 | 중단 |
  | 있음 | 있음 | 없음 | 중단 |
  | 있음 | 없음 | 있음 | 중단 |
  | 있음 | 없음 | 없음 | 통과 (시딩 생략) |

- **값 왕복** — 워크플로우의 `write_env` 함수를 그대로 추출해 `app.env`를 만들고, 실제
  Compose로 컨테이너를 띄워 환경변수를 확인했다. Base64의 `+` `/` `=`, 작은따옴표,
  달러 기호 연속이 포함된 값이 모두 원본 그대로 도착한다 (실제 값은 `{SECRET}` · `{PASSWORD}`로
  대체한 시험용 문자열 사용)

### 📌 참고사항

- Secret 세 개는 `development` Environment에 등록을 마쳤다. `production` Environment는
  아직 만들어져 있지 않으며, 그 상태로 `main`에 푸시되면 `DEPLOY_ENABLED` 가드에서 배포가 중단된다
- 이 PR이 머지되어 배포가 성공하면 이슈 #27의 관리자 인증도 같은 배포로 함께 반영된다.
  현재 `develop`에 코드는 있으나 서버에는 올라가 있지 않은 상태다
- 배포 로그에 `초기 관리자 계정을 생성했습니다` 가 출력되면 시딩까지 정상이다.
  `초기 관리자 환경변수가 없어 시딩을 건너뜁니다` 가 나오면 Secret 이름을 확인해야 한다
- 자동 롤백은 애플리케이션 이미지에 한정된다. 새 이미지가 마이그레이션을 적용한 뒤 기동에
  실패하면 스키마는 되돌아가지 않는다
