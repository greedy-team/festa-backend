### 📌 작업 개요

`develop` · `main`으로 향하는 PR에서 빌드 검증이 자동으로 돌도록 워크플로우를 추가했다.
그 전까지 백엔드에는 PR 단계 검증이 하나도 없어 컴파일이 깨진 코드도 `develop`에 머지될 수 있었다.

### 🔍 문제 분석

- 저장소에 있던 워크플로우는 모두 이슈·릴리스 자동화용이고 빌드 검증은 없었다
- 프론트엔드는 이미 PR 빌드 검증이 돌고 있어 두 레포의 기준이 어긋나 있었다

### ✅ 구현 내용

#### CI 워크플로우 추가

- **파일**: `.github/workflows/PROJECT-SPRING-CI.yaml` (신규, 47줄)
- **변경 내용**: `main` · `develop` 대상 PR과 수동 실행(`workflow_dispatch`)에서 JDK 21(temurin) 구성,
  Gradle 캐시 적용, `./gradlew build` 실행. 이어서 테스트 결과를 PR 코멘트로 요약하고
  실패한 테스트를 해당 코드 줄에 인라인 표시한다
- **이유**: 머지 전에 컴파일과 테스트를 강제하는 지점이 필요했다

주요 설정과 그 이유:

- `concurrency: ci-${{ github.ref }}` + `cancel-in-progress: true` — 같은 브랜치에 새 푸시가 오면
  이전 실행을 취소한다. 러너 점유를 줄인다
- `timeout-minutes: 15` — 매달린 빌드가 러너를 붙잡지 않게 한다
- `permissions`에 `checks: write` · `pull-requests: write` — 리포트 단계가 체크와 코멘트를 쓰려면 필요하다
- 리포트 두 단계 모두 `if: ${{ !cancelled() }}` — 빌드가 실패해도 왜 실패했는지는 보여야 한다.
  실패했을 때 리포트가 안 나오면 CI가 알려주는 값이 사라진다

#### 워크플로우 파일명에 대한 경고 기록

- **파일**: `AGENTS.md`
- **변경 내용**: `PROJECT-SPRING-CI.yaml`이 우리가 쓴 파일이지만 ProjectOps가 차지할 수 있는 이름이라는 주의 추가
- **이유**: 프론트의 `PROJECT-REACT-CI.yaml`이 ProjectOps 제공 템플릿이라 대칭을 택했다.
  업데이트 후 이 파일이 낯설게 바뀌어 있다면 그 경우라는 것을 다음 사람이 알아야 한다

### 🧭 결정 기록 (ADR)

#### 테스트 환경 구성을 이 이슈에서 다루지 않음

- **문제**: 애플리케이션 설정이 `DB_URL` · `DB_USERNAME` · `DB_PASSWORD` · `GOOGLE_CLIENT_ID` ·
  `GOOGLE_CLIENT_SECRET` · `JWT_SECRET` · `AES_KEY` 일곱 개를 필수로 요구한다.
  스프링 컨텍스트를 띄우는 테스트가 처음 추가되는 순간 이 값들이 없어 CI가 실패한다
- **선택**: 워크플로우만 넣고 테스트 환경 구성은 후속 작업으로 분리
- **대안**: 지금 값을 주입해 둠 — 어떤 방식으로 DB를 띄울지가 정해지기 전이라 추측이 된다
- **트레이드오프**: 첫 테스트를 추가하는 사람이 CI 실패를 먼저 만난다. 그래서 조사 결과를 이슈 본문에 남겼다

조사해서 확인한 것:

- H2 인메모리 DB는 쓸 수 없다. `V1__init.sql`이 `pg_trgm` · `unaccent` 확장을 만드는 PostgreSQL 전용 DDL이고,
  Flyway가 켜져 있어 컨텍스트 로딩 시 무조건 실행된다
- 따라서 선택지는 Testcontainers로 실제 PostgreSQL을 띄우거나, CI에 서비스 컨테이너를 붙이는 두 가지다
- **Testcontainers 방향이면 이 워크플로우는 수정할 필요가 없다.** GitHub 러너에 Docker가 이미 있다.
  서비스 컨테이너 방향이면 워크플로우를 고쳐야 한다
- Testcontainers를 써도 일곱 개 중 DB 관련 셋만 해결된다. OAuth 둘과 JWT · AES는 테스트용 기본값이 따로 필요하다

#### 브랜치 보호를 이 이슈에서 다루지 않음

- **문제**: `main` · `develop` 모두 보호되지 않아 이 워크플로우는 머지를 **차단하지 못하고 결과만 알린다**
- **선택**: 워크플로우 추가와 보호 설정을 분리. 차단이 필요하면 별도 작업으로 뺀다
- **대안**: 함께 처리 — 저장소 설정 변경이라 코드 리뷰로 검증되지 않는 영역이 섞인다
- **트레이드오프**: 도입 직후에는 빨간 CI를 무시하고 머지할 수 있다

### 🧪 테스트 및 검증

- 정상 PR에서 통과하는 것만으로는 부족하다는 판단으로, **컴파일 오류를 일부러 넣은 커밋에서 실패하는지**까지를
  검증 기준으로 잡았다. 항상 통과하는 워크플로우를 걸러내기 위한 것이다
- 리포트 단계는 테스트 결과 XML을 읽는데 이 시점 테스트는 0개라 파일이 생성되지 않는다.
  파일이 없을 때 경고만 남는지 단계가 실패하는지는 첫 PR에서 확인하기로 두었다

### 📌 참고사항

- 이 시점에 빌드가 통과하는 이유는 **테스트가 하나도 없기 때문**이다. 테스트 디렉터리 자체가 없었다
- `gradlew`가 변경 파일에 잡혀 있으나 내용 변경은 없다(파일 모드만 변경)
- 배포 관련 사항은 전부 별도 이슈에서 다뤘다
