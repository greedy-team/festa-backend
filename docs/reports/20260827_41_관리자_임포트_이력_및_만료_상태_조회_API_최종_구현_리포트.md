### 📌 작업 개요

`GET /api/admin/imports` 임포트 이력 조회 API를 추가했다.
누가 언제 어떤 파일을 올렸는지, 그 미리보기가 아직 유효한지 커밋됐는지 만료됐는지를
한 목록에서 볼 수 있다.

3단계로 나눈 임포트 기능의 마지막이다. #37이 업로드·검증·미리보기를, #39가 반영과 감사 이력을
맡았고, 이 단계는 **읽기만 한다** — 미리보기를 지우지도 갱신하지도 않는다.

핵심은 **아무것도 새로 저장하지 않고** 상태를 만든다는 것이다. `status` 컬럼도 history 테이블도
두지 않고, `ImportBatch`가 이미 갖고 있는 `committedAt` · `expiresAt`에서 조회 시점에 파생한다.

### 🎯 구현 목표

- type · status 필터와 페이지네이션. 필터는 페이지네이션 **전에** DB에서 적용한다
- `PENDING` · `COMMITTED` · `EXPIRED`를 기존 필드에서 파생한다
- 커밋된 배치는 **실제 감사 행**(`ImportCommitRow`) 기준으로 section별 결과를 준다
- 미리보기 원문과 원본 CSV payload는 응답에 넣지 않는다
- 업로더가 지워진 이력도 오류 없이 나온다

### ✅ 구현 내용

#### 이력 조회 엔드포인트

- **파일**: `importer/controller/ImportAdminController.java`
- **변경 내용**: 기존 `/api/admin/imports`에 `@GetMapping` 하나를 더했다.
  `type` · `status`는 선택, `page` 기본 `0`, `size` 기본 `20`
- **이유**: 업로드·커밋과 같은 컨트롤러에 두어 임포트 관련 경로가 한 클래스에 모인다

`type`과 `status`는 `String`으로 받아 컨트롤러에서 enum으로 옮긴다.
대소문자와 앞뒤 공백을 흡수하고, 모르는 값은 `IMPORT_INVALID_TYPE` ·
`IMPORT_INVALID_STATUS`(신설)로 400을 낸다. 파라미터 타입을 enum으로 선언하면
스프링이 변환 실패를 먼저 던져 공통 에러 형식 밖으로 나간다.

#### 상태 파생

- **파일**: `importer/model/ImportBatchStatus.java`, `importer/service/ImportHistoryService.java`
- **변경 내용**: `PENDING` · `COMMITTED` · `EXPIRED` enum과 판정 로직
- **이유**: 상태는 저장된 값이 아니라 **시각에 대한 함수**다. 저장하면 만료 순간마다 누군가
  갱신해 줘야 한다

```
committedAt != null                        → COMMITTED
committedAt == null && expiresAt <= now    → EXPIRED
그 외                                       → PENDING
```

커밋된 배치는 `expiresAt`이 지났어도 항상 `COMMITTED`다. 경계 `expiresAt == now`는 `EXPIRED`이며,
서비스가 `!expiresAt.isAfter(now)`로 써서 등호를 EXPIRED 쪽에 붙였다.

`now`는 **요청당 한 번만** `importClock.instant()`로 뽑아 필터 쿼리와 응답 매핑에 같은 값을 넘긴다.
두 번 읽으면 그 사이에 만료된 배치가 필터에는 PENDING으로 걸리고 표시는 EXPIRED로 나갈 수 있다.

#### 필터를 DB로 내린 조회

- **파일**: `importer/repository/ImportBatchRepository.java`
- **변경 내용**: `findHistory(type, status, now, pageable)` — type과 파생 status 조건을
  JPQL `WHERE`에 넣고 `@EntityGraph(attributePaths = "uploadedByAdmin")`을 붙였다
- **이유**: 필터를 메모리에서 하면 `totalElements` · `totalPages`가 필터 결과와 어긋난다.
  페이지네이션 전에 DB가 걸러야 페이지 정보가 사실이 된다

`:type IS NULL OR ...` 형태로 두 필터를 각각 선택적으로 만들고, 함께 오면 AND가 된다.
정렬은 `Sort.by(desc("uploadedAt"), desc("id"))`로 서비스가 고정한다.

업로더는 `@ManyToOne(fetch = LAZY)`라 그대로 두면 배치마다 조회가 나간다.
`@EntityGraph`로 한 번에 끌어와 N+1을 막았다.
`fileNames`는 `@JdbcTypeCode(SqlTypes.ARRAY)`라 별도 테이블이 아니어서 추가 조회가 없다.

#### 커밋 결과 집계

- **파일**: `importer/repository/ImportCommitRowRepository.java`,
  `importer/repository/ImportCommitAggregateRow.java`, `importer/service/ImportHistoryService.java`
- **변경 내용**: 페이지 안의 커밋된 배치 id를 모아 `aggregateByBatchIds`로
  `(batchId, section, action)` 그룹 카운트를 **한 번에** 가져온다
- **이유**: 배치마다 집계 쿼리를 던지면 페이지 크기만큼 쿼리가 늘어난다

집계 결과는 `CountsBySection` → `ActionCounts`로 접혀 `artists` · `festivals` · `lineups`
각각의 `created` · `updated` · `skipped`가 된다. 감사 행이 없는 조합은 `0`이다.
`failed`는 응답에 없다.

`PENDING` · `EXPIRED`의 `result`는 `null`이고, 커밋됐지만 감사 행이 0건인 배치는
**0으로 채워진 객체**다. 둘이 구분된다.

#### 응답 DTO

- **파일**: `importer/dto/ImportHistoryItemResponse.java`, `ImportHistoryResult.java`,
  `ImportHistorySectionResult.java`
- **변경 내용**: `importId` · `type` · `fileNames` · `status` · `uploadedBy` ·
  `uploadedAt` · `expiresAt` · `committedAt` · `result`. 페이지 겉은 기존 `PageResponse`
- **이유**: 미리보기 원문 필드를 아예 두지 않아 실수로도 새 나갈 수 없게 했다

`uploadedBy`는 `uploadedByAdmin.username`이며 관계가 `null`이면 응답도 `null`이다.
백엔드가 「알 수 없음」 같은 문구를 만들지 않는다 — 표시 문구는 프론트가 갖는다.

#### 인덱스

- **파일**: `src/main/resources/db/migration/V20260826_0000__import_history_indexes.sql`
- **변경 내용**: `import_commit_row(batch_id)`, `import_batch(uploaded_at DESC, id DESC)`
- **이유**: 집계는 `batch_id IN (...)`로 들어가고 목록은 `uploaded_at DESC, id DESC`로 정렬한다.
  둘 다 이 API가 매번 타는 경로다

### 🧭 결정 기록 (ADR)

#### 상태를 컬럼에 저장하지 않고 조회 시점에 파생

- **문제**: `PENDING` / `COMMITTED` / `EXPIRED`를 어디에 둘지
- **선택**: 저장하지 않는다. `committedAt` · `expiresAt`과 `now`로 매 조회마다 계산한다
- **대안**: `status` 컬럼 추가 — 커밋 때는 갱신할 수 있지만 **만료에는 이벤트가 없다.**
  30분이 지나는 순간을 알려줄 주체가 없어 스케줄러를 붙여야 하고,
  그 스케줄러가 밀리면 DB가 `PENDING`이라 말하는데 실제로는 만료된 상태가 된다
- **트레이드오프**: 상태로 필터하려면 그 규칙이 SQL에도 있어야 한다.
  같은 규칙이 JPQL과 자바 양쪽에 존재하게 된다 — 아래 참고사항 참조
- ⭐ **볼트 승격 권장** — 만료를 값이 아니라 시각의 함수로 다루는 판단이고 후속 cleanup 이슈가 여기 걸린다

#### `result`를 미리보기가 아니라 감사 행에서 집계

- **문제**: 커밋 결과를 어디서 읽을지. `ImportBatch.preview`에 예상 action이 이미 있다
- **선택**: `ImportCommitRow`의 실제 `section` · `action`을 집계한다
- **대안**: preview 집계 — **예상과 실제가 갈리는 자리가 이미 셋이다.**
  부분 커밋에서 선택하지 않은 행은 감사 행이 없고, 미리보기 이후 발행된 축제는
  UPDATE가 실제로는 SKIP으로 실행되며, INVALID는 감사 행을 만들지 않는다.
  preview로 집계하면 **일어나지 않은 일을 이력이라고 말하게 된다**
- **트레이드오프**: 조회가 한 번 더 든다. 배치 id를 묶어 한 번에 집계해 페이지당 1회로 눌렀다

#### 필터를 메모리가 아니라 DB 쿼리에 넣음

- **문제**: 파생 상태는 컬럼이 아니라서 자바에서 거르는 쪽이 쓰기 쉽다
- **선택**: JPQL `WHERE`에 세 상태의 조건식을 직접 적었다
- **대안**: 전체를 읽어 자바에서 필터 — `totalElements`가 **필터 전 개수**가 되어
  페이지 정보가 거짓말을 한다. 관리자가 「24건」을 보고 2페이지를 눌렀는데 비어 있는 식이다
- **트레이드오프**: 상태 규칙이 JPQL 문자열로 들어가 컴파일러가 지켜주지 않는다

#### 이 API는 아무것도 정리하지 않는다

- **문제**: 만료된 미리보기를 조회하는 김에 지울 수 있다
- **선택**: 읽기만 한다. lazy cleanup도 스케줄러도 넣지 않는다
- **대안**: 조회 시 정리 — GET이 데이터를 지우게 되고, 목록을 여는 사람이
  누군가 커밋하려던 미리보기를 없앨 수 있다
- **트레이드오프**: 만료 미리보기가 계속 쌓인다. 정리 정책과 주체는 후속 이슈로 남겼다

### 📌 참고사항

**이슈 본문의 `/api` 조항은 이미 낡았다.**
이슈는 *"`/api` prefix를 붙이지 않는다 — DEC-0084"*라고 적었으나, 그 결정은 8/23에
DEC-0099로 대체됐고 이슈 #60이 컨트롤러 5개를 전부 `/api` 아래로 옮겼다.
머지된 실물은 `/api/admin/imports`다. **구현이 이슈가 아니라 최신 결정을 따랐다.**
이슈 본문은 작성 시점(8/19)에 옳았고 그 뒤 전제가 바뀐 것이다.

**완료 조건과 실제 마이그레이션이 어긋난다.**
이슈는 *"별도 status 컬럼, history table, Flyway migration을 추가하지 않는다"*를
완료 조건에 넣었는데, `V20260826_0000__import_history_indexes.sql`이 추가됐다.
**컬럼도 테이블도 늘지 않았으니 조항의 취지는 지켰지만 문장 자체와는 맞지 않는다.**
인덱스는 스키마 구조가 아니라 조회 성능을 위한 것이고 두 인덱스 모두 이 API의 실제 경로를 따른다.

**새 엔드포인트에 Swagger 설명이 없다.**
같은 컨트롤러의 미리보기 엔드포인트 둘에는 `@Operation` · `@ApiResponse`가 붙어 있는데
이력 조회에는 없다. 이슈 #66이 관리자 컨트롤러를 문서화하면서
*"임포트는 이슈 #39·#41이 엔드포인트를 더 붙이는 중이다. 그 PR들이 추가하는 엔드포인트는
각 PR에서 직접 설명을 달고"*라며 넘긴 자리다. **넘긴 쪽도 받은 쪽도 채우지 않아 비어 있다.**
`type` · `status`가 `String`이라 허용값이 시그니처로 드러나지 않는 자리라 더 필요하다.

**상태 규칙이 두 곳에 있다.**
필터용 조건은 `ImportBatchRepository.findHistory`의 JPQL에, 표시용 판정은
`ImportHistoryService.statusOf`에 있다. 현재 둘은 일치하고(`expiresAt <= now`와
`!isAfter(now)`), `now`를 한 번만 뽑아 넘기므로 한 요청 안에서 갈릴 수 없다.
다만 **한쪽만 고치면 필터에 걸린 배치와 표시된 상태가 어긋난다** — 오류 없이 틀린 결과가 나온다.

- **status가 JPQL에 문자열 리터럴로 들어간다.** 서비스가 `status.name()`을 넘기고
  쿼리가 `:status = 'COMMITTED'`로 비교한다. `ImportBatchStatus`의 상수 이름을 바꾸면
  컴파일은 통과하고 필터만 조용히 아무것도 못 찾게 된다
- **`ImportHistoryService`의 Clock 필드명이 `importClock`이다.** 현재 저장소에 `Clock` 빈은
  `ClockConfig.clock()` 하나뿐이라 타입으로 해결되어 동작한다. 이름은 두 개의 Clock 빈이 있던
  시절의 잔재이며, 나중에 Clock 빈이 다시 둘이 되면 이 필드가 이름 폴백에 의존하게 된다
- 미리보기 정리(cleanup)의 정책과 실행 주체는 이 이슈 범위 밖이다.
  만료된 배치 행은 그대로 남고, 미리보기가 이미 정리된 배치도 `committedAt` · `expiresAt`만으로
  상태 조회가 된다
